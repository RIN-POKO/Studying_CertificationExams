第 1 章 AI の能力と限界（AI Capabilities and Limitations）

💡 ヒント

この章のたとえ：超高速で博識だが、現場の責任は持てない「リサーチアシスタント」

大量の文献を読み込み、数秒でコードや文章の下書きを作れる優秀なアシスタントがいます。ただし、このアシスタントは「次に来る最も自然な言葉」を確率で紡ぎ出しているため、知らないことも自信満々に言い切ることがあります。何が任せてよい作業で、どこからが人間の責任かを切り分けることが出発点になります。

この章のゴール

  • LLM がテキストやコードを生成する基本原理（次トークン予測）と、そこから生じる強み・弱みを説明できる。
  • Hallucination やコンテキスト劣化（Context Rot / Drift）が起きる構造的な理由を理解し、対策を選べる。
  • モデルが予期しない出力を返したときに、原因を切り分けて対処する手順を説明できる。
  • 顧客や開発チームに対して、AI に任せるべき作業と人間が最終判断すべき境界を明確に伝えられる。

要点 3 つ

  1. LLM の強みと限界は、どちらも同じ仕組みから生まれる。 次トークン予測（Next-Token Prediction）と大規模なパターン学習により、要約・変換・コード生成で高い性能を発揮する一方、事実の真偽を自動で検証する仕組みは持たない。
  2. コンテキストウィンドウには「容量」だけでなく「注意の限界」がある。 入力が長くなるほど指示の抜け漏れや焦点のぼやけ（Contextual Drift）が起きやすいため、必要な情報だけを整理して渡す設計が欠かせない。
  3. LLM には自律的な意図や現実世界の責任能力がない。 下書きの作成・構造化・選択肢の列挙は AI に任せ、セキュリティ承認・アーキテクチャの最終決定・対外的な責任は必ず人間が引き受ける。

本編

1-1 LLM が得意な領域と苦手な領域

Forward Deployed Engineer（FDE）として顧客の課題に向き合うとき、最初に問われるのは「この課題は LLM で解くべきか、どの部分に使うべきか」の見極めです。LLM の能力と限界は対になっており、性質を正確に把握することで過剰な期待や誤用を防げます。

観点得意な領域（AI に向いている）苦手な領域（人間や決定論的コードが担う）
情報処理非構造化テキストの要約、分類、JSON 等の構造化データ抽出厳密な数値計算、暗号処理、100% 再現性が必要な決定論的処理
生成・執筆コードの下書き生成、リファクタリング案、ドキュメント草案組織固有の暗黙知を前提とした最終意思決定、法的・倫理的責任を伴う承認
推論・探索複数の観点からのアイデア出し、ログやコードのパターン照合学習データやコンテキストにない最新事実の正確な再現（検索なし）
状況認識与えられたコンテキスト内での整合性チェックや変換現実世界の暗黙の制約、社内の政治的背景、未知の障害への責任ある対処
📌 重要

顧客が「AI にすべてを自動で判断させたい」と要望した場合でも、FDE は「正確性・再現性・説明責任」が求められる箇所を決定論的なコードや人間のレビューゲートとして設計に組み込む必要があります。

1-2 予期しない出力が起きる 4 つの原因と切り分け

モデルが期待どおりに動かないとき、闇雲にプロンプトを書き直すのではなく、どの層で問題が起きているかを切り分けます。

  1. 知識の不足（Knowledge Gap）は、最新の仕様や社内固有のルールが Parametric Memory に含まれていないために起きます。プロンプトや外部検索（RAG・ツール）でコンテキストに根拠を与える必要があります。
  2. 指示の曖昧さ（Ambiguity）は、成功条件や出力形式、禁止事項が明示されていないために起きます。モデルが一般的なパターンで補完してしまうため、制約と具体例を明記します。
  3. コンテキスト過多・劣化（Context Overload / Drift）は、無関係なログや長大な履歴を詰め込みすぎて重要な指示が埋もれる状態です。不要な情報を削り、重要な制約を明確に配置します。
  4. 能力の境界（Capability Boundary）は、複雑な多段階の厳密計算やツールなしのリアルタイム情報取得など、LLM 単体の性質上不得手な作業を直接頼んでいる状態です。外部ツールやコード実行に委ねる設計へ切り替えます。

1-3 AI の限界を踏まえた安全・信頼性の原則

  • 非決定性を前提にし、同じ入力でも出力が揺れる可能性に備えて、本番利用では構造化出力の検証や自動テストを組み合わせます。
  • 「もっともらしさ」と「正しさ」を切り離し、モデルが流暢に回答しても根拠（出典ファイル、ツール結果、事実データ）が伴っているかを必ず検証します。
  • Human-in-the-Loop（人間による確認）の境界を引き、取り消せない操作（本番データの削除、外部送信、契約判断）の前には人間の承認を挟みます。

まとめ：どう判断するか

状況避ける選択とるべき選択
社内固有の業務ルールに関する質問でモデルが誤答するモデルに「正確に思い出して」とプロンプトで念押しする社内ドキュメントを検索ツールやコンテキスト経由で明示的に渡す
複雑な金額集計をモデルの暗算に任せたら端数がずれたより丁寧な言葉遣いで計算をやり直させる計算処理自体はコードやツールに任せ、モデルには解釈や要約を任せる
長い会話の後半でモデルが冒頭のフォーマット指定を忘れた会話履歴をさらに増やして注意文を何度も繰り返す不要な履歴を整理し、必要な制約だけを再提示するかセッションを分ける
セキュリティ要件の最終承認を AI のレビューだけで通したい高性能モデルに切り替えて承認作業も完全に自動化するAI には論点抽出と一次チェックを任せ、最終承認は人間が行う

確認問題

問 1

ある顧客が過去の商談議事録（テキスト）から「決定事項」「課題」「次のアクション」を抽出し、同時に契約金額の複雑な日割り計算と請求書発行の最終承認までをすべて LLM 単体の 1 回の呼び出しで自動化したいと相談してきました。FDE として最も適切な提案はどれですか。

A. 最新の大規模モデルを使えば計算も承認も 1 回で完結できると提案する
B. 議事録からの項目抽出・要約は LLM に任せ、日割り計算は決定論的なコード、請求書発行の最終承認は人間が担う役割分担を提案する
C. プロンプトに「計算を絶対に間違えないでください」と追記して全工程を自動化する
D. 議事録を学習データとして毎回ファインチューニングしてから計算させる

解答

B。非構造化テキストからの情報抽出・要約は LLM が得意とする領域ですが、厳密な数値計算は決定論的コード、不可逆で責任を伴う請求承認は人間が担うべきです。

問 2

社内規定に関する Q&A ボットを開発中、モデルが実際には存在しない社内制度の名前を挙げて非常に流暢に回答してしまいました。この現象の主な原因と最初の対処として最も適切なものはどれですか。

A. モデルが意図的に嘘をついているため、温度設定ではなくモデルの倫理ガイドラインを書き換える
B. 社内固有の情報がモデルの Parametric Memory にないまま回答生成（Hallucination）しているため、検索等で公式ドキュメントをコンテキストに与え、根拠がない場合は「分からない」と答えるよう指示する
C. モデルのコンテキストウィンドウが不足しているため、質問文を 1 単語に短縮する
D. 出力トークン上限を増やして、モデルが正しい答えにたどり着くまで長く書かせる

解答

B。LLM は次トークン予測によってもっともらしい文を生成するため、根拠となる知識が与えられないと Hallucination が起きやすくなります。根拠資料をコンテキストへ渡し、不明時は回答を控える設計が有効です。

問 3

長時間のチャット支援ツールで、会話が 30 往復を超えたあたりから、最初に指定していた「出力は必ず箇条書き 3 点以内」という制約をモデルが無視するようになりました。最も可能性が高い原因はどれですか。

A. モデルがユーザーに飽きて指示を拒否している
B. 蓄積された会話履歴によってコンテキストが膨らみ、初期指示への注意が薄れる Contextual Drift が起きている
C. Next-Token Prediction は 30 往復を超えると必ず停止する仕様になっている
D. モデルの重みが会話中に書き換わってしまった

解答

B。コンテキストウィンドウに長大な履歴が溜まると、初期の制約が相対的に埋もれて出力品質が落ちる Contextual Drift が発生します。履歴の整理や制約の再配置が必要です。

第 2 章 ビルダー向け AI フルーエンシーと 4D フレームワーク（AI Fluency for Builders）

💡 ヒント

この章のたとえ：優秀な開発パートナーへの「仕事の任せ方・伝え方・検収・出荷責任」

単にプロンプトの小手先テクニックを覚えるのではなく、「どの仕事を任せるか（Delegation）」「何をどう伝えるか（Description）」「上がってきた成果物をどう見抜くか（Discernment）」「自分の名前で世に出せる状態まで責任を持てるか（Diligence）」という 4 つの習慣を揃えることが、ビルダーにとっての AI 活用力になります。

この章のゴール

  • Anthropic が定義する AI Fluency（有効・効率的・倫理的・安全な協働）の意味を説明できる。
  • 4D Framework（Delegation / Description / Discernment / Diligence）の 4 要素と、それぞれの実務上のチェックポイントを説明できる。
  • Description を構成する 3 つの視点（Product / Process / Performance）を使い分けて明確な指示を書ける。
  • 顧客や開発チームに AI 協働ワークフローを導入する際、人間が主導権（Driver's Seat）を握り続ける設計を示せる。

要点 3 つ

  1. AI Fluency とはプロンプトの暗記ではなく「協働の型」である。 AI と有効（Effective）・効率的（Efficient）・倫理的（Ethical）・安全（Safe）に協働し、人間が主導権を保ちながら成果を出す力を指す。
  2. 4D Framework が設計から出荷までの全工程を支える。 Delegation（委任）・Description（記述・指示）・Discernment（識別・評価）・Diligence（注意・責任）の 4 つが揃って初めて、本番に耐える開発ができる。
  3. 「実装は委任できても、最終判断は委任できない」。 テストや下書きの生成は Claude に任せられるが、要件の妥当性・セキュリティ・アーキテクチャの最終判断と出荷責任はビルダー自身が負う。

本編

2-1 Delegation：何を任せ、何を人間が持つか

FDE やビルダーが最初に陥りやすい失敗は、「全部 AI に丸投げする」か「逆に何も任せず手作業に固執する」かの両極端です。Delegation では、タスクの性質とリスクに応じて分担を決めます。

観点AI に委任しやすい作業人間が保持すべき判断
設計・仕様仕様書の叩き台作成、エッジケースの洗い出し業務要件の優先順位付け、顧客との合意形成
実装・テストボイラープレート作成、単体テスト生成、リファクタリング案コアアーキテクチャの選定、不可逆なデータ移行判断
レビュー・調査ログの一次整理、既知パターンのバグ候補抽出セキュリティ上の最終承認、本番リリース可否の判断
📌 重要

コアとなる判断基準は 「実装（Implementation）の委任は多くの場合安全だが、最終判断（Final Judgment）の委任は危険である」 という点です。

2-2 Description：3 つの視点で明確に伝える

「ログイン画面を作って」のような曖昧な依頼では、前提の食い違いがそのまま手戻りにつながります。ビルダー向けの Description では、次の 3 つを意識して指示を組み立てます。

  1. Product Description（何を作るか）: 目的、対象ユーザー、満たすべき要件、出力フォーマット、制約条件。
  2. Process Description（どう進めるか）: 手順、採用すべき技術・設計方針、避けるべきアプローチ、段階的な確認ポイント。
  3. Performance Description（どう振る舞うか）: 協働中の AI の役割や姿勢（例：「厳格なコードレビュアーとして、実装前に私の前提の穴を指摘してから進めてください」）。

この 3 つを分けることで、AI は「何を出せばよいか」だけでなく「どの順序で、どのような基準で思考すべきか」を把握しやすくなります。

2-3 Discernment：出力を批判的に見抜く

Claude が読みやすいコードや整った提案書を返しても、そのままコピー＆ペーストしてはいけません。Discernment では、以下の観点で出力を検証します。

  • 正確性: 要件や仕様と食い違っていないか、存在しない API や設定値を作り出していないか。
  • 品質と保守性: 過剰な複雑化や不要な依存関係、将来的な技術的負債を増やしていないか。
  • 前提の妥当性: AI が暗黙のうちに置いた仮定が、顧客環境の制約と矛盾していないか。

2-4 Diligence：責任を持って出荷する

Diligence は、技術的な正しさにとどまらず「プロフェッショナルとして世に出せる状態か」を担保する姿勢です。

  • セキュリティとプライバシー: 機密情報や認証情報をプロンプトに不用意に含めていないか、生成コードに脆弱性（インジェクション、権限漏れ等）がないか。
  • 透明性と説明責任: AI の支援を受けた成果物であっても、仕組みと根拠を自分の言葉で顧客やチームに説明できるか。
  • ライセンスとコンプライアンス: 顧客の組織ポリシーや著作権・ライセンス要件に違反していないか。

まとめ：どう判断するか

状況避ける選択とるべき選択
顧客向けの設計書を急いで作る必要があるAI に一言だけ投げて生成文をそのまま提出するDelegation で下書きを任せ、Description で要件と制約を伝え、Discernment と Diligence で人間が検証してから提出する

3-2 プラットフォームの 4 つの基礎メカニズム

  2. コンテキストとトークンの経済性として、入力（Prompt）と出力（Completion）の両方がトークン単位で計算されます。大量の固定指示や資料を毎回送る場合は、後続のコスト最適化（Prompt Caching や必要最小限のコンテキスト抽出）を視野に入れて構造を整理します。
  3. マルチモーダル（Vision 等）を活用すると、請求書画像、画面スクリーンショット、図表を含む PDF などをそのまま入力して構造化データを取り出せるため、従来の OCR 前処理パイプラインを簡素化できる場合があります。
  4. Tool Use による外部接続では、モデルにツール定義（名前・説明・入力スキーマ）を渡すことで、モデルが必要なときにツール呼び出しを要求します。アプリケーション側がそのツールを実行して結果を返すことで、社内 DB 検索やチケット起票などの実業務と連携できます。

第 4 章 適切な Claude モデルの選定（Choosing the Right Claude Model）

💡 ヒント

この章のたとえ：用途に応じた「車両の使い分け」

すべての荷物を大型トラック（Opus）で運ぶとコストと時間がかかりすぎ、逆に軽自動車（Haiku）に重い重機を積むと途中で止まってしまいます。日々の配送はバランスのよい中型車（Sonnet）を軸にしつつ、試作や大量の軽作業には軽自動車、高難度の長距離・精密作業には大型トラックを選ぶ、という使い分けがモデル選定の本質です。

この章のゴール

  • Claude の主要モデルティア（Opus / Sonnet / Haiku 等）の特性と得意なワークロードを説明できる。
  • モデル選定の 3 つの評価軸（Capabilities / Speed & Latency / Cost & Budget）のトレードオフを整理できる。
  • モデル自体を切り替える前に調整できる Effort パラメータ の役割を理解する。
  • Efficiency-First Approach と Capability-First Approach の 2 つの導入戦略を場面に応じて使い分けられる。

要点 3 つ

  1. 「常に最強のモデル」ではなく、タスクの複雑さと制約に合わせて選ぶ。 Opus（最高難度の推論・長時間の自律コーディング）、Sonnet（知能と速度の最適バランス・汎用開発）、Haiku（超高速・低コスト・大量分類やルーティング）を使い分ける。
  2. **モデルを変える前に effort パラメータでの調整も検討する。** 同一モデルファミリー内でも推論の深さ（Effort）を調整することで、レイテンシ・コストと回答品質のバランスを制御できる。
  3. 2 つのアプローチ（Efficiency-First / Capability-First）を使い分ける。 低リスク・高頻度で素早く試したいなら Efficiency-First（軽量モデルから開始）、高難度・失敗が許されない業務でまず成立性を確かめるなら Capability-First（高性能モデルから開始して最適化） をとる。

  Q -->|最難関・長時間エージェント| OP[Claude Opus / 上位モデル]
  Q -->|汎用開発・業務標準バランス| SO[Claude Sonnet]
  Q -->|大量処理・低遅延・ルーティング| HA[Claude Haiku]
  OP --> EFF[Effort パラメータとキャッシュで最適化]
  SO --> EFF
  HA --> EFF

Claude Sonnet高い知能と高速な応答を両立したバランス型ティア。一般的なアプリケーション開発や日常業務の主力

4-1 モデルティアの比較と使い分け

Claude のモデルラインナップは、単一の優劣ではなく「どの業務制約を優先するか」で設計されています。

モデルティア強み主な適用ワークロード注意点

4-2 選定を左右する 4 つの評価軸

  1. Capabilities（必要な能力）として、複雑なツール連携、長文コンテキストの統合、高度なコード生成が必要かを見極めます。
  2. Speed & Latency（速度と待ち時間）として、ユーザーが画面の前で待っている（インタラクティブ）か、夜間の非同期バッチ処理かを確認します。
  3. Cost & Budget（コストと予算）として、1 日あたりのリクエスト数や 1 件あたりの入力トークン量に対して採算が合うかを評価します。
  4. Effort Parameter（推論の深さ）を調整することで、モデルティアを上げ下げする前に同じモデル上で要件を満たせるか確認します。たとえば、単純な問いには低い Effort で即答させ、複雑な分析だけ Effort を引き上げる運用ができます。

4-3 2 つの導入アプローチ

顧客のパイロット案件を立ち上げる際、FDE はタスクの性質に応じて 2 つの進め方を選びます。

第 5 章 デリバリーメソドロジー（Delivery Methodology）

💡 ヒント

この章のたとえ：大きな建物を建てる前の「測量とモデルルーム建築」

顧客から「全社業務を AI で自動化したい」と相談されたとき、いきなり全社システムの設計図を引き始めると予算も時間も破綻します。まずは現在の作業時間やエラー率を測量し（Baseline Establishment）、最初に価値を示せる 1 部屋（First Slice）に絞ってモデルルーム（Pilot）を建て、合意した合格基準で評価する手順がデリバリーメソドロジーです。

この章のゴール

  • Use-Case Qualification により、LLM・エージェント適用に適した顧客課題を厳選できる。
  • コードやプロンプトを書く前に Baseline Metrics と定量的な Success Metrics を定義できる。
  • 全社一括ではなく First Slice に絞った Pilot Design を行える。
  • Delivery Plan Pack を構成する成果物（ユースケース評価・パイロット設計・ROI Scorecard・リスク管理）を説明できる。

要点 3 つ

  1. コードを書く前に Baseline と Success Metrics を合意する。 導入前の所要時間・精度・エラー率を数値で押さえ、何をもってパイロット成功とみなすかを事前に握っておくことで、後からの評価ブレを防ぐ。
  2. 「First Slice」に絞って素早く価値を証明する。 最初から全社横断の巨大システムを狙わず、インパクトが大きく複雑さが制御できる業務の切り口を選んでパイロットを回す。
  3. Delivery Plan Pack で関係者間の期待値とリスクを構造化する。 ユースケース適格性、パイロット境界、ROI Scorecard、マイルストーン・依存関係・リスク対策を一式で文書化し、本番移行の判断材料を揃える。

本編

5-1 Use-Case Qualification：案件の適格性を見極める

顧客の要望をすべてそのまま引き受けるのではなく、FDE は最初に「成功確率が高く、投資対効果が見合うか」を査定します。

評価軸適している課題注意・見直しが必要な課題
ビジネス価値反復頻度が高く、1 件あたりの処理時間や人手コストが大きい年数回しか発生せず、自動化しても効果が見合わない
技術的適合性非構造化データの読解、要約、分類、コード生成、知識検索が中心100% 決定論的な厳密計算や、リアルタイム超低遅延制御のみが目的
データと検証参照すべき正解データや評価基準が社内に存在し、人手で検証できる正解の定義が曖昧で、誰も出力の良し悪しを判定できない
顧客の関与現場の業務オーナーと意思決定者がパイロットに参加できる現場不在で IT 部門だけが「何か作ってほしい」と依頼している

5-2 Baseline Establishment と Success Metrics

パイロット終了後に「なんとなく便利になった気がするが投資対効果が分からない」という状態（Pilot Fatigue）を防ぐため、実装前に必ず数値の物差しを置きます。

  1. 現状の計測（Baseline）では、AI 導入前に人間が同じ作業を行った場合の平均所要時間、手戻り率、処理件数、既存ツールの精度を記録します。
  2. 成功基準の合意（Success Metrics）では、「応答精度 90% 以上」「1 件あたり調査時間を 30 分から 5 分へ短縮」のように、ビジネス側と技術側の双方が納得できる合格ラインを明文化します。
  3. 評価データの準備として、実際の業務に近いテストケースをあらかじめ確保し、主観的な感想ではなく定量評価で改善を回します。

5-3 First Slice による Pilot Design

企業の大規模ワークフローを最初からすべて置き換えようとすると、権限調整や例外処理で頓挫しやすくなります。

  • 境界を明確にする: 対象部署、入力データの種類、連携するシステムを最小限に絞ります。
  • Human-in-the-Loop を前提に組む: 初期パイロットでは完全自律実行にこだわらず、人が最終確認する半自動化から始めて安全に実績を作ります。
  • 段階的拡張を設計する: First Slice が目標を達成したあとに、次のスライスへどう広げるかの道筋を描いておきます。

5-4 Delivery Plan Pack の構成

Anthropic のデリバリー手法では、顧客と合意形成するための標準成果物として Delivery Plan Pack を整備します。

  • Use-Case Qualification Summary: 選定理由、対象業務、期待されるビジネスインパクト。
  • Pilot Architecture & Scope: 実行環境、連携システム、First Slice の範囲、対象外（Out of Scope）の明記。
  • ROI Scorecard: 現状の Baseline、開発・運用コスト、目標削減効果の試算。
  • Milestones, Dependencies & Risk Mitigation: 週次マイルストーン、顧客側の前提作業（データ提供・権限付与）、想定リスクと回避策。

まとめ：どう判断するか

状況避ける選択とるべき選択
顧客が「全 10 部署の業務を一度に AI 化したい」と要望した全社一括の巨大プロジェクトとして見積もり・実装を始める最も効果が高く検証しやすい First Slice（1 部署・1 業務）に絞ってパイロットを設計する
開発を始める前に顧客が指標設定を後回しにしようとしているまず動くものを作り、評価基準は最後に考える実装前に Baseline Metrics と Success Metrics を文書で合意する
顧客が「精度が良ければ導入する」と曖昧に述べている開発側の感覚で「良さそう」と判断して開発を進めるDelivery Plan Pack に具体的な合格数値と評価手順を落とし込む
パイロットで外部 API 連携の承認に 2 か月かかることが分かった承認待ちでプロジェクト全体を停止させるモックデータや読み取り専用の範囲で First Slice を先行させ、依存関係をリスク管理表で追う

  • パイロット成功後に起きやすい「ライセンス配布止まり」と 30-Day Fade の構造的原因を説明できる。

6-1 なぜ「30-Day Fade」が起きるのか

多くの企業導入で、技術的なパイロットやライセンス配布は順調に進んだにもかかわらず、数週間後にアクティブ率が急落します。主な原因は次の 3 点です。

  • 日常業務との接続不足により、「何に使えばよいか」が抽象的なままで、自分の毎日のタスクにどう当てはめるかが分からない。
  • 最初の失敗体験として、曖昧なプロンプトで期待外れの結果が出たとき、相談できる相手がおらずそのまま使わなくなる。
  • 組織的な後押しとルールの欠如により、「使ってよいデータか分からない」「上司や評価制度が AI 活用を推奨していない」という心理的ブレーキが残っている。

6-2 チェンジマネジメントの 4 本柱

30-Day Fade を乗り越え、組織全体の習慣に変えるために、以下の 4 つを並行して整備します。

柱具体的な施策ねらい
1. Champion Network各部門から意欲的な実務者を選出し、Slack / Teams の専用チャネルで質問対応や成功事例の共有を担うIT 部門任せにせず、現場の言葉で素早く疑問を解消できる体制を作る
2. 職種別 Enablementエンジニア、法務、財務、CS など職種ごとに「明日から使える実例プロンプトとワークフロー」をハンズオンで学ぶ一般的な操作説明ではなく、自分の業務時間に直結する成功体験を提供する
3. ガバナンスと安心感入力してよいデータ区分、禁止事項、レビュー責任のルールを明確にし、迷わず使える基準を示すコンプライアンス不安による利用萎縮と、無秩序なシャドー AI 利用の両方を防ぐ
4. 業務リズムへの組み込み定例の会議準備、週次レポート、共有 Projects、再利用可能な Skills としてチームの標準手順に組み込む「余裕があるときに使う道具」から「いつもの業務手順の一部」へ変える

6-3 他部門へのワークロード横展開（Expansion）

最初のパイロット部門で定着が進んだら、成果データをもとに次の展開先を選定・順序付けします。

  1. 定量成果の可視化: 削減時間、対応件数、品質改善を社内事例として経営層と現場双方へ共有する。
  2. 次期ワークロードの優先順位付け: 「データ整備度」「業務頻度」「部門の推進意欲」を基準に、エンジニアリング、法務、財務、カスタマーサポートなどから次の展開先を選ぶ。
  3. テンプレートの再利用: 先行部門で磨き込んだワークフローやガバナンス基準を横展開し、立ち上げコストを下げる。

状況避ける選択とるべき選択

確認問題

問 1

ある企業で全社員向けに Claude を導入し、最初の 2 週間は高い利用率を記録しました。しかし 4 週間後には、もともと新しい技術に関心が高かった一部社員しか使わなくなっていました。この現象と、立て直し策として最も適切なものはどれですか。

A. 一時的なシステム障害が起きているため、モデルティアを最上位に変更する
B. 導入直後の利用が 1 か月前後で落ち込む 30-Day Fade が起きているため、部門ごとの Champion Network 構築や職種別トレーニング、専用サポートチャネルで日常業務への定着を支援する
C. 利用しない社員への罰則規定を設け、強制的にアクセス数を増やす
D. 導入に失敗したと判断して全アカウントを解約する

解答

B。ツールを配布しただけでは 30-Day Fade が起きやすいため、現場に近い Champion の支援と職種に即した Enablement により、日常業務へ組み込むチェンジマネジメントが必要です。

問 2

法務部・財務部・カスタマーサポート部へ Claude の活用を広げる際、全社一律の一般的な使い方説明会ではなく Role-Based Training を行う最大の理由はどれですか。

A. 部門ごとに使える文字数上限が異なるため
B. 各職種の日常業務に直結する具体的なユースケースで成功体験を作らないと、実務への定着が進まないため
C. 法務部には英語だけで説明する必要があるため
D. トレーニング回数を増やしてライセンス費用を上げるため

解答

B。汎用的な機能紹介だけでは「自分の仕事でどう使うか」が結びつかず定着しません。職種別の実務シナリオで学ぶことで、即座に業務時間を削減できる実感が生まれます。

問 3

エンタープライズ導入を成功させるためのガバナンス設計として、最も適切な考え方はどれですか。

A. リスクをゼロにするため、どの部門でも業務データの入力を全面禁止する
B. セキュリティ・機密データの取扱い基準と人間による確認ルールを明確に示し、社員が安心して業務利用できる境界を整える
C. ガバナンス規程を作ると利用が減るため、ルールは一切定めず完全に自由利用とする
D. すべての出力を法務部長 1 人が毎回承認する体制にする

解答

B。全面禁止や無制限放任ではなく、「何を入力してよく、どこを人が確認するか」の明確な基準を設けることが、安全性と積極的な業務活用を両立する鍵になります。

1. AI の能力と限界

用語意味混同・注意ポイント
Next-Token Prediction文脈に続く最も確率の高い次のトークンを予測し続ける生成原理「意味を理解して論理検証している」のではなく確率予測であるため、真偽検証は別工程が必要
Context Window1 回の推論で参照できる入力・出力トークンの総容量上限に収まっていても、長大になるほど途中の指示が薄れる（Contextual Drift）
Hallucination事実や根拠がない内容を、もっともらしく出力する現象モデルの悪意ではなく確率生成の性質。根拠資料の提示と不明時の回答保留で抑える
Contextual Drift / Context Rot会話や入力が長くなるにつれ、初期指示や制約への注意が落ちて品質が下がる現象履歴を無制限に積むのではなく、整理・要約・セッション分割で防ぐ
Parametric Memory事前学習を通じてモデルの重みに蓄えられた知識社内ルールや最新情報は含まれないため、検索やコンテキスト付与が必要
Non-deterministic同じ入力でも毎回まったく同じ出力になるとは限らない性質再現性・厳密性が必須な計算や状態遷移は決定論的コードへ任せる

2. AI Fluency と 4D Framework

用語意味混同・注意ポイント
AI FluencyAI と有効・効率的・倫理的・安全に協働する実践的能力派手なプロンプト集を覚えることではなく、人間が主導権を握る設計・運用力
4D FrameworkDelegation / Description / Discernment / Diligence の 4 要素1 つでも欠けると「丸投げ」「手戻り」「品質劣化」「事故」につながる
Delegation（委任）何を AI に任せ、何を人間が担うかを決める判断実装の下書きは委任できるが、要件やセキュリティの最終判断は委任しない
Description（記述）求める内容・進め方・振る舞いを明確に言語化することProduct / Process / Performance の 3 視点を揃えると手戻りが減る
Discernment（識別）AI の出力の正しさ・品質・前提の妥当性を批判的に評価することテストが通っただけで中身を読まないのは Discernment 不足
Diligence（責任）安全性・プライバシー・ライセンス・説明責任を含めて出荷を担保すること「AI が書いたから分からない」はプロとして通用しない

4. モデル選定

用語意味混同・注意ポイント
Claude Opus最高難度の推論・長時間の自律コーディング向けフラッグシップ全タスクに使うとコストと遅延が過大になるため、高難度タスクに絞る
Claude Sonnet高い知能と高速な応答を両立するバランス型主力モデル多くの企業アプリ・開発支援における標準の起点
Claude Haiku最速・最安価な軽量モデル大量分類・抽出・ルーティング向き。複雑な多段階推論には不向き
Effort Parameter同一モデル内で推論に使う計算量（思考の深さ）を調整する設定上位モデルへ即座に変える前に、Effort 調整で品質と速度の折り合いを探れる
Efficiency-First軽量モデルから始め、不足分だけ上位モデルへ上げる進め方大量処理や厳しいコスト・遅延制約が明確な案件に向く
Capability-First高性能モデルでまず成立性を証明し、後から最適化する進め方難易度が高く、まず価値実証（PoC）を成立させたい案件に向く

総合確認問題（シナリオ形式）

総合問 1（能力と限界 ＋ 4D Framework）

FDE として顧客企業の開発チームを支援しています。顧客のエンジニアが「Claude に既存システムの複雑な決済ロジックのリファクタリングを依頼し、生成されたコードの単体テストも AI に書かせてすべてパスしたので、コードレビューを省略して本番リリースしたい」と提案してきました。FDE として指摘すべき最も重要な懸念はどれですか。

A. AI が書いたコードは単体テストが通るなら論理的に 100% 正しいため、レビュー省略で問題ない
B. テスト自体も AI が生成しているため前提の抜け漏れやエッジケースの欠落が起きる可能性があり、Discernment（出力の批判的評価）と Diligence（セキュリティ・出荷責任）の観点から人間による検証が不可欠である
C. リファクタリングは Next-Token Prediction の仕組み上、絶対に成功しないため手作業に戻すべきである
D. 単体テストの代わりに、より大型のモデルに「問題ないですか」と質問して Yes ならリリースしてよい

解答

B。実装やテストの下書き生成は Delegation できますが、決済のような重要領域で人間の検証（Discernment）と責任担保（Diligence）を省略するのは危険です。

総合問 2（プラットフォーム基盤 ＋ モデル選定）

ある大手企業で、社内の問い合わせ一次振り分け（1 日 20 万件、500ms 以内で 6 カテゴリに分類）と、複雑な法務契約書のリスク条項分析（1 日 50 件、見落とし厳禁）の 2 つのユースケースを、既存の GCP セキュリティ統制下で稼働させたいという要件があります。基盤とモデルの組み合わせとして最も適切なものはどれですか。

A. Anthropic API（個人アカウント）上で、両方のユースケースを Claude Opus で処理する
B. Google Cloud Vertex AI 上で、一次振り分けには Claude Haiku、契約書リスク分析には Claude Opus（または上位モデル）を割り当てる
C. Google Cloud Vertex AI 上で、一次振り分けには Claude Opus、契約書リスク分析には Claude Haiku を割り当てる
D. 2 つのユースケースを 1 つの長い会話セッションに混ぜて処理する

解答

B。GCP のセキュリティ統制要件には Google Cloud Vertex AI が適合します。また、大量・低遅延の分類には Haiku、高難度で見落とし厳禁の分析には Opus を選ぶのがモデル選定の原則に合致しています。

総合問 3（Description ＋ モデル挙動の診断）

顧客向けアプリで Claude に JSON 形式で顧客データを出力させようとしていますが、ときどき前置き文が混ざったり項目名が揺れたりして後続プログラムがエラーになります。原因と対策として最も適切なものはどれですか。

A. LLM は非決定的な性質を持つため、自然言語のお願いだけで形式を 100% 保証しようとせず、Tool Use や構造化出力のスキーマ定義を用い、アプリケーション側でも検証を行う
B. 出力が揺れるのはモデルが壊れているため、毎回異なるランダムなプロンプトを送る
C. 顧客データを画像に変換して Vision で出力させる
D. 会話履歴を 100 往復以上溜めてから JSON を出力させる

解答

A。LLM は非決定的であるため、自然言語の指示だけに頼らず構造化出力や Tool Use のスキーマ機能で形式を制御し、さらにアプリ層でバリデーションするのが安全な設計です。

総合問 4（Delivery Methodology ＋ Driving Enterprise Adoption）

ある製造業の顧客で、FDE として新規 AI パイロットを立ち上げ、さらにその後の全社展開まで見据えた提案を求められています。成功確率を最も高める進め方はどれですか。

A. 全社 8 部門の業務を最初から一括で自動化し、評価指標は導入後のアンケートのみで測る
