第1章 エージェントアーキテクチャとオーケストレーション

💡 ヒント

この章のたとえ：モデルは「指示を出す監督」、ハーネスは「実際に動くスタッフ」

監督（モデル）は「この資料を取ってきて」と頼むだけで、自分では動きません。スタッフ（ハーネス＝あなたのプログラム）が実際に取りに行き、結果を監督の机に置きます。監督は机の上にあるものだけを見て、次の指示を出します。机に置き忘れた資料は、監督にとって「無かったこと」になります。

この章のゴール

  • ツールを何度も使う仕事を、ループとして正しく回し、正しく止められる。
  • 複数のエージェントに仕事を分けるとき、「誰が全体を見るか」「何を明示的に渡すか」を決められる。
  • 外れると事故になる手順を、プロンプトではなくプログラム（ゲートとフック）で止められる。
  • 昨日の会話を「再開する」「新しく始める」「枝分かれさせる」のどれにするか選べる。

要点3つ

  1. モデルはツールを実行しない。 実行して結果を会話に戻すのはハーネス。ループを止める合図は stop_reason が end_turn になったときだけ。
  2. サブエージェントは親の会話を見ない。 必要な情報はコーディネーターがプロンプトに書いて渡す。通信は必ずコーディネーター経由。
  3. 事故になる順序は「お願い」ではなく「検査」で守る。 プロンプトは従う確率を上げるだけ。返金前の本人確認などはゲートとフックで止める。

30秒で全体像

flowchart LR
  U[利用者] --> C[コーディネーター<br>全体を見る親]
  C -->|Agentツールで委任| S1[サブエージェント<br>検索]
  C -->|Agentツールで委任| S2[サブエージェント<br>文書分析]
  S1 -->|結果| C
  S2 -->|結果| C
  C --> H[ハーネス<br>ツール実行・ゲート・フック]
  H -->|ツール結果| C

モデルは「このツールを呼んでほしい」と宣言し、ハーネスが実行して結果を会話に戻します。この往復がエージェントループです。仕事を分けるときは、コーディネーターがハブになり、子に渡す情報を明示します。返金のように順序を外すと事故になる箇所は、ゲートとフックで止めます。仕事の分け方は「やることが最初から見えているか」で選び、会話を続けるかどうかは「履歴の中身が今も正しいか」で選びます。

本編

1-1 ループは、モデルとハーネスのキャッチボール

モデルの1回の呼び出しは、「それまでの会話を読んで、次のメッセージを1つ返す」だけです。ファイルを開いたり、返金APIを呼んだりはしません。モデルが返すのは「このツールを、この引数で呼んでほしい」という宣言です。実際に実行するのはハーネスです。

返答には停止理由（stop_reason）が付きます。

  • tool_use なら：宣言されたツールを実行し、結果を会話に足し、もう一度モデルを呼びます。
  • end_turn なら：モデルは利用者への返答を終えています。ループを終えます。
flowchart TD
  A[会話を添えてモデルを呼ぶ] --> B{stop_reason は?}
  B -->|tool_use| C[ハーネスがツールを実行]
  C --> D[結果を会話履歴に追加]
  D --> A
  B -->|end_turn| E[利用者へ最終回答]

例：返品の依頼を4往復で処理する

利用者「注文 A-19 の壊れたヘッドホンを返金して」

回stop_reasonモデルの宣言ハーネスが履歴に足す結果
1tool_use顧客確認ツールを呼んで顧客は確認済み、ID は C-42
2tool_use注文参照ツールを呼んでヘッドホン、配送済み、金額 8000
3tool_use返金ツールを呼んで返金成功
4end_turn「返金しました」と利用者に回答（ループ終了）

もし1回目の結果を履歴に戻し忘れると、2回目のモデルは利用者の最初の文しか見えません。顧客IDを知らないので、同じ確認をもう一度要求するか、IDなしで先へ進もうとします。

❗ 重要

モデルに隠れたメモリはありません。次の判断材料は、会話履歴（トランスクリプト）に入っているものだけです。

1-2 止める合図は stop_reason だけ。文章からは読まない

「止める合図」を間違えると、仕事の途中で止まったり、終わったのに回り続けたりします。

止め方なぜダメか
文章が付いていたら終わりモデルはツールの前に「確認します」と書くことがある。文章があっても、仕事は終わっていない
文章が空なら終わりツール直前のつなぎが空に近いことがある。逆に、最終回答が短くても終わっていることがある
「完了しました」という語を拾うモデルは途中でもその語を書く。語を拾って止めると、返金の直前で止まる
回数の上限に達したら終わり上限は暴走を止めるヒューズであって、完了の定義ではない
max_tokens で切れたら終わり切断は完了ではない。切れたツール呼び出しのJSONを実行すると、壊れた引数で動く
💡 ヒント

一言まとめ：続けるのは tool_use、止めるのは end_turn。それ以外はすべて「異常」として扱う。

異常のときの対応

  • 回数の上限で止めたとき：利用者に「完了」と返してはいけません。「どこまで実行し、何が未実行か」を返します。返金だけ未実行なのに「対応しました」と書くのが典型的な事故です。
  • max_tokens で切れたとき：切れたJSONを補って実行してはいけません。金額の桁が欠けたまま返金が通るかもしれません。出力の上限を増やして同じ履歴からやり直すか、失敗として返します。

「止まらない」「同じことを繰り返す」ときの切り分け

同じツールが同じ引数で3回続くなら、原因はたいてい次のどちらかです。

  1. 結果が履歴に戻っていない（ハーネスの結び付け漏れ）→ ハーネスを直す。
  2. 結果が「失敗」の一言だけで、モデルが再試行をやめる根拠を持てない → ツールの戻り値を直す（第2章）。

プロンプトに「繰り返すな」と書いても、結果が見えていなければ、モデルの次の手は同じ要求です。

1-3 次のツールを選ぶのは、モデルか決定木か

  • モデル主導：モデルがツールの説明と会話を見て、次のツールを選びます。「返品の方針だけ教えて」なら、顧客確認も返金も呼びません。
  • 決定木：あらかじめ書いた分岐どおりにツールを呼びます。書き漏れた枝では、間違ったツールが呼ばれます。

普段の分岐はモデルに選ばせます。決定木が勝つのは「順序そのものが安全の条件」のときだけで、それは 1-9 のゲートで扱います。

⚠️ 注意

よくある失敗：「必ず顧客確認→注文参照→返金の順で呼べ」とプロンプトに固定する。モデルはだいたい従いますが、従わない回が残ります。

  • 目的が事故防止なら → プロンプトではなくゲートにする。
  • 目的が効率なら → モデルに選ばせたほうが、不要な呼び出しが減る。

1-4 コーディネーターがハブになる理由

サブエージェントは別の会話です。親の履歴はコピーされず、呼び出しをまたいでメモリも共有しません。検索役に「さっきの文書の続き」と頼んでも、「さっきの文書」はその会話にありません。

そこで、通信はすべてコーディネーター経由にします（ハブ・アンド・スポーク型）。

flowchart LR
  subgraph H["ハブ・アンド・スポーク型"]
    C[コーディネーター] <--> S[検索]
    C <--> D[文書分析]
    C <--> Y[統合]
  end

子どうしを直接つなぐと、経路が掛け算で増え、エラーの形がばらばらになり、ログを1か所で追えなくなります。利用者の目的と全員の結果を同時に見られるのは、コーディネーターだけです。

コーディネーターの4つの仕事

  1. 目的をサブタスクに分ける
  2. 誰を呼ぶか選ぶ（毎回全員を通す必要はない。「この用語の定義は？」で全文検索から始めると、待ち時間と費用が増えるだけ）
  3. 結果を集める
  4. 穴があれば、範囲を絞って呼び直す

範囲の割り方は「重ねすぎない」ことです。テーマで分けるか、情報源の種類で分けます。同じ記事を2人に読ませると、統合役は重複を消す作業に時間を使います。

1-5 全員が成功しても、全体が欠けることがある

「AIが創作産業に与える影響」を調べるのに、コーディネーターが視覚表現の3テーマだけを割り当てたとします。検索も、文書分析も、統合も、割り当てられた範囲ではすべて成功しました。それでも報告には、音楽も、執筆も、映像もありません。誰も失敗していません。割り当てられていなかっただけです。

間違った直し方正しい直し方
検索クエリを増やす（視覚の中で詳しくなるだけ）コーディネーターの分解を直す。最初にテーマ全体を列挙し、各サブタスクの担当範囲を明示する

穴が見えたあとの動きも、コーディネーターの仕事です。統合の結果に「音楽は未調査」とあれば、音楽だけを検索役に再委任し、戻ってきたら統合をやり直します。全員を最初からやり直すより安く済みます。一度きりのリレーにすると、最初の分解のミスがそのまま確定します。

💡 ヒント

一言まとめ：下流が全員成功しているのに偏っていたら、分解の幅を疑う。

1-6 サブエージェントの起動と、情報の渡し方

起動は Agent ツールで行う

サブエージェントを起動する道具が Agent ツールです（旧称 Task。古い資料やログでは Task と書かれています）。親が Agent ツールを使える状態でなければ、モデルは「検索役に頼みます」と文章で書くだけで、実際には誰も起動しません。Agent SDK の例では、承認なしで起動できるよう allowedTools に "Agent" を入れます。委任は意図ではなく、ツール要求です。

⚠️ 注意

allowedTools は「承認なしで実行してよいツール」の一覧で、使えるツールを絞る設定ではありません。絞るのは tools（使えるものを列挙）や disallowedTools（外すものを列挙）です。

渡す情報は、子のプロンプトに書く

検索結果や分析結果は、統合役のプロンプトに直接載せます。「前の役が知っている」は通用しません。会話が分かれているからです。

載せるときは、本文とメタデータを分けます。主張、抜粋、URL、文書名、ページ、公開日、などです。本文だけを貼ると、統合役の文章から出典が消えます（第5章の出典保持につながります）。

並列は「1回の返答で Agent ツールを複数呼ぶ」

sequenceDiagram
  participant C as コーディネーター
  participant S as 検索
  participant D as 文書分析
  participant Y as 統合
  C->>S: Agent ツール（1回目の返答）
  C->>D: Agent ツール（同じ返答）
  S-->>C: 結果
  D-->>C: 結果
  C->>Y: Agent ツール（次の返答。両方の結果をプロンプトに載せる）
  Y-->>C: 統合結果
  • 1回の返答に Agent ツールの呼び出しを複数出すと、ハーネスはそれらを同時に実行し、全部そろってから次のモデル呼び出しをします。
  • 返答を分けて1人ずつ起動すると、待ち時間が直列に積み上がります。
  • 依存があるものだけ直列にします。 統合は検索の結果が必要なので、同じ返答に並べても、統合は空の材料を受け取ります。

AgentDefinition の説明は具体的に

具体的に書くと、論文の依頼は文書分析役に回るようになります。

1-7 委任は「手順」ではなく「目標と品質基準」で書く

悪い委任（手順書）良い委任（目標と基準）
指示「検索ツールを使え。クエリは『創作、AI、アート』。5件取ったら文書役へ渡せ」「問いは創作産業の雇用への影響。視覚・音楽・執筆・映像を別々に検索し、主張・抜粋・URL・公開日を分けて返せ。一次情報に近い出典のない数字は空欄でよい。見つからなければ、見つからなかったと書け」
起きることテーマが視覚に偏る。件数で打ち切られる。3番目のサイトが落ちると止まる子がクエリを自分で変えられる。空欄は失敗ではなく「穴の報告」になる

親と子で、書く内容は違います。

  • コーディネーターのプロンプト：利用者の目的、品質の基準、再委任してよい条件（例：「視覚が4件で音楽が0件なら、音楽だけクエリを変えてもう一度」）。クエリの文字列そのものは書きません。
  • 子のプロンプト：返す構造と、空欄でよい条件。
⚠️ 注意

親が子の結論を自分の言葉で要約してから次の子へ渡すと、「8000円」が「数千円」になり、URLが落ちます。渡すのは、子が返した構造のままです。どうしても要約するときも、数字と出典の行は残します。

手順が「安全上の順序」なら、それは子のプロンプトではなくゲートに置きます（1-9）。

1-8 ツール呼び出しにはIDがあり、結果は必ずIDで対応させる

1回の返答にツール要求が2つあるとき、それぞれに識別子（ID）が付きます。ハーネスは結果を、そのIDに結び付けて返します。

例：並列検索の片方だけが失敗した

視覚の検索（call_v）は抜粋を返し、音楽の検索（call_m）はタイムアウトしました。

やり方何が起きるか
✅ IDで対応させ、成功は結果を、失敗は失敗の構造（種類・試したクエリ・部分結果）を返すモデルは視覚の統合を進め、音楽だけ再委任できる
❌ 返ってきた順の配列で対応させる音楽の失敗が先に届くと、視覚の欄に失敗が入る。統合は「視覚の記事が無かった」と書く
❌ 両方捨ててやり直すタイムアウトのたびに費用が倍になる
❌ 失敗を「空の成功」にする音楽は「記事が無かった」という結論になり、失敗が消える

もう1つの誤りは、モデルが頼んでいないツールを、ハーネスが気を利かせて先に実行し、結果を履歴に足すことです。モデルは「自分が頼んだ結果が並んでいる」前提で次を判断するので、どの前提で話しているかが追えなくなります。先に済ませたい条件があるなら、ゲートとして「このツールはまだ実行できない」と返します。

1-9 外れてはいけない順序は、確率では守れない（ゲート）

モデルは指示に高い割合で従います。それでも、従わない回がゼロにはなりません。返金前の本人確認を太字で強調しても、確認を飛ばす回が残ります。その1回で、別人の口座が動きます。

ゲートは、ハーネスが持つ状態の検査です。

flowchart TD
  R[モデルが返金ツールを要求] --> G{verified_customer_id が<br>記録されているか}
  G -->|ない| N[APIを呼ばず、<br>「確認が済んでいないので実行しなかった」<br>とツール結果で返す]

  • 顧客確認ツールが検証済みIDを返したときだけ、ハーネスが verified_customer_id を記録します。
  • 返金ツールの実行関数の先頭で、その値を確認します。空なら、APIを呼ばずにツール結果を返します。副作用は起きません。
  • テストの方法：プロンプトから確認の指示を全部消しても、この分岐が残ること。それがゲートです。

事故の値段が高い順序だけをゲートにします。トーンや説明の詳しさのように「だいたい従えばよい」ものはプロンプトのままにします。何でもゲートにすると、「返金の条件は？」という質問まで止まります。検査は返金ツールの実行関数にだけ掛けます。

確認のゲートと金額の検査は、別の条件です。一つにまとめないでください。

1-11 通し例：1件の返金を、ループ・ゲート・フックで処理する

依頼「注文 A-19 を返金して」。方針は「写真のない破損申告は返金しない」「5万円を超えたら人へ」。

ターン何が起きるか落とし穴
1tool_use：顧客確認。ハーネスが検証済みID C-42 を状態に記録し、結果を履歴に足す状態への記録を忘れると、後のゲートが常に空を見て、正しい顧客でも返金できない
2tool_use：注文参照。PostToolUse がUnix時刻と数値コードを「日付」「配送済み」に変換。金額 8000、写真なし変換しないと、数値コードを「未配送」と読む回があり、判断が変わる
3tool_use：返金。実行前の検査で、IDあり・5万円以下を確認。しかし方針の検査が「写真なし」を見て、APIは呼ばない。結果は「写真が無いので実行しなかった」
4end_turn：利用者に写真を依頼する文最終文だけを成功の印にすると、未実行の返金を「完了」と報告してしまう

写真があり金額が8000円なら、3ターン目でAPIが実行され、4ターン目の end_turn が本当の完了です。

1-12 人への引き渡し（ハンドオフ）は「写し」ではなく「判断材料」

引き渡す相手は、エージェントの会話ログを開けません。必要なのは全文の写しではなく、次の行動を選ぶための材料です。

悪いハンドオフ（会話の貼り付け）良いハンドオフ（構造化）
「お客様はご立腹で、注文の話のあと配送の話になり、金額はどこかで8000と言っていた」顧客：C-42 ／ 注文：A-19 ヘッドホン、配送済み ／ 希望：全額返金 ／ エージェントの判断：破損写真が無く方針外 ／ 推奨：写真を依頼、または例外承認

最低限必要なのは「顧客ID」「何が起きたか」「金額」「推奨する次の行動」の4点です。欠けると、人は最初から聞き直します。

1通の問い合わせに用件が複数あるときは、用件ごとに分け、共通の事実（同じ顧客IDなど）を共有しながら調べ、最後に1つの返答にまとめます。

1-13 仕事の分け方は「やることが最初から見えているか」で選ぶ

プロンプトチェーン動的な分解
向いている仕事やることが事前に決まっている（例：コードレビュー）次の問いが途中で生まれる（例：古いコードにテストを足す、調査）
進め方ファイルごとの局所チェック → ファイル横断のデータの流れ、と段階を分けるまず全体構造をつかみ、影響の大きい箇所を見つけ、依存が見つかるたびに優先度を更新する
逆に使うと調査に使うと、名前を付けなかった枝が消えるレビューに使うと、チェックリストを捨てて探索に流れる

なぜレビューを分けるのか：14ファイルを一度に渡すと、注意が一部のファイルに偏り、同じ問題を片方では指摘し、もう片方では見逃します。モデルが怠けているのではなく、一度に配れる注意に限りがあるからです。段階を分ければ、各段の入力が小さくなり、深さがそろいます。

分けないほうが速い仕事もあります。 サブエージェントには起動・プロンプトの複製・待ち時間のコストがかかります。1回の検索で済む調査にサブエージェントを使っても、待ちが増えるだけです。

分ける基準は次の3つです。どれにも当てはまらなければ、親が直接ツールを呼びます。

  1. 入力が長く、親の会話に残すと後の作業の予算が足りなくなる
  2. 必要なツールの組み合わせが違い、親に全部持たせると選択が揺れる
  3. 失敗しても目的の一部だけが欠ける、と切り出せる
⚠️ 注意

副作用の順序は、委任で分けない。 本人確認と返金を別の子に任せると、確認済みIDは子の会話の中に閉じこもり、親のゲートが見る状態に入りません。確認も返金も、同じハーネスの状態と検査の上に置きます。委任してよいのは、検索のように失敗しても口座が動かない仕事です。

また、「子に親の全履歴を渡せば楽」という案は、分離した意味を消します。子は関係のない途中経過まで読み、コンテキストを無駄に使います。

1-14 会話を続けるか：再開・新規・フォークの三択

判断の軸は「履歴の中のツール結果が、今も正しいか」です。履歴にあるツール結果は、実行した瞬間のファイルやAPIの「写真」にすぎません。

flowchart TD
  Q{履歴のツール結果は<br>今も正しい?} -->|ほぼ正しい| R[--resume で再開]
  R --> R2[変わったファイルがあれば<br>名指しして読み直させる]
  Q -->|大半が古い| N[新しい会話を始める]
  N --> N2[残したい結論だけを構造化して注入<br>古いツール結果は渡さない]
  Q2{同じ地点から<br>別案を比べたい?} -->|はい| F[fork_session で枝分かれ]

例：月曜日に認証モジュールを分析し、セッション名を auth-review にした

  • 水曜日、session.ts の有効期限だけが変わった → 再開して「session.ts の有効期限の比較が14日から1日に変わった。そのファイルだけ読み直し、月曜日の他の結論を維持してよいか答えて」と伝えます。名指しを忘れると、月曜日の古いコードを今のコードとして話します。
  • ファイルが大きく変わった、または当時のAPIがもう無い → 新しい会話を始め、決めた境界・未解決の問い・読むべきファイル名だけを注入します。古い数字を入れるなら「当時の観測では在庫は10」のようにラベルを付けます。ラベルがないと、新しい会話でも「現在の在庫」として扱われます。
  • 認証をミドルウェアに移す案と、各ハンドラに残す案を比べたい → 月曜日の分析の直後で fork_session します。1つの会話で両方を試すと、先の案の差分が後の案の評価に混ざります。枝に分ければ、共通の分析だけを共有し、その後の結果は混ざりません。

「古さの問題」と「比較の問題」は別の問題です。再開とフォークを同時に使う必要はありません。

1-15 API の基本：会話はアプリが毎回すべて送る

ここからは、公式ドキュメントの仕様として押さえておきたい点をまとめます。問題集ではこの細部がよく問われます。

Messages API はステートレス（状態を持たない）

API の側には、前のリクエストの内容は残りません。会話を続けるには、アプリケーションがそれまでの利用者とアシスタントのメッセージをすべてリクエストに入れて送ります。Claude が参照できるのは、そのリクエストに入っているメッセージとシステムプロンプトだけです。

よくある誤解実際
プロンプトキャッシュを使えば、前の会話を覚えていてくれるキャッシュは繰り返し送る先頭部分の処理を再利用して、時間と費用を減らす仕組み。送る内容は変わらない
max_tokens を大きくすれば、長い履歴を参照できるmax_tokens は出力の長さの上限。履歴の参照とは関係ない

ツール結果の戻し方

ツールの実行結果は、role が user のメッセージに tool_result ブロックとして入れて返します。失敗したときは is_error: true を付けます（MCP では isError。第2章）。1回の応答に tool_use ブロックが複数あれば、ハーネスはそれらを実行し、結果を次のリクエストでまとめて返します。

ループの終わり方は2つある

ループは、モデルが応答を終えた（end_turn）ときだけでなく、max_turns のようなターン数の上限に達したときにも終わります。上限で終わると、タスクは途中のままです。

💡 ヒント

必ず満たすべき業務要件（たとえば「最後に必ず記録を保存する」）は、ループの外側、つまりループを呼び出すアプリケーションのコードで確認します。ループの終わり方がどちらでも、そのコードは必ず実行されるからです。

マルチエージェントはトークンを多く使う

マルチエージェントの構成は、単一のエージェントよりはるかに多くのトークンを消費します。独立したコンテキストで調べる価値がある大きな仕事や、並列にできる仕事に使い、コーディネーターがすでに持っている情報で済む処理はコーディネーター自身が行います。

Anthropic のマルチエージェントリサーチシステムから学べること

  • 労力の調整：リードエージェントが問い合わせの複雑さを判断し、単純な事実確認なら1つのエージェントと少ないツール呼び出しで済ませる、という規則をプロンプトに入れている。
  • 並列化：リードがサブエージェントを並列に起動し、複雑な調査の時間を最大90％短縮した。
  • 依頼の書き方：目的・出力の形・使うツールと情報源の指針・範囲の明確な境界を含める。「半導体不足を調べて」のような短く曖昧な依頼では、作業の重複や抜けが起きた。
  • 受け渡しの損失を減らす：子が成果を外部に保存し、コーディネーターには軽い参照を返す。出典の特定は専用のエージェントが担う。
  • 再開：エラーが起きても最初からやり直さず、起きた地点から再開できるようにする。計画はメモリに保存して、コンテキストが切り詰められても失われないようにする。

1-17 ワークフローの型

Anthropic の「効果的なエージェントの作り方」で整理されている型を、使いどころで覚えます。

型動き向いている仕事
Prompt Chaining決まった手順に分け、各呼び出しが前の出力を処理する決まったサブタスクにきれいに分けられる仕事
Orchestrator-Workers中心の LLM が仕事をその場で分けてワーカーに任せ、結果をまとめる必要なサブタスクを事前に予測できない複雑な仕事
Evaluator-Optimizer1つが出力を作り、別の1つが評価と指摘を返す流れを繰り返す出力の質を上げたい仕事（仕事を観点で分ける仕組みではない）
Autonomous Agentツール結果を見ながら、次の行動をモデルが決め続ける手順が決められない、終わりが見えない仕事

一方向の流れの弱点：収集 → 評価 → 執筆を一度ずつ流すだけの構成では、後の段で見つかった不足を前の段に戻せません。資料を読んで初めて足りないものが分かる調査では、コーディネーターが途中の結果を見て追加の依頼を出せるループにします。不足を最も正確に知っているのは資料を読んだ子なので、子に「何が足りないか」を具体的な論点として返させます。

権限ルールdeny → ask → allow の順に評価される。Edit(./vendor/**) のように書けば特定のパスの編集を禁止できる。PreToolUse フックが許可を返しても、一致する deny ルールは拒否する
ツールの中での判定ツールの実装の中で検査すれば、どの経路から呼ばれても同じ検査が必ず行われる。いちばん確実

検査の条件は、防ぎたい誤りに合わせて選ぶ

予約の取り消しで「他人の予約を取り消させない」のが目的なら、番号の形式チェックや、番号が実在するかのチェックでは足りません。実在する別の顧客の番号は通ってしまうからです。「その予約が、認証済みの顧客のものか」を照合します。止めたときは is_error を付けて何が問題かを具体的に返すと、モデルは予約を調べ直すなどして立て直せます。

人による確認（human-in-the-loop）は、中身を見せてこそ効く

送信や支払いのような取り消しにくい操作の前に、人の承認をはさむことがあります。確認の画面に実行される内容が表示されていないと、承認は「いつも押すボタン」になり、ほぼすべてが通ります。入力の手間や承認者を増やしても判断の材料は増えません。MCP のクライアントも、機密性のある操作ではサーバーを呼ぶ前にツールの入力を利用者に見せます。

C。下流は割り当てられた仕事を完了しています。割り当てられていない領域は、下流の精度をいくら上げても出てきません。

問3

A. システムプロンプトに順序を太字で書く
B. 正しい順序の会話例を足す
C. 返金の実行直前に、確認済みIDが状態にあるかを検査し、なければAPIを呼ばない

解答

C。AとBは従う割合を上げますが、ゼロにはしません。Dの確信度は校正されておらず、難しい案件でも高く出ることがあります。

問4

B. 実行前に呼び出しを拒否するフック

A。Bの拒否フックは「呼ばせない」ための仕組みで、成功した結果の形はそろえません。

問5

A. 古いツール結果が残った会話を、変更を伝えずに再開する
B. 残すべき結論だけを新しい会話に注入し、古いツール結果は渡さない
C. 自然文の「完了」でループを止める
D. すべての子に親の全履歴を自動で引き継がせる

解答

B。写しが古いまま再開すると、過去のファイルを現在のものとして話します。履歴がまだ正しく、変更が小さいときだけ、変更箇所を名指しして再開します。

問6

コーディネーターが分析役のサブエージェントに売上の集計を任せました。子は途中でデータベースを何度も照会しましたが、親が受け取った報告には集計の結論の文章しかなく、後段の担当が必要とする月ごとの数値がありません。最初に直すべきところはどれですか。

A. 子をフォークで起動し、親の会話を子にコピーする
B. 子への依頼文（または AgentDefinition の prompt）で、最終報告に月ごとの数値を項目として含めるよう指定する
C. SubagentStop フックで、子のツール結果を次のサブエージェントに直接渡す
D. 親の allowedTools にデータベースのツールを追加する

解答

B。親に戻るのは子の最終メッセージだけで、途中のツール結果は子の中にとどまります。必要な数値は最終報告に書かせます。A のフォークは親の文脈を子に持たせる仕組みで、逆向きの受け渡しではありません。C の SubagentStop は終了時の処理を差し込むもので、受け渡しの経路ではありません。D は自動承認の設定で、報告の中身は変わりません。

問7

エージェントに使わせたくない書き込みツールがあります。プロンプトにも書いていないのに、ときどき呼ばれます。確実にそのツールを候補から外す設定はどれですか。

A. allowedTools から書き込みツールを外す
B. disallowedTools に書き込みツールの名前を書く
C. システムプロンプトに「書き込みツールは使わない」と太字で書く
D. max_turns を小さくする

解答

B。disallowedTools に書いたツールは定義ごとリクエストから外れ、Claude は見ることも呼ぶこともできません。A の allowedTools は承認なしで実行させる一覧で、外しても「使えない」ことにはなりません。C は従う割合を上げるだけで、D はツールの選択と関係ありません。

問8

テスト方針の案Aと案Bを、同じ分析の地点から比べたいと考え、セッションをフォークしました。ところが案Aの枝で書き換えたファイルが、案Bの枝からも変更済みに見えます。何が起きていますか。

A. フォークは会話の履歴だけを分け、ファイルシステムは分けないため
B. フォークのときに resume を指定しなかったため

A。フォークが分岐させるのは会話の履歴で、ファイルは共通のままです。ファイルも分けたいなら git worktree などで作業ツリーを分けます（ただし worktree は会話の履歴を引き継ぎません）。

第2章 ツール設計とMCP統合

💡 ヒント

この章のたとえ：ツールは「道具箱の道具」、説明文は「道具に貼ったラベル」

モデルは道具の形（名前）ではなく、ラベル（説明文）を読んで道具を選びます。ラベルが「いろいろ使える」だけの道具が2本あれば、取り違えます。道具が壊れたときに「壊れた」としか書かれていなければ、直すべきか、待つべきか、人を呼ぶべきかも分かりません。

この章のゴール

  • モデルがツールを正しく選べる説明文を書ける。
  • 失敗を、次の行動（再試行・修正・説明・人へ）が決まる形で返せる。
  • ツールが多すぎる状態と、少なすぎて往復が増える状態を見分けられる。
  • tool_choice の3つの設定を使い分けられる。
  • MCPの設定を「チーム共有」と「個人の実験」で置き分け、リソースとツールを混ぜない。
  • 組み込みツール（Grep・Glob・Edit・Read・Write・Bash）を取り違えない。

要点3つ

  1. 選択の決め手は説明文。 名前を変えるだけでは効果が薄い。目的・入力の形・使う例・使わない場合を書く。
  2. 失敗は「種類」と「再試行してよいか」を付けて返す。 ゼロ件の検索は失敗ではなく「成功の空」。タイムアウトの空と区別する。
  3. 持たせるツールは役割の分だけ。 よく使う狭い確認だけを例外として持たせる。

30秒で全体像

flowchart TD
  D["① 選ばせる<br>説明文に 目的・入力・例・使わない場合"] --> E["② 失敗を返す<br>isError ＋ 種類 ＋ 再試行可否 ＋ 利用者向けの文"]
  E --> N["③ 絞る<br>役割に必要な数だけ・tool_choice で自由度を調整"]
  N --> M["④ つなぐ<br>MCP: 共有は .mcp.json・カタログはリソース、操作はツール"]

モデルはツール名の雰囲気ではなく、説明文を読んで選びます。失敗は「失敗しました」だけでは次の手が決まりません。種類と再試行の可否を返します。ツールを増やすほど選択は不安定になります。tool_choice は、文章で答えてよいか、ツールを必須にするか、名前まで固定するかをハーネスが決める設定です。チームで使うMCPはプロジェクトの .mcp.json に置き、秘密は環境変数で渡します。中身の検索は Grep、パスの検索は Glob、一意な部分修正は Edit です。

本編

2-1 モデルが見ているのは「名前・説明・入力スキーマ」の一覧

ツールは、会話とは別に一覧でモデルに渡されます。各ツールは「名前」「説明」「入力スキーマ」の3つです。モデルはこの一覧とこれまでの会話だけを見て、次にどのツールを、どの引数で呼ぶかを決めます。ハーネスが「たぶん注文のことだろう」と補ってくれることはありません。

だから、選択の本文は説明文です。

悪い例起きること
get_customer：「情報を取得する」<br>lookup_order：「詳細を取得する」モデルは2つを同じ道具として扱う。「A-19」のような注文番号を get_customer に渡してしまう

2-2 説明に書く4つのこと

  1. 何のためのツールか（目的）
  2. 入力の形式（顧客IDか、注文番号か、電話番号は受けるか）
  3. どんな依頼で使うか（例）
  4. 似たツールとの境界（使わない場合）

例：説明を直す前と後

依頼「A-19 のヘッドホン、まだ届いていません」

lookup_order（注文参照）get_customer（顧客確認）
直す前情報を取得する情報を取得する
直した後目的：配送状態の参照。入力：A- で始まる注文番号。例：「届いたか」「返金の対象か」。使わない場合：氏名だけの依頼目的：本人確認。入力：顧客IDまたは電話番号。注文番号は受けない
結果→ 依頼は lookup_order に正しく行く

名前だけ変えても効果は薄い

analyze_content と analyze_document の説明がほぼ同じなら、名前を変えても揺れます。ウェブ抽出に限るなら、名前を extract_web_results にし、説明も「HTMLから本文とURLを抜き出す。PDFは受けない」に変えます。モデルは名前より説明を読むからです。

形式は「スキーマ」と「説明」の両方に書く

どちらか一方だけだと問題
スキーマだけ（注文番号は A-数字 のパターン）拒否されても、モデルは理由が分からず、同じ文字列を別の欄に入れ替えて試す
説明だけ実行時の検査がなく、表示名がそのままAPIまで届く
💡 ヒント

一言まとめ：形式はスキーマで守り、理由は説明で伝える。

1つのツールに何でもさせない

1つの analyze_document に要点抽出・要約・出典との照合を全部させると、呼ぶたびに返ってくる形が変わります。契約（入力と出力の約束）を分けます。

ツール返すもの
extract_data_points項目（欄）
summarize_content段落
verify_claim_against_source主張・抜粋・一致したか

呼ぶ側は、ツール名を見ればどの形が返ってくるか分かります。

2-3 説明を直しても選択が揺れるとき

① システムプロンプトのキーワードを疑う

システムプロンプトに「『分析』という言葉が出たら analyze_document を使え」のような行が残っていると、説明で引いた境界が負けます。モデルは説明と常時の指示の両方を見るからです。直す順序は「キーワードの行を消す → 説明の境界を残す → 効果を測り直す」です。

② 入力スキーマが両方とも自由文字列になっていないか

スキーマを分ければ（注文番号は A-数字、顧客IDは C-数字）、形が違う依頼はスキーマの段階で弾かれます。

後回しにすること

手段なぜ後回しか
具体例を10件足すトークンを使う。説明が短いままなら、新しい言い回しで同じ取り違えが起きる
発話を正規表現で振り分ける前処理「返して」が返金か返却か、のような文脈の差を捨ててしまう
2つのツールをすぐ1つに統合する入力の約束が曖昧なまま内部の分岐に隠れ、失敗の理由も混ざる。説明を直したうえで「本当に契約が1つだ」と分かってから統合する

2-4 失敗は、次の行動が分かれる形で返す

isError が立っていない結果を、モデルは成功として読みます。本文に「失敗」と書いてあっても、フラグがなければ成功の文として扱われることがあります。失敗はフラグと構造の両方で伝えます。

種類を分ける理由は、次の手が違うからです。

flowchart TD
  F[ツールの結果] --> Q{何が起きた?}
  Q -->|タイムアウト・503| T[一時的<br>再試行してよい]
  Q -->|入力の形が違う| V[検証<br>同じ引数で再試行しない<br>どの欄が違うか伝える]

  • ゼロ件を isError にすると → モデルはクエリを変えて延々と再試行します。

2-6 ツールの数：減らす、ただし例外は認める

多すぎると選択が揺れる

ツールが18個あるエージェントは、説明を読んでもなお、似た2つの間で迷います。4〜5個で足りる役割に18個渡すと、無関係な説明が毎回ノイズになります。統合役にウェブ検索を持たせると、統合の途中で探索を始め、返すべき構造を書かなくなります。

基本は「その役割のツールだけ」。例外は「よく使う、狭い確認」

統合の確認の8割が「この日付と固有名詞は出典と一致するか」だけなら、統合役に verify_fact を持たせます。

flowchart LR

検索ツール一式を統合役に渡してしまうと、例外が役割そのものになります。

できることを減らすと、選択が安定する

任意のURLを取りに行く汎用の fetch_url より、文書専用の load_document にして、許可したホスト以外は検証エラーにします。

「数を減らす」と「1つに潰す」は違う

18個を4〜5個に減らすのは、無関係な説明を候補から外すためです。一方、残った2つの説明が両方「文書を分析する」なら、先に契約（返す形）を分けます。契約が本当に1つだと分かってから統合します。

2-10 MCP のエラーは2種類ある

MCP のツールのエラー報告には、性質の違う2種類があります。

プロトコルエラー存在しないツールの呼び出し、CallToolRequest のスキーマを満たさない不正な要求、サーバー自体のエラーJSON-RPC のエラー届かないことがある
ツール実行エラーツールが動いたあとに分かる失敗。外部 API の失敗（503 も 404 も）、入力値の検証エラー、業務ロジックのエラーcontent に内容を書き、isError: true を付けたツール結果クライアントはモデルに渡すべき（SHOULD）とされている

ツールの中で API を呼んで失敗したなら、それはツール実行エラーです。ツール結果として返せば、モデルはその内容を読んで、入力を直す・再試行する・利用者に確認するといった対処を選べます。ツールが例外を投げるだけでは、何が起きたのかがモデルに届きません。

⚠️ 注意

進捗通知（progressToken が付いた要求への途中経過）や _meta（やり取りに追加情報を付けるための予約項目）は、モデルに渡す内容を入れる場所ではありません。

構造化したツール結果

ツール結果を、値ごとに名前の付いた欄を持つ形で返すと、モデルは必要な値を欄から直接取り出せます。文章で返すと、どの数字が何を表すかを読み取る必要があり、取り違えが起きます。MCP のツールは structuredContent で構造化した結果を返せ、outputSchema を定義すると型の情報も伝えられます。ただし、JSON で返してもモデルの処理が決定的になるわけではありません。効果は「値の取り出しが確実になる」ことです。

スキーマが守れること・守れないこと

enum は取れる値を列挙した候補に限り、strict: true は生成される引数をスキーマに厳密に従わせます。どちらもスキーマに書かれた制約を守らせるだけで、「この操作のときはこの引数が必須」のような条件までは守らせません。条件で必須の引数が変わるなら、操作ごとのツールに分けます。

判定はツール側で確定させる

ツールが生の確信度（0.62 など）だけを返すと、その解釈はモデルに任され、呼び出しごとに揺れます。ラベル付きのデータで決めたしきい値をツールのコードで適用し、ok や review のような状態の値と、どの欄がどの理由でそうなったかを返すと、判定が毎回同じになります。

成否が分からない操作

請求や通知の送信のように、2回実行すると2回分の結果が残る操作がタイムアウトしたときは、「失敗した」とも「再試行してよい」とも言えません。結果が不明であること自体を返し、再実行しないよう促します。

有効な空の結果は、成功の印と分けて返す

空の配列だけを返すと、「該当なし」なのか「取得できなかった」のかがモデルには分かりません。成功を示す値と結果の配列を分けて返すと、「検索は成功し、該当は0件」という意味が構造から読み取れます。条件で探して0件だったのは成功の結果で、ID を指定した照会で対象が存在しない場合とは区別します。

問6

A. JSON-RPC のプロトコルエラーとして返す
B. content に失敗の内容を書き、isError: true を付けたツール結果として返す

第3章 Claude Codeの設定とワークフロー

💡 ヒント

この章のたとえ：設定ファイルは「掲示物」

自分の机に貼ったメモ（ホームの設定）は、自分にしか見えません。職場の掲示板（リポジトリの設定）に貼れば全員に見えます。テスト担当の部屋にだけ貼りたい注意書きは、その部屋のドアに貼ります（パスの glob）。「誰に」「いつ」読ませたいかで、貼る場所が決まります。

この章のゴール

  • 指示・コマンド・スキル・パスごとの規約を、届けたい人に、届けたいときだけ届く場所に置ける。
  • 大きな変更は調査と設計を先に、小さく分かっている修正はすぐに、と進め方を選べる。
  • 文章だとぶれる変換を、入出力の例とテストで狭められる。
  • CI パイプラインで、入力待ちで止まらず、機械が読める指摘を、前回と重複させずに出せる。

要点3つ

  1. 置き場所は「誰に届くか」で決まる。 ホーム（~/.claude/）は自分だけ、リポジトリ（.claude/ やルート）は全員。散らばったファイル種別への規約は .claude/rules/ の paths。
  2. 大きく・案が複数・多数ファイルならプランモード。 変える場所が1つに特定できているなら直接実行。
  3. パイプラインは -p で非対話。 出力は JSON とスキーマで固定し、書いた会話とは別の実行でレビューする。

3-2 指示が同僚に届かないときは、層を疑う

「新しく入った人だけ規約を守らない」なら、指示がホーム（~/.claude/CLAUDE.md）に置かれている可能性が高いです。そのファイルは本人の機械にしかありません。

推測で決めず、/context を実行し、Memory files の一覧に、読み込まれるはずの CLAUDE.md が入っているかを確認します。 一覧になければ、その規約はモデルに届いていません。

📝 メモ

/memory は、メモリファイル（CLAUDE.md や CLAUDE.local.md など）の場所を一覧し、選んだファイルをエディタで開くコマンドです。実際に読み込まれたかの確認は /context で行います。（※なお、公式 Exam Guide v0.2 の Task Statement 3.1 では、読み込まれたメモリファイルの確認コマンドとして /memory が挙げられているため、試験問題では文脈に合わせて押さえておいてください。）

/context の様子原因対処
ホームのファイルだけで、プロジェクトのファイルがない起動したディレクトリがリポジトリのルートではなく、ルートの CLAUDE.md が探索範囲の外ルートで起動し直す
両方あり、指摘が人によって違うホーム側の文が勝っている共有したい文はプロジェクトへ移し、ホームからは消す
テスト編集中にテストのルールがなく、実装編集中にあるpaths の glob が逆glob を直す
個人の review だけが走るホームのスキル（または旧 commands）に同じ名前がある個人側を外す
💡 ヒント

チームで再現しない不具合は、まず個人の CLAUDE.md・CLAUDE.local.md・スキルを空にしてから再現を試します。

3-3 巨大な1枚の CLAUDE.md は分ける

1枚に全部を書くと、関係のない節まで毎ターンのコンテキストに入ります。分け方は2つです。

  1. @import：各パッケージの CLAUDE.md から、そのパッケージに必要な標準ファイルだけを取り込む。全員に全標準を読ませない。
  2. .claude/rules/ に話題別ファイル（テスト、API、デプロイ）を置く。常に必要なら条件なし、特定のファイル種別だけなら paths を付ける。

3-4 paths の glob は「編集したときだけ」規約を載せる

.claude/rules/ のファイルのフロントマターに paths を書きます。

glob読み込まれるとき
terraform/**/*terraform の下を編集するとき
**/*.test.tsx場所を問わず、テストファイルを編集するとき

一致しないファイルを編集しているターンでは、その規約のトークンを払いません。

ほかの方法がダメな理由

方法問題

規約をスキルに入れる自動ではなく、呼ばれるまで効かない

3-5 常時指示・コマンド・スキルは寿命が違う

仕組みいつ効くか向いているもの
CLAUDE.md / ルール常に（または paths 一致時に自動で）常に守ってほしい標準
スキル（SKILL.md。旧来の .claude/commands/ も同じ扱い）利用者が /名前 と打ったとき、または作業に合うと Claude が判断したとき定型作業の呼び出し、ときどきしか使わない長い手順
  • CLAUDE.md にコマンドの手順を書いても、スラッシュコマンドとしては登録されません。
  • 存在しない設定の配列にコマンド名を書く、という「第3の場所」はありません。
  • 個人の好みで共有スキルを書き換えると、チーム全員の手順が変わります。別名の変種を ~/.claude/skills/ に作ります。

3-6 スキルのフロントマター：何を隔離し、何を絞るか

  • フォークしないと、探索の長いログがそのまま本会話の履歴になります。そのあと実装を頼むと、モデルは貼られた中身の一部しか見ず、残りを忘れます。
  • フォークするなら、スキルの最後に「ファイル名と判断だけを返せ」と書きます。結論にファイル名がないと、本会話はその結論を使えません。

allowed-tools（スキル実行中だけツールを絞る）

  • 読み取りのスキルなら、Read・Grep・Glob だけにします。シェルが入っていると、調査のつもりでマイグレーションを実行できてしまいます。
  • 書き込みが必要な適用作業は別のスキルに分け、フォークしないで本会話で差分が見えるようにします。隔離と適用を1つのスキルにすると、差分がフォークの中に閉じこもり、利用者が差分を見ないまま終わります。

argument-hint（必要な引数を尋ねさせる）

ヒントがないと、引数なしで呼ばれたときにモデルが対象ファイルを推測して手順を始めてしまいます。

向いている仕事マイクロサービスへの分割、広範囲のライブラリ移行、方式が2つある統合スタックトレースが1行を指している、1つの関数に検証を足す

プランに書くもの：残す境界、動かすモジュール、触らないディレクトリ、最初の検証コマンド。コード断片を大量に貼ったものはプランではなく調査ログです。

承認してから移る：承認したプランのファイルを、次の直接実行の会話に残します。「だいたいこの方向で」と口頭で移ると、プランの制約が次のターンで落ちます。

長い調査は Explore に任せる：調査ログが長いあいだは Explore サブエージェントに渡し、本会話にはファイル名と理由だけ戻します。生の検索結果を本会話に積むと、設計を書くころにはコンテキストが探索で埋まっています。

例：途中で境界が動く

  1. 報告は「session.ts の比較が1日になっている」。スタックトレースが1つの関数を指しているので、直接実行で始めます。
  2. 読み進めると、比較がミドルウェアと各ハンドラの2か所にあり、有効期限の置き場所がサービス境界の問題だと分かりました。→ ここで直接実行をやめ、プランモードに上げます。
  3. プランを承認したら、選んだ方式の機械的な置き換えだけを直接実行します。
⚠️ 注意
  • 「途中で複雑さが見えるかもしれないから、とりあえず直接実行」は、要件の時点で再編だと分かっている仕事には向きません。
  • 調査をせずに、完全な事前指示だけで直接実行するのも危険です。まだ読んでいない依存関係を想像で固定してしまいます。

3-8 反復は「形容詞」ではなく「観測」で進める

① 入出力の例を2〜3個見せる（端のケースを1つ入れる）

「日付の検証をもう少し堅く」は、人によって別の実装になります。入力と望む出力を見せると、変換の定義が共有されます。

入力望む出力
2026-10-05OK
2026/10/52026-10-05 に正規化
""（空文字）や null、全角の数字エラー（端のケース）

端を入れないと、モデルは典型例の形だけを覚え、null で落ちます。

② 先にテストを置き、失敗の出力を一緒に渡す

期待する挙動・端のケース・性能の上限をテストにしておけば、直ったかどうかはテストが決めます。失敗を隠して「いい感じに」と頼むと、見た目は成功でも同じ端が残ります。

③ 不慣れな領域では、実装の前に質問させる

キャッシュなら、無効化のタイミング、障害時に古い値を返すか、キーの衝突。質問を飛ばすと、無効化の抜けがレビューまで残り、差分が大きくなってから設計が変わります。

④ 問題の渡し方は「依存」で分ける

関係渡し方理由
互いに影響する（同じ関数の条件と、そのテストの期待値）1つのメッセージにまとめる分けると、先の修正が後の前提を壊す
独立している（別パッケージの誤字と、無関係な日付検証）順番に1つずつ混ぜると、片方の差分がもう片方の失敗を隠す

3-9 CI パイプライン：人の入力を待てない

① -p（--print）で非対話にする

対話の Claude Code は確認の質問で止まりますが、ジョブには人がいません。-p はプロンプトを処理し、結果を標準出力に書いて、入力を待たずに終了します。

代わりにならないもの理由
「ヘッドレス」という名前の環境変数そのような仕組みはない
--batch フラグ存在しない
標準入力を捨てるプログラムが質問を出して待つこと自体は止まらない

② 出力の形を固定する

PRの行に機械でコメントを付けるなら、文章ではなく構造です。--output-format json と --json-schema で欄を固定します。

欄中身
fileファイル名
line行番号
severity重大度
body指摘の本文
duplicate前回と同じ指摘なら真（投稿スクリプトはこの行を飛ばす）

自由文だと、投稿スクリプトが行番号を読み違えます。

③ 1回の実行で渡すもの

flowchart LR
  D[差分] --> R[レビュー実行<br>claude -p]
  S[基準: CLAUDE.md] --> R
  PR[前回の指摘 JSON] --> R
  T[既存テストのパス] --> R
  R --> J[JSON の指摘<br>duplicate 付き]
  J --> P[投稿スクリプト<br>duplicate=真は飛ばす]
  • 基準は CLAUDE.md に書く：価値のあるテストとは何か、使えるフィクスチャ、指摘しないスタイル。空だと、体裁だけのテストやスタイルの指摘が増えます。
  • 既存テストを渡す：すでに覆っているケースを再提案させないためです。
  • 前回の指摘を渡す：入れ忘れると duplicate は常に偽になり、同じ行に同じコメントが2回付きます。
  • リポジトリ全体を無関係に読ませると、指摘がスタイルの話に逃げます。

④ 書いた会話でレビューしない

コードを書いた会話には、書いたときの理由が履歴に残っています。モデルはその理由を疑いにくく、自分のコードを擁護します。「よく考えて」と思考を長くさせても、同じ履歴の上で考えるだけです。

  • 生成ジョブとレビュージョブは別のプロセスにします。
  • レビューに渡すのは差分と基準だけ。生成のログをレビューのプロンプトに貼ると、別プロセスでも同じ履歴を再現してしまいます。

（この分離は、第4章の「複数パスのレビュー」と同じ理由です。）

3-10 指示ファイルが読み込まれる仕組み

仕組み押さえる点
起動時に読まれる作業ディレクトリと、その上の階層にある CLAUDE.md と CLAUDE.local.md
あとから読まれる作業ディレクトリより下のサブディレクトリの CLAUDE.md は、Claude がそのサブディレクトリのファイルを読み書き・編集したときに読み込まれる
.claude/rules/paths があれば、Claude が Read・Write・Edit で一致するファイルを扱うときに読み込まれる。paths がなければ起動時に毎回読み込まれる
@path/to/file のインポートCLAUDE.md からほかのファイルを取り込む。相対パスはインポートを書いたファイルが基準。サービスの CLAUDE.md から取り込んだ指針は、そのサービスで作業するときだけ読み込まれる
/initコードベースを調べて CLAUDE.md の下書きを作るコマンド
届き方CLAUDE.md の内容は、システムプロンプトの後にユーザーメッセージとして渡される。Claude は従おうとするが、毎回守られる保証はない（助言的）
❗ 重要

CLAUDE.md・ルール・スキルの内容は、いずれも「コンテキストとして渡される指示」で、強制される設定ではありません。必ず守らせたいこと（フォーマッタを必ず走らせる、特定のパスを編集させない）は、フック（PostToolUse の matcher に Edit|Write）や権限ルール（deny に Edit(./vendor/**)）で強制します。

一度きりの作業で手本を示すなら @ で参照

プロンプトの中で @ に続けてファイルのパスを書くと、Claude は応答の前にそのファイルを読みます。「この既存の実装と同じ書き方で」と手本を示すときに便利です。CLAUDE.md・ルール・/init は繰り返し使う指示を整える仕組みで、一度きりの作業の手本には向きません。

ほかの読み込み先

  • SessionStart フックは、セッションの開始時にコマンドを実行し、その出力をコンテキストに加えられます。
  • サブエージェントは .claude/agents/ に定義し、依頼文での指名や @ メンションで呼び出します。

3-12 仕事の進め方の公式のおすすめ

Claude に検証の手段を与える

テスト、ビルド、スクリーンショットとの比較など、Claude が自分で実行できる合否の基準を与えます。すると Claude は、作業 → 検証 → 結果を読む → 直す、を合格するまで繰り返せます。検証の手段がないと、人が検証役になり、すべての誤りが人に気づかれるまで残ります。/model で性能の高いモデルに替えても、何を正解とするかの基準は与えられません。

大きな機能は、Claude にインタビューさせてから

まず Claude に AskUserQuestion ツールで質問させ、実装の方法・端のケース・トレードオフを確かめます。答えを仕様にまとめてから、新しいセッションで実装に入ります。本人が気づいていない論点も、Claude からの質問として表に出ます。

進め方向いている仕事
すぐに依頼する（直接実行）誤字の修正、ログ行の追加、変数名の変更など、差分を一文で説明できる小さな変更
プランモード直し方が決まっていない、複数の方式から選ぶ、多くのファイルにまたがる変更。承認されるまで編集やコマンドによる変更はしない
Explore サブエージェント変える場所や影響が分からないとき、広いコードを本会話の外で読ませて要点だけ受け取る
インタビュー → 仕様 → 新しいセッション要件がまだ固まっていない大きな機能

移行は「動きが変わる箇所」を調べてから

関数名や記法の違いは検索と置換で対応できます。一方、オブジェクトが変更不可になる、既定値が変わるといった変更は、書き方が同じでも結果が変わります。こうした箇所はコードの使われ方を読んで初めて特定できるので、プランモードで調べてから進めます。

コンテキストを減らす

/compact は会話を要約して短くします。一時的に余裕ができますが、同じ会話で読み込みを続ければまた膨らみます。調査そのものをサブエージェントに出すほうが、本会話を守れます。

3-13 CI と Code Review

  • GitHub Actions で Claude Code を動かすときも、プロジェクトの CLAUDE.md に書いた規約やレビューの基準に従います。~/.claude/CLAUDE.md はその人の端末だけに効くので、CI には届きません。
  • マネージドの Code Review（Claude GitHub App を通じてプルリクエストをレビューするサービス）は、2つのファイルで調整します。
ファイル役割
CLAUDE.mdプロジェクト全体の規約。レビューはその違反を指摘する
REVIEW.md（リポジトリのルート）レビュー専用の指示。重大度の定義、Nit（細かい指摘）の件数の上限、報告しない対象（生成ファイル、ロックファイル、外部の依存コード、CI で検査済みの内容など）を書ける
  • 誤った指摘が多い種類には、「動作についての主張には、名前からの推測ではなく file:line の引用を求める」のように証拠を必須にすると、誤りが減ります。
  • REVIEW.md はプルリクエスト自身の変更ではなく、ベースブランチ（または既定のブランチ）から読まれます。
  • レビュー全体の丁寧さ（Quick・Standard・Deep）は、組織の Owner が設定するレビューのレベルで決まります。
  • GitHub Actions 連携（/install-github-app で .github/workflows/claude.yaml を作成、anthropics/claude-code-action@v1）では、permissions に id-token: write を設定し、trigger_phrase（既定 @claude）や prompt、claude_args（--max-turns 等）で制御します。
  • プラグイン（.claude-plugin/plugin.json）はスキル・agents/・hooks/hooks.json・.mcp.json をまとめて共有でき、name によりスキルが /<plugin-name>:<skill-name> の namespace に分かれ衝突を防げます。実行権限を引き継ぐため、導入前に必ず中身を検査します。

まとめ：どう判断するか

状況判断
同僚に指示が届かないホームのファイルを疑う。/context の Memory files で読み込まれているファイルを見る
置き場所に迷う全員が /名前 で呼ぶ手順は .claude/skills/（旧 .claude/commands/ も同じ扱い）、常時の標準は CLAUDE.md、呼び出す手順はスキル、散らばったファイルへの自動規約は paths
スキルの設定context: fork は本会話を守る、allowed-tools はスキル中のツールを絞る、argument-hint は引数を促す。SDK の allowedTools とは別
進め方（規模・調査）大きい・案が複数・多数ファイルはプランモード。分かっている小さな修正は直接実行。長い探索は Explore に要約させる
結果がぶれる入出力の例を2〜3個（端を含む）。影響し合う修正は1通に、独立した修正は順に。不慣れな領域は実装前に質問させる
CI非対話は -p。指摘は JSON とスキーマ。再レビューは新規と未対応だけ。書いた会話でレビューしない
必ず守らせたいCLAUDE.md・ルール・スキルは助言的。フックや権限ルール（deny）で強制する
システムプロンプトを変えたい既定を残すなら --append-system-prompt、置き換えるなら --system-prompt。自動読み込みを省くなら --bare
進め方（検証・要件定義）検証の手段（テスト等）を与える。大きな機能はインタビュー→仕様→新しいセッション

確認問題

問1

リポジトリをクローンした全員が /review で呼べるレビューの手順を置きたい。ファイルはどこに置きますか。

A. .claude/skills/review/SKILL.md
B. ~/.claude/skills/review/SKILL.md
C. ルートの CLAUDE.md の中だけ
D. 個人の ~/.claude.json

解答

A。プロジェクトのスキルはリポジトリにあるので、コミットすればチームで共有できます（旧来の .claude/commands/review.md も同じ扱いで動きます）。Bは個人用です。Cは指示であって、コマンドとしては登録されません。DはMCPの個人設定です。

問2

テストファイルが各実装の隣に散らばっています。テストを編集したときだけ、同じテスト規約を自動で読み込ませたい。どうしますか。

A. .claude/rules/ に **/*.test.tsx の paths を書く
B. 全規約をルートの CLAUDE.md に書き、節の選択はモデルに任せる
C. 規約をスキルに入れ、毎回人が呼ぶ
D. テストがあるディレクトリごとに CLAUDE.md を複製する

解答

A。Bはモデルの推測、Cは手動、Dは複製の保守が必要です。「自動で」かつ「1か所で保守できる」を満たすのは A だけです。

問3

数十ファイルとサービス境界の判断が必要な再編です。最初の進め方はどれですか。

A. プランモードで調査し、方式を決めてから変更する
B. 直接実行で進め、境界は書きながら決める
C. 調査なしの完全な事前指示だけで直接実行する
D. 直接実行を始め、困ってからプランモードへ切り替える

解答

A。境界の判断が要件の時点で必要です。書きながら決めると、間違った境界の差分が先に積み上がります。

問4

CI パイプラインのレビューが、確認の入力待ちで終わりません。何を付けますか。

A. -p
B. ドキュメントにないヘッドレス用の環境変数
C. ドキュメントにない --batch
D. 標準入力を捨てるだけ

解答

A。-p（または --print）が、結果を出して終了する起動方法です。

問5

説明文だけでは変換結果がぶれます。次に足すものとして効果があるのはどれですか。

A. 「注意深く」という語
B. 端のケースを含む入出力の例を2〜3個
C. モデルの確信度の自己申告
D. 利用者レベルの CLAUDE.md への秘密のトークン

解答

B。形容詞や自己申告では、望む変換の形が伝わりません。トークンは指示ファイルに書いてはいけません。

問6

CI のスクリプトから Claude Code を -p で呼び、出力の形式についての指示を足したい。ただし、Claude Code が既定で持つツールの使い方やコーディングの規約は残したい。どのフラグを使いますか。

A. --system-prompt-file
B. --append-system-prompt-file
C. --bare
D. --permission-mode dontAsk

解答

B。追加のフラグは既定のシステムプロンプトの末尾にテキストを加えるので、既定の指示は残ります。A は既定のプロンプト全体を置き換えるため、ツールの使い方や規約が消えます。C は CLAUDE.md やフックなどの自動読み込みを省く最小構成のモードです。D は許可していないツールを確認なしで拒否する権限モードです。

問7

プロジェクトの規約が守られていないようです。起動時に読み込まれるはずの CLAUDE.md が、このセッションに本当に読み込まれているかを確かめたい。どのコマンドを使いますか。

A. /memory
B. /context
C. /init
D. /compact

解答

B。/context の Memory files の一覧で、読み込まれたファイルを確かめます。A の /memory はメモリファイルの場所を一覧して編集するためのコマンドで、読み込まれたかの確認には使いません。C は CLAUDE.md の下書きを作り、D は会話を要約して短くします。

問8

ファイルを編集するたびに、必ずフォーマッタを走らせたい。CLAUDE.md に「編集後はフォーマッタを実行すること」と書いても、ときどき忘れられます。どうしますか。

A. CLAUDE.md の指示を太字にする
B. PostToolUse フックの matcher に Edit|Write を指定し、フォーマッタを実行する
C. .claude/rules/ に同じ指示を書く
D. スキルにフォーマットの手順を書く

解答

B。CLAUDE.md・ルール・スキルはどれも助言的な指示で、毎回守られる保証はありません。フックは決まった時点で必ず実行される決定的な仕組みです。

自分で確かめる

  1. 同じ規約文をホームの CLAUDE.md とプロジェクトの CLAUDE.md に分けて置き、別のディレクトリから開いたときにどちらが読み込まれるか、/context で確認します。
  2. **/*.test.* のルールが、実装ファイルを編集しているときには読み込まれないことを確認します。
  3. 同じプロンプトを対話で実行すると入力待ちになり、-p を付けると終了することを、短いエコーで比べます。

第4章 プロンプトエンジニアリングと構造化出力

💡 ヒント

この章のたとえ：プロンプトは「新人への業務マニュアル」

「丁寧にやって」「慎重に」と言われても、新人は何をすればいいか分かりません。「この種類のミスは報告、この種類は無視」と基準を示し、見本を2〜3枚見せ、提出用紙（書式）を決めておけば、仕事はそろいます。さらに提出物はチェック係（検証）が確かめ、間違いがあれば「どこがどう違うか」を添えて差し戻します。

この章のゴール

  • 何を報告し何を捨てるかを、形容詞ではなく「基準」で書ける。
  • 出力がぶれるとき、少数の具体例（few-shot）で一般化させられる。
  • 構文はスキーマ付きのツール使用で固定し、意味の矛盾は検証と再試行で扱える。
  • 待ち時間が許されない仕事を、遅延保証のないバッチに置かない。
  • レビューを、書いた会話から切り離し、ファイル単位と横断に分けられる。

要点3つ

  1. 「慎重に」は基準ではない。 報告する種類と捨てる種類を、コード例つきで書く。
  2. スキーマは「形」を守るが「中身の正しさ」は守らない。 合計の不一致などは、検証して、理由を添えて再依頼する。無い情報は null にする。
  3. バッチは半額だが最大24時間・遅延保証なし。 人が待っている仕事やツール往復が必要な仕事には使わない。

本編

4-1 基準のないレビューは、好みを欠陥として報告する

「コメントの正確さを確認して」とだけ頼むと、文体の好みまで指摘されます。開発者は2回目から、正しいバグの指摘まで読み飛ばすようになります。

基準はこう書く

書き方
❌ 形容詞「保守的に」「確信度が高いものだけ」「慎重に」
✅ 種類で線を引く「コメントが主張する挙動が、実際の分岐と矛盾するときだけ指摘する。命名・空行・局所的な書き癖は指摘しない」

モデルの確信度の自己申告は、難しいケースほど高く出すぎます。数値で絞り込む前に、種類で線を引きます。

レビュー規約の例（この密度で足ります）

区分内容
報告する分岐がコメントや名前と矛盾する欠陥／認証の抜け／検証されていない入力が外部へ出る箇所
捨てるインポートの順序／1行の長さ／既存ファイルにすでにある書き癖
重大度：高本番データが誤った相手に出る、または例外が握りつぶされて呼び出し元が成功に見える（コード断片つきで定義）
重大度：中特定の入力でだけ結果が違うが、データは漏れない
重大度：低報告しない、と書き切る
⚠️ 注意

「低」を残すと、モデルは「低」を埋めるために好みを報告し始めます。また「高」という語だけでは、同じ欠陥が人によって別の段階になります。段階ごとにコード断片で定義します。

誤検知が多い種類は、いったん外してよい

好みの指摘が正しいバグの隣に並ぶだけで、正しい指摘まで無視されるようになります。直すあいだ、その種類を指摘対象から外します。

  • 外すときは「インポートの順序、1行の長さ、既存の書き癖は書くな」と種類を名指しします。「慎重に」では、どの種類を外したかが残りません。
  • 戻すときは、その種類の正例と反例を足してからにします。
    • 正例：コメントと矛盾する空の catch
    • 反例：プロジェクトにすでにある同じ空の catch で、呼び出し元が失敗をちゃんと見ているもの

4-2 具体例（few-shot）は「一致表」ではなく「一般化の材料」

指示が長いのに形式がぶれるとき、効くのが few-shot です。

ポイント理由

選ばなかった代替と、その理由を書く理由がない例は、表面の語だけを真似される
正例と反例を対にする（レビュー）対がないと、例に似た正しいコードまで指摘する
該当なし（null）の例を1つ入れる（抽出）他の例が全部値を埋めていると、情報がない文書でも値を作る
出力の形も例で見せる自由文の例を見せながらスキーマを要求すると、自由文に戻る

依頼選ぶツール捨てたツールと理由

「山田さんの住所は？」顧客取得注文参照ではない。番号がなく、人を特定する依頼だから

体裁の違い（本文中の引用と末尾の参考文献、方法の節と本文に埋め込まれた条件）を例で見せると、必須欄が空で返る頻度が下がります。そのうえで、例の1つは「税額の行がない請求書 → 税額は null、合計は本文の数字のまま」にします。この例がないと、モデルは合計の1割を税額として作ってしまいます。

4-5 意味の検証と再試行：材料があるときだけ効く

意味の検証はスキーマの外に足す

声明の合計と、明細から計算した合計を両方抜き出し、一致しなければ再依頼します。情報源どうしが矛盾するなら conflict_detected を立て、どちらかを知らせずに捨てさせません。

3通目でも同じ矛盾なら、再試行をやめて conflict_detected のまま人手へ回します。上限まで自動で回すと、モデルは3通目で存在しない行を作ります。矛盾は上限を待たずに人手へ回してよいです。

検証器は値を黙って直さない

Pydantic のような検証器は、スキーマと意味の検査をコードで行い、失敗の理由を次のプロンプトに戻すための道具です。検証器が黙って桁を直すと、モデルは誤りを知りません。

却下された指摘から学ぶ：detected_pattern

レビュー指摘に detected_pattern（指摘のもとになったコードの形）を残すと、開発者が却下したときに「空の catch が誤検知の源だ」と集計できます。件数だけ捨てると、基準の改善が勘になります。

custom_id と失敗の再送

例：100件に doc-001 〜 doc-100 を付けて夜間に送った。朝、4件がコンテキスト長で失敗し、96件は成功した。

  • 同じ識別子で再送すると、どの版の失敗かがログで混ざります。
  • 下流は識別子を使って、文書ごとに「最新の成功」を1つに決めます。

4-7 レビューは「誰が」「何パスで」見るか

① 書いた会話でレビューしない

同じ会話の自己レビューでは、生成時に「この境界でよい」「この catch は意図的」と判断した文が履歴に残っています。見直せと言われても、その判断を擁護します。思考を長くさせても、同じ履歴の上で考えるだけです。差分と基準だけを渡した別の実行のほうが、前提を持たないので矛盾を見つけます。

② 多数のファイルは「ファイル単位 → 横断」の2段に分ける

各指摘に確信度を付けるのは、人に回す優先順位の材料にはなります。ただし、その数値を閾値として使う前に、ラベル付きのデータで校正が必要です（第5章）。未校正の数値で自動マージしてはいけません。

文書の中に相反する値があるとき（改定前と改定後の条件など）、値を1つしか持てない欄では、モデルはどちらかを選ぶしかなく、選び方が文書ごとに揺れます。値を配列で持たせ、各要素に記載箇所と発効日を必ず入れる構造にすると、出力の形がそろい、あとから検証できます。

エラーのメッセージをそのまま再試行に使う

'10日前後' is not of type 'integer' のような検証のメッセージは、誤った欄・受け取った値・求められる型を示しており、そのまま修正の指示として働きます。同じリクエストを変えずに送り直す再試行とは、モデルに渡る情報が違います。

4-9 出力の長さとコンテキストウィンドウ

現象仕様対処
出力が max_tokens に達したstop_reason が max_tokens になり、途中で切れる。ツールの入力の途中なら tool_use ブロックは未完成のままmax_tokens を上げて再試行。ただし出力量が入力の規模に比例するなら、入力を小さく分けて呼び、結果をつなぐ（配列ならつなげるだけで1つの結果になる）
入力だけで上限を超えたAPI は 400 の invalid_request_error（prompt is too long）を返す。通常の API でもバッチでも同じ文書を区切って送り、区切りごとの結果をあとでまとめる
コンテキストウィンドウに数えるものシステムプロンプト、messages（文書やツール結果を含む）、ツール定義、そのターンの出力入力が上限近くまで占めると、出力の余地がその分だけ減る。キャッシュで再利用する部分や、Files API で参照するファイルの中身も入力に数える
長い文書の置き場所長い文書をプロンプトの先頭に置き、質問や指示を後ろに書くと応答の質が上がる—
コンテキストの劣化（context rot）トークン数が増えるほど、精度と想起が下がる関係する情報を選んで与える。大きいウィンドウのモデルに替えても、送る量が同じなら残る

料金の決まり方：モデルごとのトークン単価 × 使った入力と出力のトークン数。max_tokens は生成の上限で、単価には関係しません。

4-11 プロンプトの書き方の公式の指針

曖昧な依頼には、解釈を置いて進め、それを示す

曖昧な依頼に質問だけを並べて返すと、利用者は答えるまで何も受け取れません。手元の情報から妥当な解釈を置いて作業を進め、置いた解釈を明示し、違っていれば調整すると申し出ます。解釈が外れていても、示された解釈を見て訂正できます。どの程度質問し、どの程度自分で判断するかは、システムプロンプトで明示的に指示できます。

観点を詰め込みすぎない

1回の呼び出しに多くの観点を詰め込むと、注意が観点の間で分かれます。ある観点の例を増やすと、その観点の検出は上がる一方で、ほかの観点の検出が下がる、という奪い合いが起きます。観点ごとに呼び出しを分け（プロンプトチェーンや並列の呼び出し）、それぞれに専用の例を持たせて、最後に指摘の一覧を統合します。

発見と絞り込みを分ける

レビューのプロンプトに「重大なものだけ」「確実なものだけ」と書くと、見つけていても基準に届かないと判断した指摘は報告されません。見落としたのではなく、指示どおりに外した状態です。見逃しを減らしたいなら、発見の段階では不確かなものや軽微なものも含めてすべて報告させ、各指摘に確信度と重大度を付けさせます。どれを採用するかは、後段の検証や振り分けでその値を使って決め、線は正解付きのデータで確かめてから引きます。

📝 メモ

4-1 の「報告しない種類を名指しする」と矛盾はしません。種類として価値がないもの（言い回しの好みなど）は最初から外し、価値のある種類の中での確からしさによる絞り込みは後段に回す、という使い分けです。

正しさと価値は別の軸

言い回しの好みの指摘は、内容としては誤っていません。だから「正しいか見直して」と頼んでも減りません。減らすには、指摘する対象と指摘しない対象を具体的に書きます。

ツールを使うエージェント型のレビュー

エージェントは、必要な情報をその場で取りに行けます（just-in-time な文脈の取得）。変更した項目や関数の名前でコードを検索し、見つかったファイルを読み、さらにその先の参照をたどる、という手順を自分で組み立てられるので、影響が思わぬ場所に及ぶ変更のレビューに向きます。ターン数の上限を設ければ、1件のレビューの長さを抑えられます。

レビューで直された結果を例に生かす

人が直した抽出を集計すると、誤りが特定の入力の型に集中していることが分かります。その型の正しい扱いを few-shot の例として示すと、同じ型の誤りをまとめて減らせます。

Prompt Evaluation（Model Grader のバイアス対策）

Code Grader（json.loads() 等による形式・構文の検査）と Model Grader（タスク達成・網羅性の評価）を組み合わせます。Model Grader で JSON 出力に score（1〜10）だけを求めると 6 付近の中庸な点に偏りやすいため、必ず先に strengths（1〜3点）・weaknesses（1〜3点）・reasoning を出力させてから score を付けさせます。評価で満点（10/10）だった出力は、理由を添えて few-shot の <ideal_output> に再利用できます。

Prompt Caching のルール（補足）

キャッシュは Tools → System Prompt → Messages の順に評価され、1文字でも変わるとその地点以降が無効になります。1リクエストあたり最大 4 cache breakpoints、breakpoint までの合計最低 1,024 tokens が必要で、TTL は既定 5分（cache hit 時に追加課金なしで延長）です。

確認問題

問1

自動レビューの誤検知が多く、正しい指摘まで無視され始めています。最初に直すものはどれですか。

A. 「確信度が高いものだけ」と足す
B. 報告する欠陥と捨てる指摘を、種類とコード例で定義する
C. 文章の否定的な調子でレビュー対象を決める
D. 3回実行し、2回以上出た指摘だけ残す

解答

B。自己申告（A）、感情（C）、多数決（D）は、何が欠陥かという定義をあいまいなままにします。

問2

文書の種類が事前に分からず、抽出スキーマが2つあります。必ず構造化された形で受け取りたい。tool_choice はどれですか。

A. auto
B. any
C. ツールを定義せず、文章でJSONを依頼する
D. バッチの custom_id

解答

B。種類が不明で、どれかの構造で必ず返させたいなら any です。特定の1段を先に通したいなら強制です。auto は文章で返すことがあります。

問3

合計欄が明細と一致しない抽出結果が、スキーマ検証は通過しています。次の一手はどれですか。

A. スキーマを通ったので採用する
B. 声明の合計と計算した合計を比べ、不一致のメッセージを添えて再依頼する
C. 同じプロンプトを、メッセージなしで再実行する
D. 必須欄を増やし、欠落を埋めさせる

解答

B。これは意味の誤りです。C は同じ結果を繰り返すだけで、D は存在しない値の創作を誘います。

問4

夜間の技術的負債レポートと、マージ前に終わらせたい危険チェックがあります。費用を下げるため両方をバッチに移す提案を、どう評価しますか。

A. 夜間のレポートだけバッチにし、危険チェックは同期のままにする
B. 両方をバッチにする。たいてい朝までに終わる
C. 識別子で対応づけられないので、夜間も同期にする
D. 遅いときだけ同期へ切り替える仕組みを、用途を分ける前に作る

解答

A。バッチには遅延の保証がありません。対応づけは custom_id でできます（C は誤り）。切り替えの仕組み（D）は、用途を分けるより先に作るものではありません。

問5

14ファイルを1つのパスでレビューすると、深さがばらつき、同じパターンの判定が矛盾します。どう分けますか。

A. ファイルごとの局所パスと、横断のデータの流れを見る別パス
B. より大きいコンテキストのモデルに替え、1つのパスを維持する
C. 提出を3ファイルずつに分ける規則だけを足し、レビューの構造は変えない
D. 独立に3回実行し、2回以上出たものだけ採用する

解答

A。原因は一度に配れる注意の偏りです。モデルの大きさ、提出の規則、多数決では、各パスの入力は小さくなりません。

問6

ツール定義に strict: true を付けて請求書を抽出しています。スキーマ違反は起きなくなりましたが、文書に書かれていない支払期日が入っていることがあります。due_date は必須の文字列です。最初に見直すべきところはどれですか。

A. strict: true を外す
B. due_date を nullable にし、「本文に明記されていなければ null」と指示する
C. due_date に日付の形式の制約を足す
D. max_tokens を増やす

解答

B。必須の欄は、スキーマを満たすために何らかの値で埋められます。strict が保証するのは形だけで、値が文書の内容として正しいかは保証しません。C の形式の制約は、もっともらしい日付（形式は正しい）を区別できません。

問7

レビューのプロンプトに「確実な問題だけを報告して」と書いたところ、本番で起きた不具合を、調査はしていたのに報告していなかったことが分かりました。見逃しを減らす変更として最も適切なものはどれですか。

A. 「もっと注意深く」と書き足す
B. 発見の段階ではすべてを報告させ、各指摘に確信度と重大度を付けさせて、採否は後段で決める
C. 同じレビューを3回実行して多数決をとる
D. 確信度が0.9未満の指摘を生成後に削除する

解答

B。「確実なものだけ」という指示が、見つけた指摘を報告から外させています。発見と絞り込みの役割を分け、絞り込みは正解付きのデータで確かめた線で後段が行います。D は絞り込みの線を変えるだけで、モデルが報告しなかったものは戻りません。

問8

Message Batches API で 5万件を処理しました。結果の一覧の順番が、送ったときの順番と違います。結果を元のリクエストと対応づける方法として正しいものはどれですか。

A. 結果は必ず送った順に並ぶので、並べ替えは不要
B. 各リクエストに付けた custom_id で対応づける
C. 結果の本文を元の文書と文字列比較して対応づける
D. バッチを1件ずつに分けて送り直す

解答

B。バッチの結果は送った順に並ぶとは限りません。custom_id で対応づけます。失敗した（errored）リクエストは課金されず、それだけを新しいバッチで送り直せます。

自分で確かめる

  1. 税額の欄がない文書とある文書を用意し、税額を必須にしたスキーマと null を許したスキーマで、ない税額が作られるかを比べます。
  2. 検証失敗の再依頼に、文書・失敗結果・メッセージを含めた場合と、プロンプトだけで再実行した場合で、同じ誤りが残る回数を数えます。
  3. 14ファイルを1つのプロンプトで読ませた指摘と、ファイル単位のあと横断させた指摘で、同じパターンの判定が矛盾する箇所を数えます。

第5章 コンテキスト管理と信頼性

💡 ヒント

この章のたとえ：長い会話は「伝言ゲーム」

伝言を重ねるほど、「8000円、金曜まで」は「なるべく早く」に丸まっていきます。だから大事な数字は伝言に任せず、メモ用紙（事実ブロック）に書いて毎回手渡します。伝言が途中で途切れたら「ここで途切れた」と正直に書き、2人の証言が食い違ったら、両方をそのまま記録します。

この章のゴール

  • 長い会話で、金額や期日を要約に溶かさず、毎回渡す事実として残せる。
  • 人へ引き渡す条件と、自分で解決する条件を分けられる。
  • 失敗を、握りつぶさず全体を止めもせず、親が復旧方法を選べる形で伝えられる。
  • 広いコードベースの探索で、会話が具体を忘れる前に発見を外に出せる。
  • 平均の精度だけで人の確認をやめず、出典の食い違いを1つの数字に潰さない。

要点3つ

  1. 数字・日付・番号・状態は要約の外。 事実ブロックとして毎回プロンプトの先頭に入れる。要約してよいのは経緯だけ。
  2. 人へ渡すのは「明示された」「方針に書いていない」「進展が止まった」とき。 怒っている、難しそう、確信度が低い、では渡さない。
  3. 平均の精度は区分の失敗を隠す。食い違う出典は両方残す。 文書の種類・欄ごとに精度を見て、出典には日付を持たせる。

  T -->|金額・状態をコピー| K[事実ブロック<br>顧客・注文・金額・状態・期日]

本編

5-1 履歴は全部渡す。ただしツール結果は足す前に切る

履歴を省くと、決めたことが消える

次のAPI依頼で履歴の一部を落とすと、前に確定した制約が消えます。「写真のない返金はしない」と決めたターンを省くと、モデルは写真なしで返金を提案します。続ける会話では、履歴を渡します。

ツール結果を無加工で積むと、コンテキストが埋まる

注文照会が40欄を返し、返品に必要なのは5欄（番号・金額・状態・配送日・写真の有無）だけだとします。40欄のまま10回照会すると、コンテキストの大半が無関係な配送業者コードで埋まります。

切るタイミング結果
❌ モデルに読ませたあと全文はすでにコンテキストを使っている
✅ 履歴に足す前必要な欄だけが残る
❗ 重要

捨てる前に、後で必要な値（金額・状態）を事実ブロックへコピーします。コピーを忘れて捨てると、履歴からもブロックからも金額が消えます。切る処理のテストは「ブロックに 8000 が残っていること」です。

5-2 事実は要約の外に置く

要約を重ねるほど、「8000円、金曜まで」は「迅速に対応」になります。取引の事実は、要約された物語とは別のブロックにします。

事実ブロックの例（文章ではなく行で書く）

顧客: C-42
注文: A-19
金額: 8000
状態: 配送済み
利用者の期日: 金曜
写真: 未着
---
経緯の要約: 破損の申告が2回あり、写真を依頼した。
  • 事実ブロックは要約関数に渡さない。要約関数を通すと、8000 が「数千円」に、金曜が「早めに」になります。
  • 実装では、要約の入力からブロックを除外し、要約の出力の前に毎回結合します。
  • 要約してよいのは経緯の叙述だけです。

用件が複数あるときは、用件ごとに層を分ける

1つの段落にまとめると、どの金額がどの注文のものか分からなくなります。

大事な但し書きは先頭にも置く（lost in the middle 対策）

flowchart LR
  A[先頭<br>よく読まれる] --- B[真ん中<br>見落とされやすい] --- C[末尾<br>よく読まれる]

長い入力の真ん中の段落にだけ「ただし返金不可」と書くと見落とされ、モデルは返金可能として話します。重要な指摘の要約を先頭に置き、詳細は見出し付きの節に分け、但し書きは先頭の事実ブロックにも1行入れます。

下流に渡すのは「事実・引用・関連度」

下流の予算が小さいなら、上流は推論の過程や全文ではなく、事実・引用・関連の度合いを返します。日付、情報源の場所、方法（検索クエリか、PDFの何ページか）を構造に含めます。親が子の文章を自分の言葉で書き直してから次に渡すと、この構造が消えます。

5-3 人へ渡す条件は「トーン」ではない

  B -->|いいえ| C{方針がこの要求に<br>何か書いている?}

直ちに渡す3つの条件

  1. 利用者が人の担当を明示した →調査より先に渡します。先に注文を調べると、人が欲しいと言ったのに待たせることになります。
  2. 方針の空白 →例：方針には自社サイトの価格調整しか書いていないのに、利用者が「競合の価格に合わせて」と言う。これは難易度ではなく方針の空白です。エージェントが承認すると、書いていない規則を作ったことになります。
  3. 進展が止まった →同じ質問を2往復しても新しい事実が出てこない。

渡さないもの

きっかけなぜダメか
「複雑に見える」単純な交換を人に渡し、方針の穴を自分で承認する、という逆転が起きる
不満のトーン範囲内の問題なら、不満を受け止めて解決を申し出る。同じ希望を重ねたら渡す
確信度の自己申告難しい案件ほど、誤って高く出る
感情スコア案件の複雑さや方針の空白と相関しない

複数の顧客に一致したら、選ばずに聞き返す

同姓が2人に一致したら、名前の近さで1人を選びません。どちらにも返金せず、電話番号の下4桁などを尋ねます。それらしい選択が、別人への返金になります。

基準は「両側の例」とセットでシステムプロンプトに置く

例正しい行動
怒った文面だが、写真と注文番号がそろった標準的な破損交換（期限内）不満を受け止め、自分で交換を申し出る
穏やかな文面だが、競合価格への合わせを求める人へ渡す（方針の空白）
同姓が2人に一致どちらにも返金せず、追加の識別子を尋ねる

この対がないと、モデルはトーンを難易度だと思い込み、怒った簡単な交換を渡して、穏やかな方針の穴を自分で承認します。また、例が「それらしいほうを選べ」になっていると、例が基準の文章に勝ちます。例のほうを直します。

5-4 失敗は、親が「3つの続き」を選べる形で返す

親の選択肢は3つです。

  1. クエリを変えて再試行する
  2. 代わりの情報源へ行く
  3. 部分結果で終え、穴を注記する

この選択には、失敗の種類・試したクエリ・取れた部分結果・考えた代替が必要です。

例：検索の子がタイムアウトした

子の返し方親が取れる行動
✅ 種類：一時的／クエリ：3本／部分結果：音楽の記事2件／代替：文書庫の検索2件を最終報告に使い、文書庫へ音楽だけを再委任する
❌ 「失敗」だけ3本全部を最初からやり直す
❌ 「検索を利用できません」の1文クエリを変える材料がない
❌ 空の成功に変換音楽は「無かった」と書いてしまう
❌ 例外のまま上げて調査全体を止める取れていた抜粋まで捨てる

成功したゼロ件は、失敗に入れない

ゼロ件を失敗にすると再試行が無駄になり、タイムアウトをゼロ件にすると、穴が「無かった」という結論になります。

子が直すのは一時的な障害だけ

子は一時的な障害を短い再試行で自分で直し、直せないものだけを親に上げます。

最終報告には穴を書く

統合の最後の節は「裏付けのある主張」と「未調査の領域」です。未調査を書かないと、読者は完全な調査だと誤解します。親は「子が返した穴の行が、最終報告に残っていること」を出力の検査にします。

5-5 広いコードベースの探索では、会話が具体を忘れる

長い探索のあと、モデルが見つけたクラス名ではなく「典型的なサービス層では…」と一般論で話し始めたら、劣化のサインです。会話の真ん中に埋もれた発見が、新しいターンの注意から落ちています。

対策は5つ。順番が大事

5-6 人の確認は、平均の精度では減らせない

平均は、件数の多い簡単な種類に引っ張られる

10万件の抽出が全体で97％でも、手書きの領収書の税額欄だけ60％かもしれません。

文書の種類欄件数精度
印刷の請求書合計95,00099％
印刷の請求書税額95,00098％
手書きの領収書税額5,00060％
（全体：文書10万件）約97％

人の確認を減らす前に、文書の種類ごと・欄ごとの表を作ります。すべての区分で安定している区分だけが、自動化の候補です。

確信度が高いものも、層化抽出で測る

確信度が高いものを監査から外すと、系統的な偏り（特定の帳票で合計を税額に入れる、など）が人の目を通らずに流れます。文書の種類と欄の組み合わせごとに、確信度の高いものからも無作為に抜き取り、誤り率を週ごとに見ます。新しい帳票の版が加わった週は、その種類の抜き取りを増やします。

確信度の閾値は、ラベル付きデータで校正する

例：100件のラベル付き請求書で、モデルの欄ごとの確信度と、実際に合っていたかを集計します。

  • 確信度0.9以上の税額のうち、実際の正解率が0.95を超える区分だけを、人の確認から外す候補にする。
  • 手書きの区分で実際の正解率が0.6なら、確信度が高くても人が見る。
  • 申告0.9の実際の正解率が0.6なら、0.9は自動採用の線ではありません。

人が見る優先順位は、校正後に低い欄と、情報源が曖昧または矛盾している抽出です。担当者の時間は有限なので、安定した欄から自動化し、矛盾は人に残します。

5-7 出典・時点・矛盾

主張と情報源の組を、統合まで壊さない

子には「URLまたは文書名・抜粋・公開日または収集日」を構造で出させ、下流はその組を保持します。親が「だいたいこう書いてあった」と書き直した時点で、組は壊れます。

2つの信頼できる情報源で数字が違うとき

例：同じ年の就業率が、出典Aでは62％、出典Bでは64％。

❌ 新しいほうを黙って採用読み手が検証できない
❌ 平均の63％を1つのセルに書くどちらの定義でもない数字になる
✅ 両方を出典つきで残す「2ポイントの差があり、定義は出典を参照」と書ける

  • 元の文書が「速報」と呼んでいるものを「確定値」と書き換えません。特徴づけと方法（調査の母数・期間）を残します。

時点の差を矛盾と取り違えない

  • 年が違うなら、矛盾ではなく時点の差として別の行にします。
  • 日付のない出典は「時点不明」と書き、年付きの行と足し算しません。日付のない「利用率」は、別の年の数字でも同じ主張に見えてしまいます。

表現は中身に合わせる

コンテキストの劣化（context rot）は、トークン数が増えるほど情報を正確に思い出す力が下がる性質です。履歴が同じ長さのまま残る限り、指示を足しても、セッションを区切って再開しても、この性質は変わりません。量そのものを減らすか、外に書き出します。

古いツール結果が残る会話の再開

会話を再開すると、以前のツール結果も履歴として毎回モデルに送られます。新しい結果を取り直しても、モデルが古い結果やそれに基づく以前の発言を参照してしまうことがあります。テストでそれが確かめられているなら、「古い結果は無視して」という注記は守られる割合を上げるだけです。古い結果を含む履歴で再開するより、新しいセッションを始め、前回の問い合わせの種類・実施した対応・未解決の点を構造化した要約で渡し、現在の状況はツールで取り直します。経緯は引き継ぎ、古いデータは持ち込みません。

5-9 顧客対応での引き継ぎの細部

first-contact resolution（FCR）を手放さない

first-contact resolution は、顧客が問い合わせを繰り返さずに済むよう、その場で対応できることを完了させる考え方です。

  • エージェントの範囲で解決できるなら、ツールで確かめたあと、追加の質問をはさまずに解決を申し出ます。そのとき引き継ぎの選択肢も示すと、顧客が人の対応を望む場合にも応じられます。
  • 一部の処理が障害で止まっても、取得済みの情報でできる説明や確認まで手放す必要はありません。タイムアウトのような一時的な失敗は、時間をおいた再試行で解決することがあります。そのうえで、何ができて何ができなかったかを正直に伝え、再試行や担当者への引き継ぎといった次の手段を示します。
  • 完了していない処理を「完了した」と伝えるのは、解決ではありません。

引き継ぎの基準を明確に書く

確信度の数値、特定の語の出現、問い合わせの種類による振り分けは、機械的に扱いやすい指標ですが、人の判断が要るかどうかとは一致しません。確信度は回答への自己評価にすぎず、語の出現は言い回しに左右され、種類ごとの対応表は会話ごとの状況の違いを扱えません。「顧客が人を明示的に求めた」「規約の例外のように権限を超える」「解決に向けて進められない」という基準を明確に書くと、モデルは会話の内容に照らして判断できます。

途中で権限を超えると分かったとき

ツールで調べている途中で、権限を超える判断（無償修理の例外など）が必要だと分かった時点で引き継ぎます。それまでに得たものは会話の中にしかないので、対象の顧客と製品、確かめた事実、特定した問題、求める判断を項目に分けて渡します。生の記録の置き場所や、会員番号と製品名だけでは足りません。

5-10 統合と出典の細部

集計方法の違いから生じる食い違い

ログイン中の利用者だけを数えたログと、自己申告のアンケートのように、集計の方法が違えば数値が食い違うのは当然です。どちらも誤りではなく、別のものを測っています。

よくある対処問題
裏付けの十分な所見だけを残す条件付きの正当な所見まで消える
出典の優先順位で一方を採るもう一方の所見と方法の違いを捨てる
再実行して一致させる方法の違いから生じる食い違いは、やり直しても消えない

出典の間で一致した所見と食い違う所見を分けて示し、出典ごとの元の数値と集計の方法を残せば、読み手が根拠の質を比べて判断できます。

時点を項目として受け渡す

時点の違う値は、日付が付いていれば推移として読めますが、日付がなければ同じ時点の食い違いにしか見えません。子のサブエージェントには、値に加えて発行日や収集時点を構造化した項目として返させます。統合のエージェントは、それを時系列に並べて改定前後の変化として報告できます。

所見と根拠の ID を組で渡す

根拠が文章の中の注記としてしか付いていないと、統合で似た所見がまとめられ文面が書き換えられたときに、対応が崩れます。所見と根拠の ID を組にした構造化データで受け渡し、統合でもその組を保たせます。PostToolUse フックのような検査は形式の欠けは見つけられても、記述と根拠の組み合わせが正しいかまでは判定できません。

状態の永続化とマニフェスト

長く動くマルチエージェントの処理では、状態を決まった形式でコンテキストの外に書き出しておきます。文章の要約と違って細部が削られません。再開時はコーディネーターがマニフェストを読み、エージェントどうしの受け渡し（抽出は21件目、分類は18件目、のような進み具合の差）を含めて続きの地点を決め、各エージェントにはそのエージェントに関係する状態だけを渡します。各エージェントが別々に自分の状態を読み直して再開すると、進み具合の差をつなぐ役がいなくなります。

一致率は正確さの代わりにならない

同じ入力に対する出力の一致率は、結果のばらつきを測る指標です。正しい値と比べていないので、一致していても誤っていることがあります。正確さは、正解付きのデータと比べて測ります。

確認問題

問1

長い返品の会話を要約し続けた結果、返金額と期日が文章から消えました。どう残しますか。

A. 金額・日付・注文番号・状態を、要約の外のブロックとして毎回プロンプトに入れる
B. 要約の回数を増やして、さらに短くする

似た仕組みを、1文で見分ける

  • ゲートは「この状態が無ければ実行しない」。PostToolUse は「実行した結果を、読む前に揃える」。実行前の遮断は「規則違反の呼び出しを、APIの前で止める」（フックで止めたいときは終了コード 1 ではなく 2 を使う）。
  • auto は文章を許す。any はどれかのツールを必須にする。強制は名前を1段だけ固定し、成功したら戻す。
  • 再開は、履歴が今も本当なとき。新規への注入は、ツール結果が古いとき。フォークは、同じ起点から案を混ぜずに比べるとき。フォークが分けるのは会話だけで、ファイルは分けない（ファイルを分けるなら git worktree / --worktree）。
  • allowedTools は自動承認、tools・disallowedTools は絞り込み。--bare は自動読み込みを省き、サブスクリプションではなく ANTHROPIC_API_KEY を使う。
  • MCP のツールは モデルが呼ぶ、リソースは アプリが制御して @ で参照、プロンプトは 利用者が / で実行。
  • strict と構造化出力は形を守る。値の意味・表記・null にする条件はプロンプトと検証で扱う。
  • プロンプトチェーンは、面が見えているレビュー。動的な分解は、次の問いが途中で生まれる調査。
  • コマンドは打って呼ぶ共有手順。スキルは必要なときだけ読む手順。CLAUDE.md は常に読む指示。paths は編集したファイルにだけ載る規約。
  • バッチは、人を待たせずツール往復も要らない仕事。同期は、結果が来るまで次へ進めない仕事。
  • 有効な空は、探して無かった。失敗の空は、探せずに終わった。前者は結論、後者は穴。
