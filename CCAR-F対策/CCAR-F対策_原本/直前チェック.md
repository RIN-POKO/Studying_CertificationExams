# 直前チェック

5つの技能の判断を、1枚で見直すためのページです。各行は「どちらを選ぶか」の二択で、✕ が選ばないほう、○ がこのノートの選択です。迷った行は、見出しのリンクから本編に戻ってください。

## 1. ループと委任（[第1章](01-エージェントアーキテクチャとオーケストレーション.md)）

| 場面 | ✕ 選ばない | ○ 選ぶ |
| --- | --- | --- |
| ループを閉じる条件 | 文章の「完了」、空の文、回数の上限 | `end_turn`。`tool_use` のあいだは実行して履歴に戻す |
| トークン上限で切れたJSON | 欠けた引数を補完して実行する | 切断として扱い、予算を足して続け直すか失敗を返す |
| 同じツールが3回続く | プロンプトに「繰り返すな」と足す | 結果が履歴にあるかを先に見る |
| 次のツール | すべての分岐を決定木にする | モデルに選ばせる。事故になる順序だけゲート |
| 子は親の結論を知っているか | 知っている前提で「さっきの結果」と書く | 知らない。本文と出典を子のプロンプトに書く |
| 並列 | 依存のある役を同じ返答に並べる | 依存の無い役だけ、1回の返答に Agent ツール（旧 Task）を複数。結果は識別子で対応 |
| 子から親に戻るもの | 途中のツール結果も親に届く前提 | 届くのは最終メッセージだけ。必要な数値は最終報告に書かせる |
| ツールを絞る | `allowedTools` から外す | `tools` か `disallowedTools`。`allowedTools` は自動承認の設定 |
| ループが上限で止まった後の必須処理 | プロンプトで「必ずやれ」 | ループの外のアプリのコードで確認・実行する |
| 下流が全員成功なのに成果物が偏る | 検索クエリを増やす | 分解の幅を直し、欠けた題だけ再委任する |
| 時刻形式がばらつく | モデルに翻訳させる | 実行後、読む前の `PostToolUse` で揃える |
| 閾値を超える返金 | プロンプトに禁止を書くだけ | 実行前に遮断し、APIを叩かない |
| レビュー | 14ファイルを1つのパス | 面が見えているならファイル単位のあと横断 |
| 調査 | 最初のディレクトリだけを手順に固定 | 発見のたびに計画を更新する |
| 昨日の会話 | 古いツール結果を、変更を伝えずに再開 | 差分が小さいなら名指しで再開。写しが古いなら結論だけ新規。案の比較はフォーク |

> [!TIP]
> 一人で足りる仕事は分けない。分けるのは、入力が長い、ツールの集合が違う、失敗が目的の一部だけ、のどれかがあるとき。副作用の順序は委任ではなく、同じハーネスのゲートに置く。

## 2. ツールとMCP（[第2章](02-ツール設計とMCP統合.md)）

| 場面 | ✕ 選ばない | ○ 選ぶ |
| --- | --- | --- |
| 似たツールの取り違え | 例を20件、正規表現の前処理、即統合 | 説明に入力、例、端、使わない場合。キーワードの常時指示を消す |
| 改名 | 名前だけ変える | 名前と説明を一緒に変える |
| 失敗 | 「失敗しました」の一文 | `isError`、種別、再試行可否、人に読める文。詳細は別欄 |
| ゼロ件 | タイムアウトと同じ空 | 成功の空。タイムアウトは失敗の構造 |
| 一時的な失敗 | モデルに同じ引数を繰り返させる | 子の中で短く再試行し、解けないものだけ親へ |
| ツールの数 | 18個を1つの役割に渡す | 4〜5個。頻出で狭い確認だけ横断させる |
| 抽出なのに文章が返る | `auto` のまま | 種が不明なら `any`。先頭の1段だけ名前を強制し、成功したら戻す |
| 共有のMCP | トークンをリポジトリに書く | `.mcp.json` には環境変数の参照だけ |
| 個人の実験 | `~/.claude/CLAUDE.md` にサーバーを書く | ローカルスコープ（既定）で追加し `~/.claude.json` に保存。終わったら外す |
| ツールの中で外部 API が 503 | JSON-RPC のプロトコルエラー | `isError: true` のツール実行エラー。モデルが対処を選べる |
| 毎回同じ順で呼ぶ2つの API | 説明に「続けて呼べ」と書く | 1つのツールにまとめる（判断が必要な手順はまとめない） |
| 何があるか | 検索ツールの連打 | リソース。操作はツール |
| 呼び出し元を探す | 全 Read、Glob | Grep。パスは Glob。一意なら Edit。駄目なら Read して Write |

## 3. 設定とワークフロー（[第3章](03-Claude-Codeの設定とワークフロー.md)）

| 場面 | ✕ 選ばない | ○ 選ぶ |
| --- | --- | --- |
| 同僚に届かない指示 | ホームのファイルに足す | プロジェクトの `CLAUDE.md`。読み込まれたかは `/context`（`/memory` は一覧と編集） |
| 既定の指示を残して足したい | `--system-prompt` | `--append-system-prompt`。自動読み込みを省くなら `--bare` |
| 必ず走らせたい整形 | `CLAUDE.md` に書く | `PostToolUse` フック（matcher `Edit\|Write`） |
| 散らばったテストの規約 | ディレクトリごとに複製、モデルに節を選ばせる | `.claude/rules/` の `paths` |
| 全員の `/review` | ホームのスキル、指示ファイルの中だけ | `.claude/skills/review/SKILL.md`（旧 `.claude/commands/` も同じ扱い） |
| 常に守る規約 | スキルに閉じる | `CLAUDE.md` か、パスが一致したルール |
| 長い探索 | 本会話にログを貼る | `context: fork`。戻すのはファイル名と判断 |
| スキル中のシェル | 調査スキルに残す | 読み取りは Read、Grep、Glob。適用は別スキルでフォークしない |
| 数十ファイルの再編 | 直接実行で境界を後から決める | プランモード。承認したプランを次の実行の文脈に残す |
| 1行が特定できている欠陥 | プランモード | 直接実行 |
| ぶれる変換 | 「堅く」 | 端を含む入出力を2〜3個。判定は先に置いたテスト |
| 影響し合う修正 | 別メッセージ | 1通にまとめる。独立なものは順に |
| パイプラインが入力待ち | 標準入力を捨てる | `-p`。指摘は json とスキーマ。再レビューは新規と未対応だけ |
| レビュー担当 | コードを書いた会話 | 差分と基準だけを渡した別プロセス |

## 4. 基準、スキーマ、バッチ（[第4章](04-プロンプトエンジニアリングと構造化出力.md)）

| 場面 | ✕ 選ばない | ○ 選ぶ |
| --- | --- | --- |
| 誤検知で信頼が落ちた | 「確信度が高いものだけ」 | 報告と非報告を種類とコード例で定義し、悪い種類は直すあいだ外す |
| 重大度 | 「高」という語だけ | 段階ごとのコード断片。低は報告しない、と書き切る |
| 形式がぶれる | 似た例をたくさん並べる | 関連性があり互いに違う例を2〜4個。理由つき。1つは、情報が無いときの null |
| 見逃しを減らしたい | 「確実なものだけ報告」 | 発見はすべて報告させ、確信度と重大度を付けて後段で絞る |
| 出力が `max_tokens` で切れる | 切れた JSON を補う | 上限を上げる。出力が入力に比例するなら入力を分けて結果をつなぐ |
| JSONの構文 | 「JSONだけ」と文章で頼む | スキーマつきの `tool_use`。strict は構文だけ |
| 文書に無い税額 | 必須欄にして埋めさせる | null を許す。判別不能は `unclear`。未知の分類は `other` |
| 合計が合わない | スキーマを通ったので採用 | 声明と計算を比べ、メッセージを添えて再依頼。ソースが無ければ人手 |
| 再試行の2通目 | プロンプトだけを再実行 | 元の文書、失敗した結果、検証の一文 |
| 夜間の報告 | 同期のまま費用を満額払う | バッチ。失敗だけ新しい `custom_id` で再送 |
| マージ前の危険チェック | バッチへ移し、遅ければ同期に落とす | 最初から同期。バッチに遅延の保証は無く、途中のツール往復もできない |
| 送信間隔 | 「たいてい早い」 | 約束から最大処理時間を引いた残りより短く |
| 14ファイル | 1つのパス、多数決、窓を大きくするだけ | ファイル単位のあと横断。書いた会話ではレビューしない |

## 5. 事実、引き渡し、出典（[第5章](05-コンテキスト管理と信頼性.md)）

| 場面 | ✕ 選ばない | ○ 選ぶ |
| --- | --- | --- |
| 続ける依頼 | 前のターンを省く | 履歴を渡す |
| 金額と期日 | 要約に溶かす | 要約の外の事実ブロックに、毎回先頭へ |
| 40欄のツール結果 | そのまま履歴に積む | 関連欄だけ残してから足す。残す数字は先にブロックへコピー |
| 但し書き | 長い入力の中央だけ | 先頭のブロックにも1行 |
| 「人に代わって」 | 調査してから渡す | 直ちに渡す |
| 範囲内の不満 | 即人へ渡す | 一度解決を申し出、希望が重なったら渡す |
| 方針に書いていない要求 | 複雑そうだから自分で承認 | 方針の空白として渡す |
| 複数の顧客が一致 | それらしい1人を選ぶ | 追加の識別子を尋ねる |
| 検索のタイムアウト | 空の成功、または全体を止める | 種類、試行、部分結果、代替。穴は最終出力に注記 |
| 会話が「典型的なパターン」と言う | そのまま続ける | スクラッチパッド、委任、フェーズの構造、そのあと `/compact` |
| プロセスが落ちた | メモリの進捗を前提にする | マニフェストの次のフェーズから |
| 全体の精度が高い | 人の確認を一括で外す | 文書種と欄の表。高い確信度も層化して測る。閾値はラベルで校正 |
| 2つの出典で数が違う | 新しいほう、または平均 | 両方を出典と日付つきで残す。年が違うだけなら時点の差として別の行。集計方法が違うなら方法も残す |
| 直近しか見ない長い会話 | 大きいウィンドウのモデル、キャッシュ | スライディングウィンドウ |
| 古いツール結果が混ざる再開 | 「古い結果は無視して」と注記 | 新しいセッション＋構造化した要約。現状はツールで取り直す |

## 似た仕組みを、1文で見分ける

- ゲートは「この状態が無ければ実行しない」。`PostToolUse` は「実行した結果を、読む前に揃える」。実行前の遮断は「規則違反の呼び出しを、APIの前で止める」（フックで止めたいときは終了コード `1` ではなく **`2`** を使う）。
- `auto` は文章を許す。`any` はどれかのツールを必須にする。強制は名前を1段だけ固定し、成功したら戻す。
- 再開は、履歴が今も本当なとき。新規への注入は、ツール結果が古いとき。フォークは、同じ起点から案を混ぜずに比べるとき。フォークが分けるのは会話だけで、ファイルは分けない（ファイルを分けるなら `git worktree` / `--worktree`）。
- `allowedTools` は自動承認、`tools`・`disallowedTools` は絞り込み。`--bare` は自動読み込みを省き、サブスクリプションではなく `ANTHROPIC_API_KEY` を使う。
- MCP のツールは モデルが呼ぶ、リソースは アプリが制御して `@` で参照、プロンプトは 利用者が `/` で実行。
- `strict` と構造化出力は形を守る。値の意味・表記・`null` にする条件はプロンプトと検証で扱う。
- プロンプトチェーンは、面が見えているレビュー。動的な分解は、次の問いが途中で生まれる調査。
- コマンドは打って呼ぶ共有手順。スキルは必要なときだけ読む手順。`CLAUDE.md` は常に読む指示。`paths` は編集したファイルにだけ載る規約。
- バッチは、人を待たせずツール往復も要らない仕事。同期は、結果が来るまで次へ進めない仕事。
- 有効な空は、探して無かった。失敗の空は、探せずに終わった。前者は結論、後者は穴。

## 6つの公式シナリオ別チェックポイント（本番はここから4つ出題）

本番試験では、以下の6つの公式シナリオからランダムに4つが出題されます。各シナリオで問われやすい判断を、直前の最終確認としてまとめました。

### Scenario 1: Customer Support Resolution Agent（第1章・第2章・第5章）

| チェック項目 | ✕ 選ばない | ○ 選ぶ |
| --- | --- | --- |
| 返金前の本人確認 | プロンプトで「必ず確認せよ」と指示 | `prerequisite gate`（`PreToolUse` hook）で `get_customer` 済みを強制 |
| 上限を超える返金（例：\$500超） | ツールを実行してからエラーにする | `PreToolUse` hook で API を叩かず遮断し、`escalate_to_human` へ structured handoff |
| 顧客が「人に代わって」と明示 | 先に注文や返金可否を調査してから渡す | 明示の要求は調査より先に直ちに `escalate_to_human` |
| 範囲内の不満・苦情 | 即座に人へ渡す | 一度解決を申し出て（FCR）、引き継ぎの選択肢も示し、希望が重なったら渡す |
| 複数顧客が一致したとき | 一番それらしい1人を推測して進む | 処理を止め、追加の識別子を顧客に尋ねる |
| 長い会話の金額・注文番号 | 要約の中に溶かす | 要約の外の事実ブロック（case facts）として毎回先頭に保持 |

### Scenario 2: Code Generation with Claude Code（第3章・第5章）

| チェック項目 | ✕ 選ばない | ○ 選ぶ |
| --- | --- | --- |
| 規約・標準の置き場所 | 個人の `~/.claude/CLAUDE.md` | リポジトリの `CLAUDE.md`（または `.claude/CLAUDE.md`）。個人用は `CLAUDE.local.md` |
| テストなど特定ファイル種別の規約 | ディレクトリごとに `CLAUDE.md` を複製 | `.claude/rules/` に YAML frontmatter の `paths`（glob）を指定 |
| 着手方法の選択 | 大規模変更を直接実行／1行修正を plan mode | 大規模・複数ファイル・複数案は plan mode。1箇所の明確な修正は direct execution |
| 広い探索によるコンテキスト圧迫 | 本会話で全ログを出力 | `Explore` subagent やスキルの `context: fork` で隔離し、ファイル名と結論だけ戻す |
| フォーマッタや編集禁止の強制 | `CLAUDE.md` に強い表現で書く | `PostToolUse` hook（matcher `Edit\|Write`）や権限ルール（`deny`）で決定的に強制 |

### Scenario 3: Multi-Agent Research System（第1章・第2章・第5章）

| チェック項目 | ✕ 選ばない | ○ 選ぶ |
| --- | --- | --- |
| subagent 間の連携と履歴 | subagent が親の履歴を自動継承する前提 | 継承しない。coordinator 経由で本文と出典をプロンプトに明示して渡す |
| 並列実行の仕方 | 依存関係のある作業を同時に投げる | 依存のない作業だけ、1回の coordinator 応答で複数の `Task`（Agent）ツールを呼ぶ |
| エラーと空結果の扱い | タイムアウトと 0件を同じ空配列で返す | `errorCategory` と `isRetryable` を返し、`valid empty result` と失敗を分ける |
| 統計数値の矛盾・時点差 | 新しいほうや平均に潰す | 両方の出典（URL/文書名/抜粋）と発行日を構造化して残し、未調査（coverage gap）も明記 |
| 長時間探索の中断対策 | メモリ上の履歴だけを頼りに `/compact` | scratchpad ファイルと manifest に書き出してから `/compact`。再開は manifest 次フェーズから |

### Scenario 4: Developer Productivity with Claude（第2章・第3章・第1章）

| チェック項目 | ✕ 選ばない | ○ 選ぶ |
| --- | --- | --- |
| ツール数と重複の整理 | 18個を全部渡す／すぐ1ツールに統合 | 役割ごとに 4〜5個へ絞り、境界（`description` に形式・例・使わない場合）を明確化 |
| 組み込みツールの使い分け | パス探しに `Grep`／中身検索に `Glob` | 中身は `Grep`、パスは `Glob`、一意な修正は `Edit`（非一意なら `Read` + `Write`） |
| MCP の共有と個人設定 | 秘密トークンを `.mcp.json` に直書き | 共有は `.mcp.json`（`${VAR}` 参照）、個人実験は `~/.claude.json` |
| MCP プリミティブの使い分け | カタログ一覧を `Tool` として毎回積む | 読むだけのカタログは `Resources`、操作は `Tools`、利用者テンプレートは `Prompts` |
| 昨日の作業の再開方法 | ツール結果が古いのにそのまま `--resume` | 履歴が正しければ `--resume`＋変更ファイル名指し。古ければ構造化要約で新規。比較は `fork_session` |

### Scenario 5: Claude Code for Continuous Integration（第3章・第4章）

| チェック項目 | ✕ 選ばない | ○ 選ぶ |
| --- | --- | --- |
| CI からの非対話実行と出力 | 対話モードのままパイプで渡す | `claude -p`＋`--output-format json`＋`--json-schema`（結果は `.structured_output`）。再現性重視は `--bare`＋`ANTHROPIC_API_KEY` |
| レビュー担当の分離 | コードを書いた同じセッションで自己レビュー | 生成時の推論を持たない**独立した別インスタンス**でレビュー |
| 多数ファイル（例：14件）のレビュー | 1回のプロンプトに全ファイルを渡す | ファイル単位のローカルパス → 横断統合パスの順に分けて注意の偏りを防ぐ |
| 誤検知の抑制と重複防止 | 「確信度が高いものだけ」と書く | 報告対象・非対象と severity をコード例で定義。前回指摘と既存テストを渡して重複防止 |
| GitHub 連携設定 | `REVIEW.md` を PR の変更ブランチから読む想定 | `REVIEW.md` はベースブランチから読まれる。Actions は `anthropics/claude-code-action@v1`（`id-token: write`） |

### Scenario 6: Structured Data Extraction（第4章・第5章）

| チェック項目 | ✕ 選ばない | ○ 選ぶ |
| --- | --- | --- |
| JSON 構文と意味の検証 | 文章で「JSON だけ返して」と頼む | `tool_use` + JSON Schema で構文固定。意味（`calculated_total` vs `stated_total`）はアプリ側で検証 |
| 文書に無い情報・未知の分類 | 全項目を `required` にして埋めさせる | 無い可能性の欄は `nullable`、判別不能は `unclear`、未知分類は `other`＋詳細文字列 |
| 検証失敗時の再試行 | 同じプロンプトをそのまま再送 | 元の文書・失敗出力・検証エラーメッセージを添えて再試行（情報が文書に無ければ再試行しない） |
| 出力形式や境界の安定化 | 似た例を大量に並べる | 理由付きの few-shot 例を 2〜4個（`null` の例を含む） |
| 同期 API vs Batch API | マージ前チェックに Batch API を使う | 即時性が必要なら同期 API。夜間大量処理・ツール往復不要なら Message Batches API（50%割引・最大24時間・`custom_id`） |
| 精度評価と閾値調整 | 全体の平均精度だけで人の確認を外す | 文書種別・項目（field）単位で評価し、ラベル付き検証データで確信度閾値を校正 |
