# 用語集

CCDV-P（Claude Certified Developer – Professional）の試験範囲で頻出する専門用語を分野別に整理しました。「ひとことで」で意味を掴み、「まちがえやすい点」で本番試験のひっかけ選択肢を見抜くポイントを確認してください。

## 第1章 高度なエージェントアーキテクチャとオーケストレーション

| 用語 | ひとことで | まちがえやすい点 |
| --- | --- | --- |
| スーパーバイザー／ワーカー階層 | 親が分解・委任・集約を担い、子が個別タスクを実行する構成 | ワーカーは親の会話履歴を自動共有しない。必要な前提は親が明示する |
| コンテキスト分離 | サブエージェントごとに独立した会話を持たせる境界 | 長大なツール生ログを親に返すと、親のコンテキストまで汚染される |
| Human-in-the-Loop (HITL) | 不可逆・高リスク操作の前に人間の承認を挟む制御 | プロンプトで「確認してから実行」と書くだけでは決定論的に止まらない |
| チェックポイント | 実行途中の状態・完了ステップを外部ストアに記録する仕組み | 会話履歴やメモリだけに依存するとプロセス再起動やモデル更新で失われる |
| べき等性キー (Idempotency Key) | 再開・再試行時に同じ副作用が二重実行されるのを防ぐ一意識別子 | チェックポイント再開とセットで使わないと二重課金・二重送信が起きる |
| ワークフロー型 vs エージェント型 | 事前定義の決定論的経路 vs モデルが動的に手を選ぶ自律ループ | 定型比率が高い業務を自律エージェントのままにするとコストと失敗率が増える |
| Claude Managed Agents | Anthropic がホストするサンドボックス・状態管理・セッション永続化基盤 | セルフホストサンドボックスも選択可能。自前ハーネス構築の手間を省く |
| Context Compaction | 古い会話をモデルの要約に置き換えて継続する機能（`compact_20260112` 等） | 要約から漏れた数値・ID は消えるため、重要事実は外部メモリに逃がす |
| Context Editing | 古い `tool_result` や `thinking` をルールで削除する API 機能 | キャッシュ参照後に API 側で処理されるため、キャッシュプレフィックスを壊しにくい |
| `tool_search` / `defer_loading` | 大規模ツールカタログを初期コンテキスト外に置き、必要時に検索・読込する手法 | 100個のツールを毎回全定義すると TTFT 悪化・コスト増・選択精度低下を招く |
| `betaZodTool` / `toolRunner` | TypeScript SDK ベータ版のツール定義・自動実行ヘルパー（Zod 3.25.0 以降が必要） | `while` ループや JSON スキーマ手書きを省けるが、Zod バージョン要件に注意 |
| Skills / Plugins | 手順を `SKILL.md` で共有する単位 / Skills・フック・MCP 等をまとめた配布パッケージ | サブエージェントは親のスキルを自動継承せず、組み込みエージェントはスキル不可 |

## 第2章 本番環境の統合・信頼性・知識グラウンディング

| 用語 | ひとことで | まちがえやすい点 |
| --- | --- | --- |
| 指数バックオフ＋ジッター | 再試行間隔を指数的に延ばし乱数を足す手法 | `429` / `529` に有効。`max_tokens` や `refusal` に無差別適用してはいけない |
| サーキットブレーカー | 下流障害時に回路を開いて呼び出しを止め、即フォールバックする仕組み | 障害中にリトライを増やし続けると連鎖障害を悪化させる |
| `stop_reason: "max_tokens"` | 出力トークン上限到達による切断 | 同じ入力でリトライしても同じ場所で切れる。上限引き上げや分割で対処する |
| `stop_reason: "refusal"` | 安全性ポリシーによる応答拒否 | 別モデルへ無差別リトライせず、安全性の専用処理経路へ回す |
| バックプレッシャー | 下流能力を超えた流入をキュー制限や `429` で上流へ押し返す制御 | 無制限キューはメモリ枯渇とタイムアウト連鎖を招く |
| Message Batches API | 同期比 50% 割引の非同期一括処理 API（最大24時間） | 遅延保証がなく途中のツール往復も不可。リアルタイム対話には使えない |
| Streamable HTTP | リモート MCP で推奨される HTTP ベース通信方式 | ローカル stdio と違い、OAuth 2.1 等の認証とゲートウェイ統制が必須 |
| ハイブリッド検索 | BM25（キーワード）＋ベクトル検索の組み合わせ | 固有名詞・エラーコードの取得漏れはベクトル単独では防げない |
| リランキング (Reranking) | 検索候補をクロスエンコーダ等で精査して上位に並べ替える処理 | 検索結果がトップ20にあるのにトップ5に入らない（順位不備）に効く |
| `web_search_20260209` | Anthropic ホストのサーバー側ウェブ検索ツール（動的フィルタリング対応） | `allowed_domains` は `https://` なし、`pause_turn` 時は同じ `tools` で再送する |

## 第3章 オブザーバビリティと本番環境のモニタリング

| 用語 | ひとことで | まちがえやすい点 |
| --- | --- | --- |
| 分散トレース | 親・子・LLM・ツール・検索を親子スパンで紐づける記録 | アプリ全体の応答時間だけでは、どのターン・どのツールが遅いか分からない |
| ZDR (Zero Data Retention) | プロバイダー側にプロンプト・応答を残さないデータ保持制限 | ZDR 下でもトークン数・`stop_reason`・版数等のメタデータは記録可能 |
| SLI / SLO | サービスの定量指標（TTFT、成功率、拒否率等）とその目標値 | HTTP 200 率だけでは「回答がデタラメ」な品質障害を見逃す |
| 品質ドリフト | モデル更新や入力分布変化により、エラーなしで品質が徐々に悪化すること | モデル ID・プロンプト版数ごとに指標をスライスして検知する |
| テールサンプリング | 完了後の結果を見て保存を決める方式（エラー・異常は 100% 保存） | 一律低率のヘッドサンプリングは稀な重大障害を取りこぼす |
| 障害コホート分析 | 失敗トレースを属性（版数・ツール・テナント等）で集計し偏りを特定する分析 | 個別トレースの目視だけではシステム全体の支配的な原因が見えない |
| Compliance API | 会話コンテンツ・監査ログ・アクティビティフィードを保持する監査連携 API | Primary Owner がメンバー利用開始前に有効化必須（後からオンでも空白は埋まらない） |
| コントロールバンド (`bands.yaml`) | 過去30日平均と `σ`・ウェスタン・エレクトリック・ルールで段階検知する監視枠 | `1sigma` はログのみ、5回中4回 `1σ` 超えや8回連続平均超えは `2σ` 扱い |
| Analytics API / Spend Limits API | 利用量チャージバック用 API / 組織やロールの支出上限設定用 API | 支出上限の設定は Analytics API ではなく Spend Limits API を使う |

## 第4章 高度なデバッグとインシデント対応

| 用語 | ひとことで | まちがえやすい点 |
| --- | --- | --- |
| 4層の切り分け | 障害を「モデル出力」「ハーネス」「ツール」「データ」のどこかに特定すること | ツールの空配列やハーネスの履歴戻し忘れを「モデルのせい」にしない |
| トリアージ | 影響範囲・重大度・緊急度を素早く判定すること | 原因の完全特定より先に、影響拡大を止める緩和・ロールバックを優先する |
| ポストモーテム | 障害のタイムライン・原因・恒久対策をまとめる振り返り（Blameless） | 書いて終わりにせず、回帰評価テストと監視アラートへ必ず反映する |

## 第5章 評価エンジニアリングと品質保証

| 用語 | ひとことで | まちがえやすい点 |
| --- | --- | --- |
| ゴールデンセット | 期待出力や基準が確定した厳選テストセット | 同じセットを使い続けると「飽和」や「汚染」が起き、識別力を失う |
| LLM-as-judge | LLM を使って出力品質を自動採点する手法 | 人間ラベルでキャリブレーションするまでリリースゲート権限を与えない |
| 位置バイアス (Position Bias) | ペア比較で先頭（または末尾）の回答を無意識に選好する偏り | 提示順序のランダム化（または入れ替え比較）で抑える |
| 評価者間信頼性 | 人間とジャッジ（または人間同士）の判定一致度（Cohen's κ 等） | 一致度が低いまましきい値を下げると、不良プロンプトが素通りする |
| ジャッジのドリフト | ジャッジ用モデルの更新等により採点基準がズレること | ジャッジモデル版数を固定し、更新時は人間ラベルで再校正する |

## 第6章 大規模環境でのコストとレイテンシの最適化

| 用語 | ひとことで | まちがえやすい点 |
| --- | --- | --- |
| モデルルーティング / カスケード | 難易度に応じた事前振分 / 小型モデルから上位モデルへの段階的昇格 | すべてを最上位モデルで処理するとコストが破綻する |
| Prompt Caching | 先頭プレフィックスの一致による入力トークン再利用 | 先頭付近に動的値（時刻・ID）を入れるとキャッシュが毎回無効化される |
| TTFT vs E2E レイテンシ | 初回トークンまでの時間 vs 全処理完了までの時間 | ストリーミングは TTFT に効くが、直列ツール待ちを含む E2E は並列化が効く |
| `output_config.effort` | 推論の深さと出力トークン量を制御するパラメータ（`low`〜`max`） | 簡単なサブエージェントにデフォルト `high` を使うと過剰な思考で遅延する |
| アダプティブ思考 / `Ultracode` | Claude Opus 5 の動的思考機能 / `xhigh` で複数エージェントへ動的分散するセッション設定 | `effort` は `thinking` 外の `output_config` に置く。`Ultracode` はエフォートレベルではない |
| Programmatic Tool Calling | `code_execution_20260120` でコンテナ内スクリプトがツール結果を処理し要約だけ返す手法 | `strict: true`、`disable_parallel_tool_use`、`tool_choice` 強制、`Haiku 4.5` は非対応 |

## 第7章 ランタイムガードレールと本番環境のセキュリティ

| 用語 | ひとことで | まちがえやすい点 |
| --- | --- | --- |
| 決定論的強制 | モデルの外部（フック・許可リスト・ゲート）で確実に遮断する制御 | 強いシステムプロンプトや `effort` 低下は強制力のある境界ではない |
| 高リスクな3要素 | プライベートデータ ＋ 信頼できない入力 ＋ 外部通信経路の同時保有 | 1つでも遮断するか、外部通信に許可リスト／承認ゲートを強制する |
| 間接プロンプトインジェクション | チケット・Web・RAG 文書などの外部データに悪意ある指示を混ぜる攻撃 | 「外部指示を無視せよ」というプロンプトだけでは防げない |
| ツール／メモリポイズニング | ツール説明文や永続メモリに悪意ある指示を潜ませる攻撃 | 署名・許可リスト・変更検知でサプライチェーンを守る |
| ワークロード ID フェデレーション | 静的 API キーの代わりに OIDC 等で短期トークンを動的発行する仕組み | 長期固定キーをコンテナや Git に置かない |
| フック終了コード `2` / `SessionStart` | `2`＝ブロック＋stderr フィードバック、`1`＝非ブロック。`compact` 後の再注入は `SessionStart` | 終了コード `1` ではブロックされない。`PostCompact` ではなく `SessionStart(compact)` を使う |
| EMA / Claude Tag / Agent Proxy | IdP 連動コネクタ認証 / Slack マルチプレイヤーエージェント / 外部通信時の認証注入プロキシ | Claude Tag は ZDR・CMEK・ローカル HIPAA 組織では利用不可。資格情報はサンドボックスに届かない |

## 第8章 ソフトウェア提供のためのエージェントフリート運用

| 用語 | ひとことで | まちがえやすい点 |
| --- | --- | --- |
| `git worktree` 分離 | 並列エージェントごとに独立した作業ディレクトリとブランチを与える構成 | 会話のフォーク（`fork_session`）はファイルシステムを分離しない |
| シャドーモード | AI レビューを実行・計測するが、マージはブロックしない試験運用段階 | 人間レビューとのキャリブレーション前に必須ゲートにしてはいけない |
| 無人実行 (Headless) | CI やスケジュールで `claude -p` 等を使い非対話で実行する形態 | ターン上限・コスト上限・Draft PR 制限・人間エスカレーションが必須 |
| 管理設定 (Managed Settings) | 組織管理者が強制適用し、個人設定で上書きできないポリシー | 個人設定任せにすると MCP 許可リストや ZDR 要件が守られない |
| `--bare` フラグ / `.worktreeinclude` | CI 向けに `CLAUDE.md`・フック・MCP 自動検出をスキップするフラグ / worktree へ複製する除外ファイル一覧 | 設定評価スイートで `--bare` を使うと評価対象が読まれない。CI 実行時は `ANTHROPIC_API_KEY` 必須 |
| `REVIEW.md` / マネージド Code Review | PR レビュー基準（`Important` / `Nit`）定義 / インラインコメント専用（承認・ブロックなし）のレビュー機能 | 修正プッシュや `@claude` 実装・定期実行には `claude-code-action@v1` を使う |
