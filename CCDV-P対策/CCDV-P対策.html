本番環境で Claude を運用する8つの技能

Claude Certified Developer – Professional (CCDV-P) の対策教材です。単なるプロトタイプやチャットボットの構築にとどまらず、本番環境で大規模に稼働する Claude アプリケーションとエージェントの 信頼性・品質・コスト・安全性・フリート運用 に責任を持つエンジニア向けの知識を体系化しています。

読み終えると、次の8つの領域で実務的かつ試験基準に沿った判断ができるようになります。

  • マルチエージェントの障害分離、状態永続化、コンテキストとメモリの最適化を設計する
  • 障害種別に応じたリトライ／フォールバック、レート制限、MCP 運用、大規模検索を設計する
  • 分散トレース、ZDR 下のログ設計、SLI/SLO、大規模トレースのコホート分析を実装する
  • マルチターン／マルチエージェントの非決定的な障害を切り分け、インシデント対応とポストモーテムを主導する
  • ゴールデンセット、CI/CD 評価ゲート、キャリブレーション済み LLM-as-judge、オンライン評価を構築する
  • モデルルーティング、Prompt Caching、Batch API、ストリーミング、output_config.effort でコストとレイテンシを最適化する
  • 多層ランタイムガードレール、敵対的入力（プロンプトインジェクション等）への防御、ID・シークレット・監査を実装する
  • 並列コーディングエージェント、AI コードレビュー、無人実行、組織ガバナンスを運用する

本試験で繰り返し問われる5つの判断軸

  1. 失敗の種類を切り分ける：レート制限・長さ超過・安全性拒否・検索ミス・ツール故障は原因が異なるため、単一の雑なリトライやプロンプト修正で済ませない。
  2. プロンプトに頼らず決定論的に強制する：セキュリティ境界、不可逆な操作、順序制約はモデルの「お願い」ではなく、フック・ゲート・権限・サンドボックスで封じる。
  3. 測定とキャリブレーションが先：LLM-as-judge も SLO も、人間のラベルや実際のトレースに照らして校正されるまではゲート権限を与えない。
  4. コンテキストとキャッシュを資産として設計する：長いセッションでは Compaction / Editing・外部メモリ・tool_search を組み合わせ、キャッシュプレフィックスを壊さない。
  5. 自動化を段階的に信頼する：AI コードレビューや自律エージェントは、シャドーモード → キャリブレーション → 人間による承認ゲート（HITL）の順で権限を広げる。

第1章 高度なエージェントアーキテクチャとオーケストレーション（配点 17%）

💡 ヒント

この章のたとえ：大規模プロジェクトの「プロジェクトマネージャー」と「各専門チーム」

1人の担当者に全工程と全資料を抱えさせると、机（コンテキストウィンドウ）がパンクし、停電（プロセス再起動）が起きれば最初からやり直しになります。本番のエージェント運用では、仕事を適切に分割して独立した作業室（コンテキスト分離）で動かし、進捗を日誌（チェックポイント／永続メモリ）に刻み、要所だけ承認（Human-in-the-Loop）を挟む設計が求められます。

この章のゴール

  • 本番環境のマルチエージェント設計で、障害分離・通信境界・承認フローを正しく構成できる。
  • 中断・再起動・モデル変更に耐えるセッション永続化とチェックポイント設計ができる。
  • コスト・信頼性・品質データに基づき、ワークフロー型とエージェント型の移行、およびハーネス選定ができる。
  • コンテキスト上限やコスト上限に近づいた長時間エージェントに対し、Compaction・Context Editing・永続メモリ・キャッシュ維持・大規模ツールカタログ管理を適切に組み合わせられる。

要点3つ

  1. エージェント間の委任はコンテキスト分離の境界になる。 サブエージェントは親の会話履歴を自動共有しないため、必要な前提・出典・出力形式を明示して渡し、障害もサブエージェント単位で封じ込める。
  2. 長時間稼働エージェントの命綱は「外出しした状態」である。 メモリや会話履歴だけに状態を置かず、チェックポイント・構造化状態・セッション永続化によって、中断やモデル更新後も安全に再開できるようにする。
  3. コンテキストは「要約・削除・外出し・キャッシュ維持」の4手で守る。 Context Compaction（要約）、Context Editing（古いツール結果・思考ブロックの除去）、永続メモリ（ファイル／DB）、tool_search（大規模ツールの遅延ロード）を使い分け、途中の指示変更でキャッシュプレフィックスを壊さない。

本編

1-1 マルチエージェントのオーケストレーション

本番のマルチエージェントでは、「何人でどう分けるか」だけでなく 「どこで失敗が止まるか（障害の封じ込め）」 を設計します。

パターン適した場面注意点・障害モード
スーパーバイザー／ワーカー階層複合タスクの分解・進捗管理・結果統合が必要スーパーバイザーがボトルネック化しやすい。ワーカーの途中経過は親に自動共有されない
並列サブエージェントディスパッチ互いに依存しない調査・ファイル処理・評価の同時実行依存関係のあるタスクを並列化すると不整合が起きる。個別ワーカーの部分失敗を許容する集約設計が必要
エージェント間直接通信（メッシュ）対等なピア同士の交渉・反復レビュー循環呼び出し（無限ループ）や状態発散のリスクが高い。本番ではスーパーバイザー経由のハブ＆スポークが原則

コンテキスト分離と委任の境界

  • なぜ分離するのか: 大量の検索結果やログを1つのコンテキストに積むと「コンテキスト汚染（Context Rot）」が起き、モデルの判断精度が低下する。
  • 組み込みサブエージェントの使い分け:
    • 汎用サブエージェント: 調査と実行の両方を要する複数ステップのタスク向け。
    • Explore: コードベースの高速な検索・ナビゲーション向け。
    • Plan: プランモード中にプラン提示前のコードベース調査・分析に使用。
  • 委任の判断ルール: 「中間作業の内容がメインスレッドにとって重要か？」で切り分ける。途中経過を見て反応する必要があるならメインスレッドで実行し、最終結果と要約だけが必要ならサブエージェントへ委任する。
  • 効果的なサブエージェント設計の4本柱:
    • 具体的な description: メインエージェントのシステムプロンプトに全サブエージェントの名前と説明が含まれ、いつ起動するかだけでなく親が書く入力プロンプトの内容も形作る。
    • 構造化された出力フォーマット: システムプロンプトで出力形式（例：概要／重大な問題／主要な問題／軽微な問題／推奨事項／承認ステータス）を定義し、自然な停止ポイントを作って迷走を防ぐ。
    • 障害の報告セクション: 出力に「遭遇した障害」を含め、セットアップ問題・回避策・問題のある依存関係を返させてメインスレッドでの再発見を防ぐ。
    • 最小限のツールアクセス制限: リサーチ／読み取り専用は Glob, Grep, Read のみ、コードレビュアーは Bash（git diff 用）を追加し Edit/Write は外す、変更エージェントのみ Edit, Write を付与する。
  • 避けるべき3つのアンチパターン:
    • 専門家を名乗らせるペルソナ付与: 「あなたは Python の専門家です」のような指定は実質的な能力を付加しないため無意味。
    • 逐次パイプラインの分割: 再現 → デバッグ → 修正のように各ステップが前の発見に依存する作業を分割すると、引き継ぎで情報が失われる。
    • テストランナーとしての委任: 失敗時は完全な出力が必要なのに要約しか返らないと診断できず、検証では全構成中最も成績が悪い。
  • 承認フロー (HITL): 返金実行、本番 DB 更新、外部メール送信などの高リスク操作は、ワーカーに自律実行させず、実行前に一時停止（suspend）して人間の承認を待つ。
📌 重要

ワーカーの1つがタイムアウトやエラーで落ちても、スーパーバイザー全体がクラッシュしないよう、構造化されたエラーを返して「部分的成功の継続」または「該当タスクのみ再委任」できる設計にする。

1-3 大規模環境でのアーキテクチャの選択

「すべてを自律エージェントにする」のは本番では過剰設計になりがちです。本番のコスト・信頼性・品質データに基づいて ワークフロー型 と エージェント型 を適切に選び、必要に応じて移行します。

比較軸ワークフロー型（決定論的パイプライン）エージェント型（自律ループ）
手順の予測可能性ステップが事前に決まっている（抽出→検証→保存など）入力や途中結果に応じて次の手が動的に変わる
コストとレイテンシ予測しやすく、最小限の呼び出しで済むステップ数が変動し、コスト・レイテンシの上振れがある
信頼性とテスト各ノードを単体テストしやすく、SLA を守りやすい非決定的な経路をとるため、評価とガードレールが必須
移行の判断基準エージェントのトレースを分析し、80%以上が同じ固定経路を辿っているなら ワークフロー型へ切り出して固定化 するワークフローの分岐が爆発し、例外処理がコードで書ききれなくなったら エージェント型へ移行 する

Claude Managed AgentsAnthropic がホストする分離コンテナ（FS・bash・ウェブ検索）、セッション永続化、メモリ、イベントストリーム配信を提供（全 API アカウントでデフォルト有効）長時間自律タスクや並列セッションのインフラ構築・保守コストを削減したい場合

Managed Agents の4プリミティブとイベントストリーム順序

Python SDK 等で Managed Agents を構築する際は、以下の4ステップで組み立てます。

  1. エージェント定義: client.beta.agents.create(name, model, system, tools=[{"type": "agent_toolset_20260401", "default_config": {"enabled": True}}])（実行間で再利用可能）。
  2. 環境作成: client.beta.environments.create(name, config={"type": "cloud", "networking": {"type": "limited"}})。limited は allowed_hosts のみ許可し、unrestricted は事前列挙できない場合のみ使う。
  3. セッション開始: client.beta.sessions.create(agent=agent.id, environment_id=environment.id, title=...)。
  4. ストリーム購読とイベント送信: 必ず client.beta.sessions.events.stream(session_id=...) を先に開いてから client.beta.sessions.events.send(...)（type: "user.message"）を送る（ストリームは開いた後のイベントのみ配信するため）。主要イベントは agent.message、agent.tool_use、session.status_idle（event.stop_reason.type が end_turn か requires_action かを確認）。

1-4 コンテキストとメモリのアーキテクチャ

Claude の知識源は パラメトリックメモリ（重み内の訓練知識）、入力されたコンテキスト（コンテキストスタッフィング）、エージェント的コンテキスト（検索・ツールによる外部取得） の3つです。主力モデルは最大 100万トークン を扱えますが、毎ターン会話全体（前置きされた非表示のシステムプロンプト等も含む）が再送信・再課金されます。そのため、長い会話の終盤での短い質問は新しいセッションで聞くより高コストになることがあります。なお、エフォート設定が高いほど Claude は回答前に積極的に検索・確認を行い、コンテキストが増える代わりに回答品質が向上します。

長時間稼働するエージェントがコンテキスト上限やコスト上限に近づいたとき、以下の4つの手法を組み合わせます。

1. Context Compaction と Context Editing の使い分け

手法仕組み強み注意点
Context Compaction古い会話ターンをモデルの要約に置き換える（サーバーサイド betas=["compact-2026-01-12"]、context_management={"edits": [{"type": "compact_20260112"}]}）会話全体の流れや意図を保ったまま長期間継続できる要約から漏れた数値・ID・制約は失われるため、重要事実は外部メモリへ退避する
Context Editing古い tool_result や thinking ブロックをルールに基づき削除するAPI レベルでトークン数計算前・キャッシュ参照後に適用されるため、プロンプトキャッシュを壊しにくい大量のツール出力が蓄積するワークフローに特に有効
ジャストインタイムコンテキスト全資料を事前読み込みせず、必要時にツール（例：lookup_building_code）で動的取得する初期入力トークンを最小化し、コンテキスト汚染を防ぐ適切なツール description とスキーマ設計が必要

2. キャッシュを損なわずに会話途中で指示を変更する方法

Prompt Caching は プレフィックス完全一致 で機能します。会話の途中で system プロンプトやツール定義を書き換えると、それまでのキャッシュがすべて無効化（Cache Miss）され、コストとレイテンシが急増します。

  • NG: 状況が変わるたびに system プロンプトの文言を書き換える。
  • OK: system プロンプトとツール定義は不変のプレフィックスとして固定し、動的な指示変更や状態更新は 最新の user メッセージ（またはシステム注入ブロック）として末尾に追加 する。

3. 大規模ツールカタログの扱い（tool_search）

MCP サーバーや社内 API が増え、ツール定義が数十〜数百個になると、それだけで数万トークンを消費し、ツール選択の精度も落ちます。

  • すべてのツール定義を毎回コンテキストに載せず、defer_loading と tool_search を用いて、タスクに必要なツールだけをオンデマンドで検索・ロードさせる。

4. 永続メモリ（Persistent Memory）

セッションをまたいで保持すべきユーザーの好み、学習した手順、確定済みの事実（Case Facts）は、コンテキストウィンドウ内ではなく外部のメモリファイル・DB（またはクライアント側でストレージバックエンドを実装する Memory Tool、Claude Code の CLAUDE.md）に保存し、必要なものだけを読み込みます（一時的な数値等は記憶せず都度調べ直します）。

確認問題

問1

ある企業で、自律型エージェントが社内調査からレポート作成までを20ステップかけて実行しています。本番トレースを分析したところ、リクエストの90%は「データ取得 → 正規化 → テンプレート埋め込み」という完全に同じ3段階の経路を辿っており、不要な推論トークンと時折発生する分岐ミスがコストとエラー率を押し上げています。最も適切なアーキテクチャ改善はどれですか。

A. エージェントのモデルをより大型のものに変更し、分岐ミスを減らす B. 90%の定型パターンを予測可能なワークフロー型パイプラインへ切り出し、例外的なケースのみエージェント型にフォールバックさせる C. 各ステップで全会話履歴を保持したまま max_tokens を増やす D. すべてのステップを複数の並列サブエージェントに分割し、メッシュ通信で合意形成させる

解答

B。本番のトレースとコストデータから経路の大半が固定化していることが分かっている場合、決定論的なワークフロー型へ移行することでコスト・レイテンシ・信頼性を大幅に改善できます。

問2

長時間稼働するカスタマーサポート兼調査エージェントで、会話が長くなるにつれてコスト上限に近づいています。このエージェントは各ターンで大きなデータベース検索結果（tool_result）を受け取りますが、数ターン後には古い検索結果の詳細は不要になります。プロンプトキャッシュのヒット率を維持しつつコンテキスト消費を抑えるには、どの組み合わせが最適ですか。

A. 毎回クライアント側で古い user メッセージを手動削除して再送信する B. system プロンプトを毎ターン要約して書き換える C. サーバーサイドの Context Editing（古い tool_result のクリア）を有効にし、確定した顧客・注文の重要事実は外部メモリ／先頭の固定領域外ではなく永続ストアへ保存する D. すべてのツール呼び出しを廃止し、全データベースを system プロンプトに埋め込む

解答

C。Context Editing はキャッシュ参照後に API 側で古い tool_result を整理するためキャッシュプレフィックスを壊しにくく、ツール多用エージェントのコスト・精度を効果的に保てます。A や B はプレフィックスを変えてしまいキャッシュミスを招きます。

問3

複数のサブエージェントが並列で外部 SaaS のチケットを更新する処理で、3つ目のサブエージェントの実行中にネットワーク障害でプロセスが再起動しました。再起動後に安全かつ低コストで処理を完了させる設計はどれですか。

A. プロセス起動時に最初から全3つのサブエージェントを再実行する B. 各サブエージェントの完了状態と成果物をチェックポイントに保存しておき、再起動後は未完了の3つ目のみ再開し、外部更新には冪等性キーを付与する C. サブエージェント間の直接通信で互いの進捗をメモリ上に記憶させる D. 障害が起きた場合は自動的にモデルバージョンをダウングレードして最初からやり直す

解答

B。耐久性のある実行には、チェックポイントによる再開可能性と、再実行時の二重更新を防ぐ冪等性キーの両方が不可欠です。

問4

A. 120個のツール定義を system プロンプトに平文で書き直す B. tool_search（遅延ロード）を導入し、タスクに関連するツールだけを動的にコンテキストへ読み込む C. output_config.effort を max に引き上げる D. 会話の毎ターンでツール定義の順序をランダムにシャッフルする

解答

B。大規模ツールカタログをコンテキストウィンドウの外に置き、必要なときに tool_search で取得することで、入力トークン削減とツール選択精度の向上を両立できます。

問5

稼働中の長時間エージェントで、会話の途中から「本日の出力は必ず英語の箇条書きにすること」という一時的な方針変更を適用したいと考えています。プロンプトキャッシュの効率を損なわない方法はどれですか。

A. リクエストの system パラメータの先頭に新しい指示を挿入する B. system プロンプトとツール定義は変更せず、最新の user メッセージに指示変更を追記する C. すべてのツール定義の description に英語出力の指示を追記する D. 会話履歴をすべて破棄して新規セッションを開始する

解答

B。Prompt Caching は先頭からのプレフィックス一致で判定されるため、system やツール定義を変えるとキャッシュが無効化されます。末尾のメッセージで追加指示を渡すことでキャッシュヒットを維持できます。

問6

Claude Managed Agents の Python SDK を用いて新しいセッションを開始し、最初のユーザーメッセージを送信してエージェントの応答イベントを漏れなく受け取りたいと考えています。正しい実行順序と設計はどれですか。

A. events.send() で user.message を送信したあとに events.stream() を開く B. 先に client.beta.sessions.events.stream(session_id=...) を開いてから、client.beta.sessions.events.send(...) で user.message を送信する C. 環境作成時にすべてのホストを常に networking: {"type": "unrestricted"} に設定する D. 毎回のセッションごとに client.beta.agents.create() で新しいエージェントを作り直す

B。Managed Agents のイベントストリームは開いた後のイベントのみを配信するため、送信前に events.stream() を開く必要があります。環境ネットワークは可能な限り limited（allowed_hosts 指定）にし、エージェント定義は実行間で再利用します。

問7

A. 組み込みの Explore サブエージェントを使えば、親セッションのスキルが自動継承される B. .claude/agents にカスタムサブエージェントを定義し、フロントマターに skills: api-conventions を明示的に列挙する C. システムプロンプトに「あなたは API 設計の専門家です」とペルソナを追記する D. テスト実行と修正の逐次パイプラインを別々のサブエージェントに細かく分割する

第2章 本番環境の統合・信頼性・知識グラウンディング（配点 20%）

💡 ヒント

この章のたとえ：国際空港の「管制塔」と「精密な図書館司書」

飛行機（リクエスト）が急増しても、滑走路が1本だけなら大渋滞します。天候不良（レート制限）なら待機旋回し、機体トラブル（安全性拒否や出力長超過）なら別の滑走路（フォールバックモデル）へそのまま飛ばすのではなく、専用の着陸手順へ振り分けなければなりません。そして図書館司書（検索・グラウンディング）は、曖昧な記憶で答えず、必ず「どの棚のどの資料の何ページか」を添えて回答します。

この章のゴール

  • 停止理由やエラー種別を正確に分類し、適切なリトライ・サーキットブレーカー・モデル／リージョン／プラットフォーム間フォールバックを設計できる。
  • レート制限、トークンスループット、キューイング／バックプレッシャー、Batch API の経済性、マルチテナント分離からボトルネックを特定できる。
  • リモート MCP の認証・バージョン管理・段階的ロールアウト（カナリア／ロールバック）とプロンプト変更管理を運用できる。
  • エージェント型検索と RAG を比較評価し、ハイブリッド検索・リランキング・出典引用・不確実性明示・検索品質の段階的診断ができる。

要点3つ

  1. すべての失敗を同じリトライ／フォールバック経路に流してはならない。 レート制限（429 / 529）は指数バックオフ＋ジッターでリトライし、max_tokens は上限調整や分割、安全性拒否（refusal）は専用処理経路へ分岐させる。
  2. スループット設計は「何が制約か」を見極める。 RPM/ITPM/OTPM のレート制限なのか、同時実行によるトークンスループットなのか、遅延許容できるバッチ経済性なのかを切り分け、キューとバックプレッシャーで保護する。
  3. 知識グラウンディングは「検索品質の4段階」で診断する。 取得漏れ（Recall）、チャンク分断（Chunking）、順位付け（Ranking）、生成時の無視（Synthesis）のどこで落ちたかを特定し、出典引用と不確実性シグナルを強制する。

2-1 Claude サービスの信頼性エンジニアリング

本番環境で最も多い失敗は、原因の異なるエラーをすべて同じリトライやフォールバックモデルへ流してしまうこと です。

プラットフォーム間・リージョン間の差異に注意

ファーストパーティ API（Anthropic API）とクラウドプラットフォーム（Amazon Bedrock / Google Cloud Vertex AI）では、以下の差異があるため単純なフォールバックでは動作が変わることがあります。

  • モデル ID と機能提供時期: 新機能（Context Editing や特定ベータ機能、Prompt Caching の仕様、Batch API の形式）の提供タイミングやパラメータ形式が異なる。
  • リージョン制約とクォータ: クロスリージョン推論（Cross-Region Inference）やプロビジョンドスループット（Provisioned Throughput）の有無、データレジデンシー要件（EU/US/JP 等）。
  • 認証とネットワーク: API キー vs IAM ロール（STS / Workload Identity）。

2-3 本番環境の MCP と変更管理

ローカル開発の stdio MCP から本番のリモート MCP へ移行する際は、運用・セキュリティ・互換性管理が不可欠です。

リモート MCP の本番要件

  • トランスポートと認証: リモートサーバーでは Streamable HTTP を使用し、OAuth 2.1（PKCE / トークン検証・スコープ制限）や mTLS、API ゲートウェイで認証を強制する。静的シークレットの共有やリポジトリ直書きは厳禁。
  • ツールとスキーマのバージョン管理: ツール名や入力スキーマの必須項目追加・型変更は 破壊的変更 となる。バージョン付きエンドポイント（/v1/mcp, /v2/mcp）や後方互換な任意フィールド追加で移行期間を設ける。
  • 動作の破壊的変更に対する移行テスト: ツール出力フォーマットやエラー形式が変わった際、エージェントが誤動作しないか回帰テストを実行する。

CI/CD パイプライン内で Claude Code を非対話実行し、デプロイメントやトリアージに組み込む際は以下の原則を守ります。

  • 段階的導入: まずは読み取り専用の判断ステップ（ビルド失敗のトリアージ、テスト要約、変更履歴作成）から始め、書き込みステップはブランチ保護と PR 経由に限定する。
  • サンドボックスと短命トークン: エージェントジョブは短命・スコープ付きトークンのコンテナでサンドボックス実行し、常設の本番認証情報を持たせない。
  • 環境ごとの MCP サーバー分離: MCP ツール許可ルールは引数を指定できないため、.mcp.json で環境ごと（deploy-dev, deploy-staging, deploy-prod）に別々の MCP サーバーを用意し、ジョブに渡すトークンと --allowedTools で環境分離する。
  • --permission-mode dontAsk: 許可リスト外のツール呼び出しを即座に拒否し、CI ジョブがプロンプト待ちで停止するのを防ぐ。
  • PreToolUse フックによる承認ゲート: 本番環境では release を許可リストから外し、フックが allow を返した場合のみ実行（フェイルクローズ）させる。rollback は事前承認済みランブックとして許可リストに残し、ステージングで定期的に予行演習する。

2-4 大規模な検索と知識グラウンディング

本番アプリケーションで外部知識を参照させる際、エージェント型検索 と RAG の特性を理解して選択・統合します。

手法仕組み強み弱み
RAG (Retrieval-Augmented Generation)事前にチャンク化・埋め込みを行い、クエリ時に検索してコンテキストへ注入低レイテンシ・予測可能なコスト・大規模コーパスに強い固定チャンクで文脈が切れる、複数ホップの探索に弱い
エージェント型検索エージェントが検索・Grep・閲覧ツールを反復呼び出しして探索複雑な多段階推論、最新コード・文書の正確な探索に強いターン数が増えレイテンシ・コストが高くなる
ハイブリッド構成初期候補をハイブリッド検索＋リランキングで絞り、不足時のみエージェントが追加検索速度と精度のバランスが良いパイプラインが複雑になり各段の監視が必要

検索パイプライン設計と障害診断（4段階）

検索に根拠を置くアプリで回答品質が落ちた場合、生成モデルを疑う前にどの段階で失敗したか を切り分けます。

  1. チャンク分断 (Chunking): 見出し・表・文脈が途中で切れており、単独チャンクでは意味が通じない → Contextual Retrieval（各チャンクの埋め込み・BM25 インデックス作成前に、文書全体の文脈を説明する短い前置きを付与する手法）や親子チャンクを採用。
  2. 取得漏れ (Retrieval Recall): 固有名詞や型番がベクトル検索で拾えていない → ハイブリッド検索（Contextual BM25 + ベクトル） を導入。
  3. 順位不備 (Ranking): 正解チャンクがトップ20にはあるがトップ5に入っていない → リランキング（Reranker） を導入。
  4. グラウンディング失敗 (Synthesis): 正解チャンクはコンテキストにあるのにモデルが無視／幻覚を起こす → Citations API や search_result ブロックを用いて文字単位の引用元を強制し、該当情報がない場合の「不明（insufficient_evidence）」出力を設計する。

サーバーツール web_search_20260209 による最新・公式情報のグラウンディング

訓練データにない最新情報や公式標準を検証して回答させる場合は、Claude のサーバーツール web_search_20260209 を tools リストに追加します。

  • クライアント実装不要: サーバーツールのため、クライアント側でハンドラーを書いたり tool_result を返送したりする必要がありません。
  • 動的フィルタリング: Claude 4.6 以降と web_search_20260209 以降の組み合わせではデフォルトで動的フィルタリングが有効になり、関連コンテンツのみがコンテキストウィンドウに届くためトークンを節約できます。
  • ドメイン制限 (allowed_domains): https:// なしの裸ドメイン（サブドメインを含む）を指定し、信頼できる公式情報源のみに検索対象を限定できます。
  • 長時間ターンと応答ブロック: stop_reason: "pause_turn" が返った場合は、レスポンスをアシスタントメッセージとして同じ tools とともに再送して続行します。回答は複数の text ブロックに分かれることがあるため結合して読み取り、web_search_tool_result ブロックから参照元（title, url）を確認します。

まとめ：どう判断するか

状況避ける選択とるべき選択

1つの顧客の大量リクエストで他顧客も 429 になる全テナント共有の単一キューで処理テナント別クォータ・キュー分離・バックプレッシャーを導入

確認問題

問1

本番の Claude 統合システムで、特定のリクエストに対して stop_reason: "max_tokens" が返却されました。ハーネスがこのエラーを「一時的エラー」とみなして別のリージョンの同じモデルに3回リトライした結果、入力と出力のトークンコストが4倍に膨れ上がり、ユーザーには同じ途切れた応答が返されました。根本原因と正しい修正はどれですか。

A. バックオフ時間を30秒に延ばしてリトライする B. stop_reason に応じて分岐し、max_tokens はリトライせずに出力上限の調整や入力分割・継続生成で処理する C. サーキットブレーカーを開いて全トラフィックを停止する D. すべてのリクエストを Message Batches API に切り替える

解答

B。max_tokens はネットワーク障害ではなく出力長上限への到達であり、同じ入力でリトライしても同じ位置で切断されます。停止理由で分岐し、上限引き上げや分割処理に切り替える必要があります。

問2

エンタープライズ向けマルチテナント環境で、ある1社が大量の文書要約ジョブを急激に投入したため、API の ITPM（1分あたり入力トークン数）上限に達し、他の全顧客のリアルタイムチャットまで 429 エラーで遅延しています。優先的に導入すべき対策はどれですか。

A. リトライ回数を無制限にして全員が成功するまで待機させる B. テナント別のクォータとキュー分離、およびバックプレッシャーを導入し、バッチ処理は Message Batches API 等へ分離する C. 全顧客のモデルを最も高価な上位モデルに切り替える D. プロンプトキャッシュを無効化する

解答

B。ノイジーネイバーを防ぐには、テナントごとのクォータ・キュー分離とバックプレッシャーが必須です。さらに遅延許容できる大量要約は Batch API へ分離すると ITPM の競合を緩和できます。

問3

社内規定検索 RAG システムで、特定のエラーコード（例：ERR-9042）に関する質問の正答率が低いことが判明しました。検索ログを調べると、正解文書はインデックスに存在するものの、ベクトル検索の上位10件にすら入っていません。最初に取るべき対策はどれですか。

A. 生成モデルの温度パラメータ（temperature）を下げる B. ベクトル検索にキーワード検索（BM25）を組み合わせたハイブリッド検索とリランキングを導入する C. システムプロンプトに「エラーコードを推測しないこと」と追記する D. チャンクサイズを現在の10倍に大きくする

B。固有名詞や型番・エラーコードは意味ベースのベクトル検索だけでは取りこぼしやすいため、BM25 等のレキシカル検索を組み合わせたハイブリッド検索で取得漏れを防ぎ、リランキングで順位を上げます。

問4

この章のたとえ：飛行機の「ブラックボックス」と「コックピット計器」

飛行機が落ちたあとに「たぶんエンジンの調子が悪かった」では原因を特定できません。各部品のセンサー（分散トレース）、燃料消費（トークンとコストのメトリクス）、計器の異常警告（SLI/SLO とアラート）が必要です。ただし、乗客の個人情報（PII）や機密会話はプライバシー規則（ZDR）に従って保護したうえで記録しなければなりません。

この章のゴール

  • エージェントループとツール呼び出しの分散トレース、コスト、キャッシュ効率を計装できる。
  • ゼロデータ保持（ZDR）などのプライバシー制約下で安全なコンテンツキャプチャを構成できる。
  • LLM サービス特有の SLI / SLO を定義し、品質ドリフト・動作回帰・異常使用を検出するアラートを設計できる。
  • サンプリング戦略、集計、障害コホート分析を用いて大量トレースからシステム全体の問題を定量化できる。

要点3つ

  1. エージェントの観測は「リクエスト単位」ではなく「トレース単位」で行う。 親エージェントからサブエージェント、各ツール呼び出し、検索結果、モデル応答までを親子スパン（Span）で紐づけ、推論とグラウンディングを追跡可能にする。
  2. デバッグ可能性とプライバシー（ZDR / PII）は設計で両立する。 機密データをそのまま平文ログに流さず、構造化イベント・メタデータ・PII リダクション・条件付きサンプリングを組み合わせる。
  3. 平均値（Average）は本番の異常を隠す。 パーセンタイル（p95 / p99）、キャッシュヒット率、モデル更新前後のドリフト、障害コホート分析によって局所的な悪化を炙り出す。

ZDR（ゼロデータ保持）およびプライバシー制約下のログ設計

医療・金融・エンタープライズ環境では、本番ログに生プロンプトや顧客の PII（個人識別情報）を残せないケースが多くあります。

  • 常に記録可能（メタデータ）: トークン数、レイテンシ、モデル名、プロンプトバージョン、stop_reason、ツール名、エラー種別、ハッシュ化されたセッション ID。
  • PII リダクション後に記録: 入力・出力・ツール引数をログパイプラインへ送る前に、正規表現や NER で氏名・メール・カード番号等をマスキングする。
  • ZDR 環境でのコンテンツキャプチャ: プロバイダー側にログが残らないため、障害調査に必要な最小限のデータ（サンプリングされたトレースやエラー時のみ）を自社管理の暗号化・アクセス制御付きストアに一時保持する（またはコンテンツ記録自体をオプトイン／環境変数で制御する）。

コントロールバンドとメトリクスの自律ループ（ステージ6：維持）

人が手動で監視画面を見るだけでなく、決定的な監視スクリプトが異常を検知して Claude をヘッドレス起動し、intent.md を出力して開発パイプラインへ流す「メトリクスのループを閉じる」設計が有効です。

  • bands.yaml とウェスタン・エレクトリック・ルール: 過去30日間の1時間ごとの読み取り値の平均と標準偏差（σ、フラットベースライン対策で MIN_SIGMA = 0.01）で正常帯域を定義します。緩やかなドリフト検知のため、直近5回中4回が 1σ 超え、または 8回連続で平均超え の場合は 2σ 扱い に引き上げます。
  • ティア別アクション:
    • 1sigma: action: log（ログ記録のみ。月720回で偶然1日4回程度発生するため通知しない）
    • 2sigma: action: diagnose（Read,Grep,Bash(gh run view *) 等の読み取り専用ツールで診断）
    • 3sigma: action: propose（routes: [pull_request, runbook:rollback-deploy] のゲート付きルートのみ実行可能）
  • インシデントの回帰防止と Claude Tag 連携: 修正リリース後は再現用 eval JSON をスイートに追加します。また、Slack チャンネルに常駐する Claude Tag（パブリックベータ）と MCP を連携させ、インシデント対応やメトリクス確認、ポストモーテム記録を行うこともできます。

3-3 大規模なトレース分析と支出管理

本番で1日何百万件もリクエストが流れる場合、全トレースの生テキストを保存・目視することは不可能です。

支出の管理（Enterprise 課金とトークンプール制御）

Enterprise 契約はメンバー単位のプラットフォーム料金＋組織全体で共有されるトークンプールで構成されます（セールス支援型は月次後払い、セルフサービス型はクレジット前払いで枯渇すると停止）。自律ステップが多い Cowork や Claude Code は消費量が多くなりやすいため、以下のレバーで上限を動かさずに支出を抑えます。

  • 最も効果的なレバー: 組織／ロールごとのデフォルトモデルをミドルレンジに設定＋デフォルトエフォートを中程度に設定＋定型業務へのエフォート上限設定（多くのユーザーはピッカーを触らないため効果が高い）。
  • コンテキスト設計と定期タスクの見直し: 常にコンテキストに含まれる「プロジェクト」より、オンデマンド読み込みの「スキル」の方がトークン効率に優れます。また、放置されたスケジュールタスクがトークンプールを消費し続けないよう定期的に棚卸しします。
  • 支出レビューの3サーフェス: 定期レビュー用の分析ダッシュボード（Groups ビューあり）、単発質問用の Analytics チャット、財務ツール連携・チャージバック用の Analytics API（Primary Owner がキー発行、グループ別分解可）。なお、利用上限の設定には Spend Limits API を使います。

サンプリング戦略の選択

  • ヘッドサンプリング（一律 1% など）: コストは低いが、発生率 0.1% の重大なエッジケース障害を取りこぼす。
  • テールサンプリング（推奨）: 正常かつ低レイテンシなトレースは 1〜5% に間引き、エラー発生・高レイテンシ（p99超）・refusal・再試行発生・ユーザー低評価 のトレースは 100% 保存 する。

障害コホート分析 (Failure Cohort Analysis)

個々のトレースを1件ずつ眺めるだけでは「全体で何が一番効いているか」が見えません。トレースを集計し、属性別のコホート（集団）で比較します。

  • 例：全体のエラー率は 2% だが、コホート分析すると「特定の mcp_server_version=v2 × language=ja の組み合わせ」だけでエラー率が 35% に跳ね上がっていることを定量的に特定できる。

確認問題

問1

本番環境で稼働中のエージェントシステムにおいて、週末にトークンコストが通常の3倍に跳ね上がりました。HTTP エラー率は変化していません。原因を最も素早く特定するためにダッシュボードで確認すべきメトリクスの組み合わせはどれですか。

A. サーバーの CPU 使用率とディスク I/O B. cache_read_input_tokens / cache_creation_input_tokens（キャッシュヒット率）、1トレースあたりのターン数、tenant_id 別の使用量 C. データベースのコネクションプール数 D. ユーザーのブラウザ種別と OS バージョン

解答

B。HTTP エラーなしでコストが急増する場合、キャッシュ無効化（ヒット率低下）、エージェントのループ回数増加（ターン数増）、特定テナントの異常利用が主な原因です。

問2

金融機関の Claude アプリケーションで、コンプライアンス要件により ZDR（Zero Data Retention）が適用されており、本番の顧客プロンプト平文を一般的なログ基盤に保存できません。しかし、障害発生時の切り分け能力は維持したいと考えています。最も適切な計装方針はどれですか。

A. すべてのロギングとトレースを完全に停止する B. トークン数、レイテンシ、stop_reason、ツール名、エラー種別、プロンプト版数などの構造化メタデータを常時記録し、コンテンツは PII リダクションと厳格なアクセス制御下でエラー時のみ限定キャプチャする C. ZDR を解除して全顧客の生プロンプトを平文で外部 SaaS に送信する D. 開発者のローカル端末に本番トラフィックを複製して表示する

解答

B。プライバシー制約下でも、構造化メタデータによってループ・コスト・ツール障害の大半は診断可能です。コンテンツが必要な場合もリダクションと最小権限のサンプリングで制限します。

問3

1日500万件のリクエストを処理するシステムで、全トレースの保存コストが高すぎるため、一律 1% のヘッドサンプリングを導入しました。しかし、発生率 0.2% の「特定条件でのみ発生するツール引数の破損」が調査できなくなりました。適切な改善策はどれですか。

A. サンプリング率を 0.1% にさらに下げる B. 正常リクエストは低率でサンプリングしつつ、エラー・max_tokens・異常レイテンシ・低評価のトレースを 100% 保存するテールサンプリングへ切り替える C. ログの出力先を標準出力からテキストファイルに変える D. 問題が起きるまで本番環境でデバッグプリントを有効にする

解答

B。ヘッドサンプリングは稀な障害を取りこぼします。結果に基づいて保存対象を選ぶテールサンプリングなら、コストを抑えつつ異常トレースを確実に捕捉できます。

問4

個々の失敗トレースをいくつか確認したところ、すべてツールタイムアウトや出力形式エラーなど別々の症状に見えました。システム全体の根本的な偏りを定量化するために行うべき分析はどれですか。

A. 最も遅かった1件のトレースだけを徹底的に書き直す B. 失敗トレースをモデル版・プロンプト版・ツール名・入力カテゴリなどの属性で集計する障害コホート分析を行う C. すべてのエラーを無視して SLO を緩和する D. ランダムに選んだ成功トレースを10件読む

解答

B。障害コホート分析により、一見バラバラに見える障害が特定のプロンプト版やツール・入力カテゴリに集中していることを定量的に発見できます。

問5

Enterprise 環境で可視性を確保するため Compliance API と保持期間（Retention）を設定する際、正しい仕様と運用判断はどれですか。

A. Compliance API はメンバーが使い始めた後から有効化しても、過去の空白期間の会話が遡って記録される B. Compliance API は Primary Owner がメンバーのアクセス開始前に有効化し、カスタム保持期間の最短は 30日（ゼロ保持オプションはなし）であることを前提に設計する C. 保持期間を短縮しても、過去の履歴はアーカイブ領域に残りいつでも復元できる D. アクティビティフィードとリモートセッショントランスクリプトは、カスタム保持期間を 30日に設定すると 30日で削除される

解答

B。可視性要素はメンバーのアクセス開始前に設定が必須で、後からオンにしても空白期間は埋まりません。カスタム保持期間の最短は 30日（組織全体適用・短縮時は過去履歴が復元不可で消去）で、アクティビティフィードとリモートセッショントランスクリプトは設定にかかわらず 6年間保持されます。

第4章 高度なデバッグとインシデント対応（配点 10%）

💡 ヒント

この章のたとえ：救急外来の「トリアージ」と「原因究明カンファレンス」

患者（本番システム）が急変したとき、いきなり手術（プロンプトの当てずっぽうな修正）を始める前に、まず止血（緩和・ロールバック）を行います。次に、症状が「脳（モデル出力）」「神経伝達（エージェントハーネス）」「手足（ツール）」「カルテ（データ／検索）」のどこから来ているかを証拠に基づいて切り分け、再発防止を検査項目（回帰評価）に組み込みます。

この章のゴール

  • マルチターン、マルチエージェント、非決定的な本番障害の証拠を分析し、発生源（モデル・ハーネス・ツール・データ）を正確に切り分けられる。
  • モデルの拒否（refusal）や検索グラウンディング障害を、システム障害の一種として診断・処理できる。
  • システム停止や品質回帰時のトリアージ、緩和、ロールバック、ステークホルダーへのコミュニケーションを選択できる。
  • インシデントの知見を回帰テスト、モニタリングカバレッジ、ポストモーテムへ確実にフィードバックできる。

要点3つ

  1. 非決定的な障害は「4つの発生源」で切り分ける。 モデルの出力（推論・拒否）、エージェントハーネス（ループ・履歴管理・状態）、ツール（スキーマ・タイムアウト・戻り値）、データ（検索漏れ・陳腐化）を証拠（トレース）で特定する。
  2. インシデント中の最優先は「原因究明」ではなく「止血（緩和・ロールバック）」である。 最新の変更を即座にロールバックするか、トラフィックを安定版・縮退運転へ逃がしてから根本原因を調査する。
  3. 同じインシデントを二度と起こさない「学習ループ」を閉じる。 ポストモーテムで終わらせず、再現ケースを CI/CD の回帰評価スイートに追加し、検知できなかった理由をアラート・SLI に反映する。

本編

4-1 複雑な障害の診断（4層の切り分け）

マルチターンやマルチエージェントの障害は、「モデルのせい」と決めつけると原因を見誤ります。トレースを上から順に追い、入力と出力の境界 で責任を切り分けます。

発生源典型的な証拠（トレース上の兆候）具体的な障害例
1. モデル出力正しいツール結果とプロンプトが渡っているのに、誤った判断や形式違反を返す突然の refusal 増加、指示無視、長いコンテキスト中間部の見落とし（Lost in the Middle）
2. エージェントハーネスモデルの宣言は正しいが、次ターンの入力履歴や状態が壊れているツール結果を履歴に戻し忘れ、サブエージェントへの委任時に必須 ID が欠落、max_turns 到達後の必須処理漏れ
3. ツールモデルの引数は妥当だが、ツール側が異常を返す（または誤解を招く表現）タイムアウト時に空配列 [] を返して「該当なし」と誤認させる、isError: true 未設定、5xx 障害
4. データ / 検索ハーネスもツールも正常だが、渡された情報自体が誤り・不足・古い古い社内規定が上位にヒット、チャンク分断による数値欠落、信頼できない外部文書からの間接インジェクション

障害の一種としての「モデルの拒否」

モデルが stop_reason: "refusal"（または拒否文言）を返したとき、ハーネスがそれを検知できないと、ユーザーに「申し訳ありませんが対応できません」がそのまま返るか、後続パーサーがクラッシュします。

  • 正当な安全拒否なのか、無害な入力に対する 過剰拒否（False Refusal） なのかを分類し、過剰拒否であればシステムプロンプトの表現調整や誤検知ルールの見直しを行います。

4-2 インシデント対応と学習ループ

本番で品質回帰やシステム停止が起きた際、エンジニアは以下の順序で動きます。

インシデント対応の4ステップ

  1. トリアージ (Triage): 影響を受けているテナント、機能、モデル版、プロンプト版を特定し、重大度を確定する。
  2. 緩和とロールバック (Mitigate & Rollback): 原因デプロイ（プロンプト更新・モデル変更・MCP 改修）が直近にあるなら 即座にロールバック する。外部障害ならサーキットブレーカーや縮退運転（軽量機能・人間エスカレーション）へ切り替える。
  3. コミュニケーション (Communicate): 影響範囲・暫定回避策・復旧見込みを関係者と顧客へタイムリーに共有する。
  4. 学習ループへの反映 (Close the Loop):
    • 回帰評価の追加: インシデントを再現するケースをゴールデンセット／CI 評価ゲートへ必ず追加する。
    • モニタリングの拡張: 今回アラートが遅れた、あるいは鳴らなかった理由（例：refusal 率を監視していなかった等）を特定し、SLI/アラートを追加する。
    • ポストモーテム: 個人を責めず（Blameless）、システムとプロセスの改善アクション（担当・期限付き）を確定する。
📌 重要

本番障害の最中に「プロンプトを少しずつ書き換えて様子を見る」のは厳禁です。変更履歴が錯綜してロールバック不能になり、復旧を遅らせます。まずは既知の安定バージョンへ戻すことが最優先です。

Claude Tag と Claude Cowork を活用した実務ワークフロー

  • オンコールアラートのトリアージ（Claude Tag）: オンコールチャンネルに /invite @Claude で招待し、プロアクティブな返信をオンにして監視・ページング・コードホストを接続します。ランブック・担当者リスト・ロールバック承認ルールを一度指示すれば、アラート発生時にスレッドへ原因・影響・修正案を投稿し、オンコール担当者の承認後にロールバック実行とドラフト PR 作成を行えます。スケジュールルーティンで緩やかな劣化の定期監視や月曜の引き継ぎ投稿も可能です。
  • エスカレーションの自動トリアージ: チケッティングツールと連携し、過去チケット照合・担当チームタグ付け・P1 の場合のみ担当者へ @メンション・初回返信の下書きを行います。Claude は顧客への返信を下書きにとどめ、自動送信はしません（担当者がレビューして送信します）。スレッド内の訂正はチャンネルメモリに記憶させられます。
  • インシデントポストモーテム（Claude Cowork）: Engineering プラグインの /incident-response スキル＋作業フォルダ（テンプレート、ランブック、ログ）＋ Connectors を活用し、タイムスタンプ付きの出来事再構築、根本原因と寄与要因の分離、担当者付きアクションアイテム、ブレームレス言語でドラフトを作成します（/schedule で解決済みインシデントの定期生成も可能）。
  • サポートインシデントの顧客向けレビュー: Operations プラグインの /runbook や /status-report を出発点に、顧客向けレビュー（/incident-review）を作成します。対象読者（CSM 転送用）の明示、影響顧客数と期間の数値化（SLA クレジット用）、顧客の直接引用、タイムスタンプによる時間範囲限定、内部向け付録と顧客向け文書の分離がポイントです。

B。ツール結果自体はワーカー内にあり、親に届くのはワーカーの最終メッセージだけです。出力指示やハーネス側の構造化出力契約を見直すべきです。

A. 問題の顧客カテゴリの入力例を収集し、数時間かけて新しいプロンプトを設計・テストする B. まずプロンプトを直前の安定バージョンへ即時ロールバックして顧客影響を止め、その後に拒否された入力のトレースを分析する C. すべての安全ガードレールを無効化する D. モデルの temperature を 1.0 に上げて回答の多様性を増やす

解答

B。インシデント対応の基本は「まず止血（ロールバック）」です。原因分析と修正は影響を止めたあとに行います。

第5章 評価エンジニアリングと品質保証（配点 12%）

💡 ヒント

この章のたとえ：自動車の「衝突安全テスト場」と「計測器の校正」

新しいエンジン（プロンプトやモデル）を公道（本番環境）に出す前に、テストコース（CI/CD 評価ゲート）で合格させなければなりません。しかし、計測器（LLM-as-judge）自体が狂っていれば、危険な車が合格し続けます。まずは人間のプロの評価（ラベル付きデータ）で計測器をキャリブレーションし、コースが古びて暗記されないよう定期的にテストコースも刷新します。

この章のゴール

  • ゴールデンセット、回帰テスト、CI/CD 評価ゲートを含むオフライン評価システムを設計し、長期的な妥当性（汚染・飽和・カバレッジ不足対策）を維持できる。
  • 人間ラベルと照合して LLM-as-judge をキャリブレーションし、位置バイアス等の歪みを排除して信頼できるジャッジを構築できる。
  • 本番ライブトラフィックでのサンプリング、A/B テスト、フィードバックループ、タスク種別に応じたオンライン評価指標を選択できる。

要点3つ

  1. キャリブレーションされていない LLM-as-judge にリリースゲートを任せてはならない。 位置バイアス（先に出た方を好む等）をランダム化で抑え、人間のラベルとの一致度（Cohen's kappa 等）が許容水準に達するまでゲート権限を与えない。
  2. 評価スイートは「作って終わり」にすると腐敗する。 テストデータの汚染（Contamination）、全問正解による飽和（Saturation）、本番分布との乖離（カバレッジ不足）を防ぐため継続的に更新する。
  3. オフライン評価とオンライン評価は車の両輪。 リリース前はゴールデンセットと CI ゲートで守り、リリース後はライブトラフィックのサンプリング・A/B テスト・タスク別指標（抽出・生成・エージェント・検索）で実品質を測る。

LLM-as-judge別の LLM（または評価用プロンプト）を使って出力品質を自動採点する手法
位置バイアス (Position Bias)ペア比較において、内容ではなく「最初（または最後）に提示された回答」を好んで選んでしまう LLM ジャッジの偏り
評価者間信頼性 (Inter-rater Reliability)人間同士、または人間と LLM-as-judge の判定がどれだけ一致しているかの指標（Cohen's κ など）
キャリブレーション (Calibration)ジャッジのスコアや判定基準が、人間の専門家ラベルの判断と一致するように調整・検証すること

5-1 評価システムの設計と長期維持

本番運用では「変更したら悪化した（リグレッション）」をリリース前に防ぐため、オフライン評価システムを構築します。

評価スイートの構成要素

  1. 動作チェック (Behavioral Checks): 決定論的な単体テスト（JSON スキーマ準拠、禁止語不使用、期待ツールの呼び出し有無）。高速・低コスト。
  2. 検索・グラウンディング指標: 検索の適合率（Retrieval Precision）と再現率（Recall）、回答が根拠文書に基づいているか（Groundedness / Faithfulness）。
  3. 回帰テストスイート: 過去のインシデントや既知の難しいエッジケースを集めたテスト群。
  4. 非決定的なエージェントの評価（pass@k vs pass^k）: エージェントは試行ごとに経路が変わるため、単一実行だけでなく複数試行で評価する。「k回中1回でも成功すればよい」探索タスクには pass@k を、本番の信頼性（k回連続で成功すべきタスク）には pass^k を用いる。また、最終結果だけでなく トランスクリプト（ツール呼び出し軌跡） も採点し、インフラノイズ（コンテナ・ネットワーク揺らぎ）を分離する。
  5. ゴールデンセットとリリース基準: 本番分布を反映した代表ケース。プロンプト・モデル・エージェント変更時に「必須テスト 100% 合格＋品質スコア劣化なし」等のゲート基準を設定する。

CI における継続的なエージェント設定評価

CLAUDE.md、.claude/**（スキル・フック）、evals/** の変更時や定期スケジュール（例：cron: '0 2 * * *'）で、CI（GitHub Actions 等）から claude -p を非対話実行して設定変更の回帰を検証します。

  • eval スイートの構築: 直近の作業から 20〜50件 の実タスクを eval JSON（from コミット、prompt、may_change 許可ディレクトリ、checks 配列）として定義します。本番インシデント発生時は再現 eval を必ずスイートに追加します。
  • 改ざん防止のワークツリー分離: 実行前に evals/ を /tmp/evals へ退避し、git worktree add --detach /tmp/run <from> で過去コミットをチェックアウトします。チェックアウト内の evals/ と .claude/ を削除したうえでテスト対象の CLAUDE.md と .claude/ をコピーして実行することで、エージェントがテストやチェック自体を書き換えるのを防ぎます。
  • フラグと検証の注意点: --bare フラグは高速起動のために CLAUDE.md・スキル・フックをスキップするため、設定評価スイートでは絶対に追加してはいけません。evals/check.sh では git status --porcelain で may_change 以外のファイル変更を検知して失敗させ、--output-format json の is_error も確認します。

5-2 LLM-as-judge のエンジニアリング

自然言語の品質や複雑な推論をすべてコードで採点することは困難なため、LLM-as-judge を用いますが、設計と校正を誤ると偽の安心感を生みます。

よくあるバイアスと対策

バイアス／問題内容対策
位置バイアスペア比較で A（先頭）を無意識に多く選ぶ提示順序をランダム化（または A/B 入れ替えて両方評価） し、一貫しない場合は引き分け・無効とする
冗長性バイアス中身が薄くても長い回答を高評価するルーブリックに簡潔性・過剰情報の減点基準を明記し、事実単位（Factuality）で採点させる

キャリブレーションの鉄則

  1. まず人間がラベル付けした代表サンプル（例：100〜200件）を用意する。
  2. 明確なルーブリック（1〜5点の具体例付き、または Pass/Fail の二値基準）を設計する。
  3. LLM-as-judge の判定と人間ラベルの一致度（一致率や Cohen's kappa）を測定する。
  4. 一致度が許容水準に達するまで、CI/CD のリリースゲートとしての権限を与えない。

5-3 オンラインでの品質測定

オフラインテストをすべて通過しても、本番のリアルなユーザー行動は予測を超えます。

  • ライブトラフィックのサンプリング: 本番トラフィックの一部を継続的に抽出し、オフラインと同じジャッジや人間レビューにかけて品質推移を監視する。
  • A/B テスト: 新旧のプロンプトやモデルをトラフィック分割して比較し、ユーザー行動（解決率、再質問率、離脱率、Thumbs Up/Down）で統計的有意差を検証する。
  • タスク種別に合った指標の選択:
タスク種別適切な指標
構造化抽出フィールド単位の完全一致（Exact Match）、F1 スコア、スキーマ準拠率

5-4 Claude が選ぶツールの設計と評価

Claude が誤ったツールを選ぶ、呼び出し回数が多すぎる、引数形式を間違えるといった場合、まず確認すべきは ツール定義（name, description, input_schema, input_examples） です。

  • 良い description の4要素（最低3〜4文、複雑な場合はさらに詳しく記述）:
    • 何をするか
    • いつ使うべきか／いつ使うべきでないか（使わない場合の代替ツール名も明記）
    • 各パラメータの意味・正規化ルール
    • 何を返さないか
  • input_examples（任意）: 望ましい入力例（例：MEG-2026-0142）を示します。input_schema に対して有効でない例を書くと API が 400 エラーを返す点に注意が必要です。
  • 重複ツールの統合: 似た役割の薄いツールを並べると選択精度が落ちます。fields（enum 配列）パラメータを持つ統合ツールへ整理することで、eval スコアが大きく向上します（コース事例では6ツールを3ツールへ統合し、30問の正答率が 47% → 87% に改善）。
  • デバッグの切り分け: 誤ったツール選択や過剰呼び出しは description とツール統合を見直し、型や形式の誤りはスキーマの description と input_examples を見直します。

まとめ：どう判断するか

状況避ける選択とるべき選択
ペア比較ジャッジが先頭の回答ばかり選び、人間と一致しないそのまま合格しきい値を下げたりモデルだけ変える順序のランダム化（または入れ替え）でバイアスを抑え、人間ラベルで再校正するまでゲート権限を外す
評価スイートで全モデルが 99% を記録している「品質が完璧になった」と判断する飽和を疑い、本番の失敗ケースや高難度ケースを追加して識別力を回復する

構造化抽出タスクのオンライン品質を測りたい文章の流暢さ（Fluency）を LLM に採点させるフィールド単位の正確性、検証エラー率、人間修正率などタスク適合指標を選ぶ

第6章 大規模環境でのコストとレイテンシの最適化（配点 8%）

💡 ヒント

この章のたとえ：物流ネットワークの「配車最適化」と「高速道路の優先レーン」

すべての荷物を大型トラック1台（最上位モデル）で運べば確実ですが、燃料代（コスト）が破綻します。軽トラック（Haiku）で運べる荷物は振り分け、同じルートは定期便（Prompt Caching）を使い、急がない荷物は深夜便（Message Batches API）に回します。急ぐ荷物には、積荷を全部降ろす前に渡し始める工夫（ストリーミング）と、複数スタッフの同時作業（ツール並列実行）を使います。

この章のゴール

  • 使用量とコストのデータに基づき、コストモデリング・モデルルーティング／カスケード・キャッシング・Batch 経済性・テナント予算を設計できる。
  • TTFT（初回トークンまでの時間）と全体レイテンシ（E2E）を区別し、ストリーミング、ツール並列実行、キャッシュチェックポイント、output_config.effort を適切に適用できる。

要点3つ

  1. モデルルーティングとカスケードでフリート全体の単価を下げる。 簡単な分類・抽出は小型モデル（Haiku 等）へルーティングし、確信度が低い・失敗したケースだけ上位モデル（Sonnet / Opus）へカスケードする。
  2. Prompt Caching は「構造の安定性」が命。 長いシステムプロンプト、ツール定義、共通文書をプレフィックスに固定し、cache_read_input_tokens を最大化して入力コストと TTFT を劇的に下げる。
  3. レイテンシは「TTFT」と「全体時間」を切り分けて最適化する。 体感速度（TTFT）にはストリーミングとキャッシュが効き、全体完了時間には並列ツール実行、effort レベル調整、出力トークン抑制が効く。

6-1 大規模環境でのコストアーキテクチャ

フリート規模（数千〜数百万リクエスト/日）になると、1リクエストあたり数円の差が月間数百万円の差になります。

1. コストのモデリングと予測

コストは 入力トークン単価 × 入力量 + 出力トークン単価 × 出力量 + キャッシュ書込/読込費 で決まります。

  • 落とし穴: エージェントループでは、ターンが進むたびに過去の履歴全体が入力トークンとして再課金される ため、ターン数が 2倍になると総入力トークンは 4倍近く膨らみます。Prompt Caching と Context Editing が不可欠な理由です。

2. モデル階層とルーティング／カスケード

3. キャッシング戦略と Programmatic Tool Calling（導入順）

ツール多用型ワークフローでは、まずプロンプトキャッシング、次に Programmatic Tool Calling の順で導入します。

  • プロンプトキャッシングの仕様と料金（Sonnet 5）: ツール定義リストの最後のツールに cache_control: {"type": "ephemeral"} を追加（またはトップレベル cache_control を指定）してプレフィックスをキャッシュします。読み取りは 1/10（0.1倍）、書き込みは 1.25倍（デフォルト TTL 5分、使用ごとに更新）、"ttl": "1h" は書き込み 2倍 です。なお、Sonnet 5 ではキャッシュ対象プレフィックスが 最低 1,024トークン 必要です（未満だとエラーなしでキャッシュされません）。総入力トークンは input_tokens + cache_read_input_tokens + cache_creation_input_tokens で計測します。
  • 診断: cache_read_input_tokens が想定より低い場合、直前にタイムスタンプや動的 ID を混入させて プレフィックスを壊していないか、1文字でも定義を変えていないか、TTL を超えて失効していないかを確認します。
  • Programmatic Tool Calling（プログラムによるツール呼び出し）: Claude がコンテナ内でスクリプトを実行し、ツール結果をスクリプト側で集計・フィルタして最終要約だけを Claude に返すことで、中間結果の再課金を劇的に削減します。
    • 4つの設定: ① code_execution_20260120 以降を tools に追加、② 対象ツールに "allowed_callers": ["code_execution_20260120"] を設定、③ レスポンスの resp.container.id を次回リクエストの container= に渡す、④ スクリプトがパースできるようツール定義に戻り値の JSON 形状を明記。
    • 非対応制約: strict: true ツール、disable_parallel_tool_use、tool_choice による強制、Claude Haiku 4.5 では利用できません。互いに依存しないルックアップに最適です。

4. Batch API とリアルタイムの経済性

  • Message Batches API: 同期 API 比 50% 割引。夜間バッチ、大規模データ抽出、オフライン評価の大量実行に最適。
  • 使えない場面: ユーザーが待機している対話 UI、24時間以内の厳格な短時間 SLA が必要な処理、途中で外部ツール往復が必要なエージェントループ。

5. テナントごとの予算適用

  • ハードリミット到達時：完全拒否（429）するか、自動的に安価なモデル／低 effort モードへグレースフルデグラデーションさせるかを契約プランに応じて設計する。

確認問題

問1

あるマルチステップの検索エージェントで、E2E レイテンシ（全体完了時間）が 12秒かかっており、目標の 5秒を超えています。トレースを見ると、1回の処理で互いに依存しない4つの社内 DB 検索ツールを 4ターンに分けて1つずつ直列実行していました。E2E レイテンシを短縮する最も効果的な変更はどれですか。

A. ストリーミングを有効化する B. 4つの独立したツール呼び出しを1回のモデル応答で並列宣言させ、ハーネス側で非同期に並列実行する C. システムプロンプトを短くする D. Message Batches API に切り替える

解答

B。独立したツール呼び出しを並列化することで、4回分のネットワーク往復とツール待ち時間を1回分に圧縮でき、E2E レイテンシを大幅に削減できます。ストリーミング（A）は TTFT（体感）には効きますが、ツール実行を含む全体の完了時間は短縮しません。

問2

長いシステムプロンプト（15,000トークン）に Prompt Caching を設定しているにもかかわらず、メトリクスを見るとキャッシュヒット率が 5% 未満で、ほぼ毎回 cache_creation_input_tokens が課金されています。最も可能性の高い原因はどれですか。

A. 出力トークン数が多すぎるため B. システムプロンプトの先頭付近に「現在時刻（秒単位）」や「リクエストごとの一意な ID」を埋め込んでおり、プレフィックスが毎回変化しているため C. ストリーミングを使用しているため D. モデルの effort を high にしているため

解答

B。Prompt Caching は先頭からの完全一致が条件です。先頭付近に動的な値（現在時刻、ランダム ID、ユーザー固有情報）があるとキャッシュが毎回ミスします。動的情報は末尾の user メッセージに置くべきです。

問3

ある開発チームは、定型的なコードスタイルチェックや簡単なデータ抽出を行うサブエージェントでも、デフォルトの high effort を使用しているため、不要に長い思考プロセスと遅延が発生しています。モデルファミリーを変えずにレイテンシと出力トークンコストを抑える最も適切な設定はどれですか。

A. output_config.effort を low（または medium）に調整する B. stop_reason を無視して 2秒で接続を切る C. リトライ回数を増やす D. max_tokens を 10 に設定する

解答

A。effort パラメータを下げることで、同一モデルのまま思考トークンや出力の冗長さを抑え、レイテンシとコストを最適化できます。

問4

以下の4つのワークロードのうち、Message Batches API の利用が最も不適切なものはどれですか。

A. 毎晩深夜に実行する 5万件のサポートチケットの感情分析・タグ付け B. オフライン評価スイート（3,000問）のモデル回答一括生成 C. ユーザーが画面の前で結果を待っており、途中で 3〜4回の外部 API ツール往復が必要な対話型トラブルシューティングエージェント D. 週次の法務文書アーカイブからのメタデータ抽出

解答

C。Message Batches API は最大24時間の非同期処理（即時性保証なし）であり、途中のツール往復を伴うリアルタイム対話には使えません。

問5

ツールを多数呼び出すワークフローでプロンプトキャッシングを導入したものの、40ターン近くかけて大量のツール結果を処理するため入力コストが依然として高額です。次にとるべき施策と必要な設定はどれですか。

A. code_execution_20260120 を tools に追加し、対象ツールに "allowed_callers": ["code_execution_20260120"] を設定して Programmatic Tool Calling を行い、次ターンへ resp.container.id を渡す B. strict: true と disable_parallel_tool_use を同時に有効にして Programmatic Tool Calling を使う C. 並列ツール呼び出しの tool_result を1件ずつ別々の user メッセージに分けて送信する D. Claude Haiku 4.5 に切り替えて Programmatic Tool Calling を実行する

解答

A。Programmatic Tool Calling により、コンテナ内のスクリプトでツール結果を処理して要約だけを Claude へ返すことでトークンとコストを大幅に削減できます。strict: true、disable_parallel_tool_use、tool_choice 強制、Claude Haiku 4.5 は非対応であり、また通常の並列ツール呼び出しではすべての tool_result を1つの user メッセージにまとめる必要があります。

問6

Claude Opus 5 でアダプティブ思考を有効にしつつ、effort を high に設定して思考要約も取得したい場合、正しい API パラメータ配置はどれですか。

A. thinking={"type": "adaptive", "effort": "high"} とし、display は省略する B. thinking={"type": "adaptive", "display": "summarized"} とし、output_config={"effort": "high"} のように output_config 内に配置する C. client.messages.stream() を使う場合はツールループを完全に書き直す必要がある D. 単純な分類タスクでも常に effort: "max" とアダプティブ思考を併用する

B。effort は thinking ブロック内ではなく output_config 内に配置し、思考テキストを表示するには "display": "summarized" を指定します。なお、client.messages.stream() でも最後に stream.get_final_message() を呼べば既存のツールループをそのまま維持できます。

第7章 ランタイムガードレールと本番環境のセキュリティ（配点 11%）

💡 ヒント

この章のたとえ：銀行の「多層金庫」と「警備システム」

窓口係（プロンプト）に「強盗にお金を渡さないで」とお願いするだけでは、巧みな話術（プロンプトインジェクション）で騙される可能性があります。本番セキュリティでは、入口の金属探知機（入力フィルタ）、金庫の物理ロックと二段階承認（決定論的ゲート・フック・承認）、隔離された応接室（サンドボックス）、そして持ち出し先のホワイトリスト（最小権限・宛先許可リスト）という モデルの外部の強制力 を何重にも重ねます。

この章のゴール

  • エージェントのリスクプロファイルに応じて、入出力フィルタ、PII リダクション、フック、サンドボックス、承認ゲートを含む多層ガードレールを設計できる。
  • ツールを使用するエージェントの攻撃対象領域（プロンプトインジェクション、ツール／メモリポイズニング、データ流出、高リスクな3要素の組み合わせ）を分析し、OWASP Top 10 for LLM Applications や NIST AI RMF に基づく緩和策とレッドチーム演習を設計できる。
  • ワークロード ID フェデレーション、シークレット管理、最小権限、監査ログを含むエンタープライズ向け ID・セキュリティ基盤を適用できる。

要点3つ

  1. 不可逆なアクションとデータ流出をプロンプトだけで防いではならない。 システムプロンプトの警告は強制力のない「お願い」に過ぎない。宛先許可リスト、承認ゲート、フック（PreToolUse）、最小権限という モデル外部の決定論的制御 で遮断する。
  2. 「プライベートデータ ＋ 信頼できない入力 ＋ 外部通信」の3要素が揃う構成が最も危険。 どれか1つでも遮断するか、外部通信前に人間の承認や許可リストを強制する（多層防御）。
  3. 静的 API キーを廃し、ワークロード ID フェデレーションと最小権限を徹底する。 エージェント自身の ID と権限をスコープ化し、セキュリティ上重要なアクションは改ざん不能な監査ログに残す。

偽陽性 (FP) と偽陰性 (FN) のチューニング

  • 高リスク操作（医療処方・送金・削除）: 偽陰性（見逃し）を極小化するため厳格にし、ブロック時は人間エスカレーションや安全なフォールバック応答を返す。
  • 低リスク操作（社内ドキュメント要約）: 偽陽性（過剰ブロック）が多すぎると利用者が使わなくなるため、人間のフィードバックをもとにしきい値を調整する。
  • 注意: 「ロギング（記録）」は事後の 検知（Detection） であり、流出の 防止（Prevention） にはならない。

フック（Hooks）の決定論的制御と落とし穴

CLAUDE.md の指示（「たいてい従う」）と異なり、settings.json のフック（${CLAUDE_PROJECT_DIR} 参照、/hooks で一覧確認）は必ず実行される決定論的制御です。

  • 主要イベント: PreToolUse（唯一の事前強制プリミティブ）、PostToolUse（編集後の自動フォーマット・lint）、Stop / SubagentStop（ターン終了を拒否し続行させる）、PreCompact / PostCompact、InstructionsLoaded（コンテキスト読み込み監査）、SessionStart。
  • 終了コードの落とし穴: 0 は続行、2 はブロックして標準エラー出力（stderr）を Claude へフィードバックします。終了コード 1（および 2 以外の非ゼロ）はノンブロッキングエラーでありブロックしない点に注意が必要です。
  • コンパクション後の再注入: コンパクション後にコンテキストを再注入するには PostCompact ではなく compact マッチャー付きの SessionStart を使います（stdout のプレーンテキストが会話コンテキストに戻る）。
  • PreToolUse の JSON 出力と updatedInput: hookSpecificOutput.permissionDecision で "allow" / "deny" / "ask" / "defer"（非対話 -p の一時停止・再開用）を返します（非対話実行では ask は拒否扱い）。updatedInput でコマンド内のシークレットをプレースホルダーにリダクトして実行継続する場合は、入力オブジェクト全体を置換するため変更しないフィールドも書き戻す必要があります。

7-2 エージェント型システムの脅威対策と敵対的テスト

信頼できないコンテンツ（外部 Web、ユーザー投稿、顧客チケット、メール）を処理し、かつツールを使うエージェントは攻撃対象領域が広がります。

最も危険な「3要素の組み合わせ」への対処

エージェントが以下の3つを同時に持つと、間接プロンプトインジェクションによる データ流出（Data Exfiltration） が成立します。

  1. プライベートデータへのアクセス（CRM、社内 DB、メール履歴）
  2. 信頼できない入力（外部チケット、Web ページ、添付ファイル）
  3. 外部との通信経路（メール送信ツール、外部 Webhook、任意の URL への HTTP リクエスト、画像 URL 埋め込み）

塞ぎ方（決定論的制御）:

  • 外部通信ツールに 宛先許可リスト（Allowlist） または 承認ゲート を設ける。
  • CRM アクセスを「そのチケット自身の顧客アカウント」だけに 最小権限でスコープ限定 する。
  • やってはいけない対策: 「チケット内の指示を無視せよ」とシステムプロンプトを強く書き直すだけ、またはモデルの effort を下げるだけ。

フレームワークと安全な MCP 構成

  • OWASP Top 10 for LLM Applications: プロンプトインジェクション（LLM01）、機密情報漏洩（LLM02）、サプライチェーン／MCP 脆弱性（LLM03）、過剰な自律性（Excessive Agency, LLM06）などを体系的に点検する。
  • NIST AI Risk Management Framework (AI RMF) & GenAI Profile: Govern / Map / Measure / Manage の 4機能に沿ってリスク評価とレッドチーム演習を継続的に実施する。
  • 安全な MCP 構成と API 接続: 信頼できる署名済み・許可リスト登録済みの MCP サーバーのみ接続し、ツール説明の改ざん（Rug Pull / ツールポイズニング）を監視する。なお、ツールは内部システム用（自前保守）、スキルは手順用、MCP はサードパーティサービス用と使い分ける。API ベータ（betas=["mcp-client-2025-11-20"]）で mcp_servers と mcp_toolset を使う場合は、default_config: {"enabled": False} とし、configs で読み取り専用ツールのみ {"enabled": True} にして最小権限・コンテキスト節約を徹底する。

コネクタの3ゲートと EMA・Claude Tag 管理者ガイド

  • コネクタの3つの独立したゲート（すべて開く必要あり）: ①組織ゲート（Owner / Primary Owner）、②ロールゲート（既存ロールはデフォルト Always allow、新規作成ロールはデフォルト Needs approval）、③メンバーゲート（本人の接続、または IdP 経由で自動接続・オフボーディング連動する EMA: Enterprise-managed authorization）。書き込み・削除ツールはリスクオーナー承認のもと段階的に付与する。
  • マルチプレイヤーエージェント（Claude Tag）の特性と統制: シングルプレイヤー AI とは「独自のアイデンティティと認証情報」「共有された記憶」「共有されたコンテキスト」の3点が異なる。
    • 利用前提と PHI 禁止: Team / Enterprise Plan 対象、Scheduled tasks (Was Routines) 有効化が必須。ZDR、CMEK、ローカルモード用 HIPAA 構成を有効にしている組織では利用不可であり、BAA 対象外のため PHI（保護対象保健情報）を扱う環境へ導入・接続してはならない。
    • 3スコープと認証情報: Slack ページ（組織ルート）＞ ワークスペース ＞ 単一チャンネル の順に適用され、同一ホストの認証情報は最も狭いスコープが優先（401/403 でもフォールバック再試行なし）。外部リクエストは Agent Proxy を通過する際に認証情報が付与されるため、サンドボックス内に資格情報は届かない。
    • アイデンティティとホワイトリスト運用: チャンネル／グループ DM では Claude Tag 自身のサービスアカウントで動作するため、GitHub のブランチ保護で 2件の承認レビューを推奨（1対1 DM は接続済みユーザー本人のアカウント・席課金）。Respond in all channels と DM をオフにして承認チャンネルのみ許可し、ゲスト／Slack Connect チャンネルはデフォルト Restrict（沈黙）を維持する。制御コマンドは !mute, !unmute, !restart, !configure, !status（👎リアクションでスレッドミュート）。

確認問題

問1

社内サポートエージェントが、顧客チケットの本文を読み、CRM からアカウント情報を取得して、ツール経由で外部メールを送信できます。レッドチーム演習で、チケット本文に隠された指示によって別顧客のレコードを検索し、攻撃者の外部アドレスへメール送信されてしまいました。チームは既に「チケット内の指示を無視せよ」というシステムプロンプトを追加しています。この悪用経路を最も直接的に塞ぐ追加対策はどれですか。

A. より強い言葉で「顧客データの流出は禁止」とシステムプロンプトに追記する B. メール送信ツールに宛先の許可リストまたは人間による承認ゲートを適用し、CRM へのアクセス権限をそのチケット自体のアカウントのみに限定する C. モデルの effort レベルを low に下げる D. 送信された全メールの宛先と本文を事後調査用にログ記録する

解答

B。公式試験ガイドのサンプル問題です。「プライベートデータ ＋ 信頼できない入力 ＋ 外部通信」が揃っているため、プロンプトレベルの指示では防げません。モデル外部の決定論的制御（許可リスト・承認ゲート・最小権限スコープ）で経路を物理的に塞ぎます。

問2

組織で複数のサードパーティ製 MCP サーバーを本番エージェントに導入する際、ある MCP サーバーがアップデート後にツールの description を書き換え、エージェントに秘密ファイルを外部へ送信させようとする「ツールポイズニング（Rug Pull）」のリスクが懸念されています。最も適切な緩和策はどれですか。

A. MCP サーバーのツール定義をモデルの推論で毎回チェックさせる B. MCP サーバーをバージョン固定＋許可リスト管理し、ツール定義のスキーマ・説明の変更検知（CI/CD 審査）と、外部通信・ファイルアクセスに対する最小権限・エグレス制御を強制する C. すべての MCP ツールに allowedTools を設定して自動承認する D. 開発者に口頭で気をつけるよう周知する

解答

B。サプライチェーン／ツールポイズニング対策には、MCP の許可リスト化・バージョン固定・変更監査と、サンドボックス／最小権限による多層防御が必要です。

問3

クラウド上の Kubernetes クラスタで稼働する多数のエージェントから、外部 SaaS や Claude プラットフォームへ認証する際、セキュリティ監査で「静的 API キーの長期保管」が指摘されました。エンタープライズのベストプラクティスとして置き換えるべき仕組みはどれですか。

A. API キーを Base64 エンコードして Git リポジトリに保存する B. ワークロード ID フェデレーション（OIDC 等）を導入し、短期有効な認証トークンを動的に発行・交換する C. 全エージェントで1つの共通マスターキーを使い回す D. 認証自体を無効化して IP 制限のみにする

解答

B。静的シークレットの漏洩・ローテーション漏れを防ぐため、クラウド環境ではワークロード ID フェデレーションによる短期トークン認証が標準です。

問4

本番のエージェントが「顧客のクレジットカード番号をそのまま出力に含めてしまう」インシデントを防ぐため、最も確実なランタイムガードレールの配置はどれですか。

A. 出力後のユーザー画面で CSS を使って文字色を白にする B. モデルのプロンプトに「カード番号は書くな」と記載するだけにする C. モデルの入力前・出力後の両方に決定論的な PII リダクション／マスキングフィルタを配置し、そもそもツール戻り値から不要なカード番号フィールドを除外する D. temperature を 0 に設定する

解答

C。ツール戻り値からの事前除外（最小権限データ）と、入出力での決定論的 PII リダクションを組み合わせることで、モデルの気まぐれに依存しない確実な防御になります。

問5

Claude Code のフックで危険なツール呼び出しを確実にブロックし、かつコンテキストのコンパクション後に重要な開発ルールを再注入したい場合、正しい組み合わせはどれですか。

A. フックのスクリプトを終了コード 1 で終了させ、再注入には PostCompact フックを使う B. フックのスクリプトを終了コード 2 で終了させて stderr を Claude に返し、再注入には compact マッチャー付きの SessionStart フックを使う C. 無人実行ではセキュリティのため常に --dangerously-skip-permissions を使う D. マネージド設定で allowManagedHooksOnly: true を有効にしつつ、必須フックはリポジトリ側の .claude/settings.json にだけ書く

解答

B。終了コード 1 はノンブロッキングエラーであり、ブロックするには必ず終了コード 2 を使います。コンパクション後のコンテキスト再注入は PostCompact ではなく compact マッチャー付きの SessionStart を使います。なお、allowManagedHooksOnly: true を有効にするとプロジェクト設定のフックは無効化されるため、必須フックはマネージド設定自体に定義します。

問6

Slack で動作する Claude Tag を企業へ導入する際のセキュリティ・コンプライアンス判断として正しいものはどれですか。

A. ZDR やローカルモード用 HIPAA 構成を有効にしている組織でもそのまま導入できる B. チャンネル内では Claude Tag 自身のサービスアカウントで動作するためブランチ保護で 2件の承認レビューを推奨し、外部通信の資格情報はサンドボックス内には置かず Agent Proxy 経由で付与する C. 同一ホストの認証情報が 401/403 を返した場合、より広い親スコープの認証情報へ自動フォールバックする D. ゲストが参加する Slack Connect チャンネルでもデフォルトでフルアクセス応答が有効になっている

解答

B。Claude Tag は ZDR / CMEK / ローカルモード用 HIPAA 構成組織では利用不可です。同一ホスト認証情報は最も狭いスコープが優先されフォールバックせず、ゲスト／Slack Connect チャンネルのデフォルトは Restrict です。

自分で確かめる

  1. 自身が運用・設計中のエージェントについて、「プライベートデータ」「信頼できない入力」「外部通信」の3要素が揃っていないか棚卸しし、揃っている場合はどこに決定論的制御を入れるか図示してみる。
  2. PreToolUse フックで、特定の禁止パラメータ（例：外部ドメイン宛メール、許可されていないディレクトリの削除）を終了コード 2 でブロックする小さなテストを書いてみる。

第8章 ソフトウェア提供のためのエージェントフリート運用（配点 10%）

💡 ヒント

この章のたとえ：複数ラインの「自動工場」と「品質管理ライン長」

1人の職人（単一エージェント）ではなく、何十台ものロボット（コーディングエージェント群＝フリート）を同時に動かしてソフトウェアを作る時代です。同じ作業台を共有させると部品がぶつかるため、作業台を分け（git worktree）、製造スピードが人間の検査を上回るなら自動検査機（AI コードレビュー）を「まずは試運転（シャドーモード）」から始め、工場全体のルール（管理設定・MCP 許可リスト・ガバナンス）を統一します。

この章のゴール

  • 分離されたワークツリー（git worktree）、タスク分解、マージ／コンフリクト戦略を含む並列ファンアウトを設計し、フリートレベルの障害を診断できる。
  • 生成速度が人間レビューを上回る環境で、シャドーモード導入・人間レビューとのキャリブレーション・監督設計を伴う AI コードレビューを運用できる。
  • 目標駆動・スケジュール駆動・イベント駆動の無人エージェント（ヘッドレス運用）を、チェックポイント・通知・エスカレーション付きで設計できる。
  • 管理設定（Managed Settings）、MCP 許可リスト、ゲートウェイ、Skills／プロンプト／MCP 共有のガバナンスを組織全体に適用できる。

要点3つ

  1. 並列コーディングエージェントは「ワークツリーの分離」と「共有ファイル回避の分解」が前提。 同一ディレクトリで並列編集させると競合と上書きが起きるため、git worktree で作業空間を分け、インターフェース境界に沿ってタスクを分解する。
  2. AI コードレビューはいきなりマージゲートにしない。 まずシャドーモードで導入し、人間のレビュー指摘とキャリブレーションして精度（偽陽性・見逃し）を確認してからブロッキング権限を与える。
  3. 組織導入は「管理設定・許可リスト・ガバナンス」で統制する。 開発者個人の判断任せにせず、エンタープライズ管理設定、MCP 許可リスト、統一テレメトリ、ゲートウェイルーティング、共有 Skills／MCP の品質・安全審査を敷く。

8-2 検証と AI コードレビューの運用

コーディングエージェントが大量の PR を生成するようになると、人間のコードレビューがボトルネック になります。かといって検証を緩めると本番障害が増えます。

AI コードレビュー導入の3段階

  1. シャドーモード導入: 本番の PR に対して AI レビューを実行するが、結果は開発者や管理用ダッシュボードに記録するのみで マージはブロックしない。
  2. 人間レビューとのキャリブレーション: 人間のシニアエンジニアの指摘と AI の指摘を比較し、重大なバグの見逃し（偽陰性）と、ノイズになる些細な指摘（偽陽性）を調整する。
  3. ゲート昇格と人間による監督: 一致度が基準を満たした領域（セキュリティ・型不整合・回帰テスト欠如など）からマージゲートへ昇格させ、設計判断や高リスク変更は 人間による最終承認 を残す。
📌 重要

コードを生成したエージェントと 同じセッション・同じ推論文脈 で自己レビューさせてはなりません。生成時のバイアスを引き継ぐため、差分と規約のみを渡した独立したレビュープロセスを使います。

REVIEW.md・マネージド Code Review・GitHub Action の使い分け

  • REVIEW.md の運用: リポジトリルートに配置し、レビューのパス（Bugs / Security / Compliance）、Important と Nit の定義、Cap the nits（例：1レビュー最大5件）、Do not report（src/gen/ 等）を定義します。同じ誤りが2回指摘されたら CLAUDE.md にルールを追記し、月1回 REVIEW.md をチューニングします。
  • マネージド Code Review（Team / Enterprise）: Owner が管理設定で Allow code review を有効化し、Claude GitHub app を導入します。PR 作成・プッシュ・@claude review 時に重複排除・ランク付けされたインラインコメントを投稿しますが、承認・ブロック・修正プッシュは行いません（ブランチ保護の職務分掌を維持、ローカル修正には /code-review --fix を使用）。
  • GitHub Action（anthropics/claude-code-action@v1）: レビューを超えた作業（@claude メンションからの実装、cron 定期レポート等）に使います（/install-github-app で導入）。id-token: write 権限とワークロード ID フェデレーション（または anthropic_api_key / use_bedrock 等）、prompt（自動実行時）、claude_args（--max-turns 5 等）を設定します。

8-3 無人実行とイベント駆動のエージェント運用

コーディングエージェントは、人間が画面を見ているときだけでなく、バックグラウンドで自律稼働します。

駆動タイプ例必須の安全設計
目標駆動 (Goal-driven)テストカバレッジ 80% 達成、特定ライブラリの移行完了まで反復明確な終了条件（テスト通過）、max_turns・コスト上限、チェックポイント保存。長時間タスクはローカル占有を避ける Cloud session（クラウドサンドボックス）と手元環境を使う Remote Control を使い分ける
スケジュール駆動 (Scheduled)毎晩の依存関係脆弱性パッチ PR 作成、デッドコード整理変更範囲の制限、自動テスト通過後の Draft PR 作成（自動マージしない）
イベント駆動 (Event-driven)CI/CD 失敗・本番アラート発生時の一次調査（トリアージ・原因 PR 特定・修正案提示）冪等な再実行制御、一定時間／失敗回数での 人間への通知とエスカレーション

自動化のスペクトラムと長時間セッションの操縦

  • 4段階の自動化手段:
    • クラウドスケジュールタスク（旧称ルーティン、リサーチプレビュー）: claude.ai/code/routines や /schedule で設定（cron / HTTP POST / PR イベント）。最短間隔は1時間ごとで、デフォルトブランチの新規クローンから開始し claude/ ブランチにプッシュします（PR トリガー時は PR ヘッドから開始）。
    • ヘッドレスモード（claude -p）: --output-format json --json-schema '...' で .structured_output に構造化出力を得て、claude --resume "$(jq -r .session_id /tmp/plan.json)" でステップ分割再開できます。
    • --bare フラグ（CI 向け決定論的実行）: フック、Skills、プラグイン、MCP、CLAUDE.md の自動検出をスキップし、--settings や --mcp-config で明示指定したものだけを読み込みます（サブスクリプション認証を使わないため ANTHROPIC_API_KEY が必須）。
    • Agent SDK: TypeScript / Python で query 関数を呼び出し、自社アプリへ組み込みます。
  • 長時間セッションの操縦ツール: プランモードでの事前精査、方向指定付き圧縮（/compact <残したい焦点>）、Esc 2回の巻き戻し（コードと会話を復元／会話を復元／コードを復元／ここから要約／ここまで要約の5択）、/goal <完了条件>（評価器はトランスクリプトしか読めないためテスト出力等で確認可能な条件にする）、ループ監視（自己ペースまたは固定間隔・最大7日）。
  • Slack @Claude 定型業務スケジュール: チャンネルで曜日・時刻・ソース・形式・サイレント条件を1メッセージで指定して作成（@Claude !scheduled で一覧確認、作成者離脱後もチャンネルに残る）。

8-4 組織全体でのコーディングエージェントの構成

全社規模で Claude Code 等を展開する場合、ガバナンスと標準化が不可欠です。

  • 管理設定とポリシー (Managed Settings)・Claude Tag 管理者ガイド: 危険なシェルコマンドの禁止、組織外へのデータ送信制限、ZDR の強制などを管理ポリシーとして配布し、個人設定での無効化を禁止する。また、トリガーやタグ機能を通じた自律実行の権限範囲を組織レベルで統制する。
  • カスタマイズのガバナンス（4つの配布コントロール）: Skill の実行には組織設定で Cloud code execution and file creation と Skills の両方がオンである必要があります。配布は ①Owner provisioning、②Skill sharing（同僚共有）、③Share with groups、④Publishing（Off / Requires review＝自己承認不可 / Open。厳格化しても既公開アイテムは自動削除されないため手動削除が必要）の4つで統制します。
  • MCP の許可リスト: 承認済み・セキュリティ審査済みの社内 MCP サーバーのみ接続を許可し、未検証の野良 MCP の追加をブロックする。
  • テレメトリとゲートウェイルーティング: すべてのエージェント通信を組織の AI ゲートウェイ経由にし、利用量・コスト・エラー率・監査ログを一元収集する。
  • プロンプト・Skills・MCP サーバーの共有ガバナンス: チーム間で再利用する Skills や MCP は中央リポジトリでコードレビュー・自動テスト・セキュリティスキャンを通過したものだけを配布する。

確認問題

問1

大規模なモノレポで、10台の並列コーディングエージェントを同時に動かしてマイグレーション作業を行っています。フリート全体のテレメトリを確認したところ、個別エージェントの実装成功率は高いにもかかわらず、最終的な統合成功率（マージ成功）が 30% に落ちています。最も可能性の高いフリートレベルの障害原因と対策はどれですか。

A. モデルが非協力的であるため temperature を上げる B. エージェント間のワークツリー分離やファイル境界に沿ったタスク分解が不十分で、共通ファイルでのマージコンフリクトと相互上書きが多発しているため、git worktree 分離と依存関係を考慮したタスク分解・統合ステップを導入する C. 各エージェントの max_tokens を増やす D. 並列実行をやめて、常に1人のエンジニアが手動でコードを書く

解答

B。個別タスクが成功しても統合で失敗する場合、並列ファンアウトにおけるタスク分解の境界重複とワークスペース分離不備が典型的な原因です。

問2

コーディングエージェントの導入により PR の作成速度が3倍になりましたが、人間のレビュアーが追いつかず滞留しています。開発チームは AI コードレビューを導入しようとしています。品質を維持しつつ開発を止めない導入手順として最も適切なものはどれですか。

A. 初日から AI が「承認」すれば人間のレビューなしで自動マージする B. まずシャドーモードで AI レビューを動かし、人間のレビュー結果と照合してキャリブレーションを行ったうえで、信頼できる検査項目から段階的にゲート・補助へ組み込む C. レビュー工程そのものを廃止し、本番監視だけで対応する D. コードを生成したエージェントに同じ会話内で「自分のコードを厳しくレビューして」と頼む

解答

B。AI レビューはシャドーモードでの計測と人間レビューとのキャリブレーションを経てからゲート権限を与えるのが安全です。D は自己レビューバイアスがあるため不適切です。

問3

CI/CD パイプラインの夜間ビルドが失敗した際、イベント駆動の無人エージェントを起動して一次対応（原因コミットの特定と修正 PR の作成）を行わせたいと考えています。本番環境への安全性を確保するための必須設計はどれですか。

A. エージェントに本番デプロイ権限と main ブランチへの強制プッシュ権限を与える B. サンドボックス環境でテストを実行させ、修正は人間レビュー用の Draft PR にとどめ、一定ターン数で解決しない場合はログと調査結果を添えて人間へエスカレーション・通知する C. 無人実行ではタイムアウトやターン上限を一切設定しない D. 失敗時はすべてのテストを削除してビルドを通す

解答

B。無人運用では、変更の自動反映を避け（PR＋テスト検証）、コスト・ループ暴走を防ぐ上限と人間へのエスカレーション経路を設計します。

問4

あるエンタープライズ企業が、全社数百名のエンジニアにコーディングエージェント（Claude Code 等）を展開します。セキュリティと品質のガバナンスを保つため、組織レベルで適用すべき構成の組み合わせはどれですか。

A. 各エンジニアの個人の裁量で任意の外部 MCP サーバーをインストールさせる B. 管理設定（Managed Settings）によるポリシー強制、承認済み MCP の許可リスト、ゲートウェイ経由の統一テレメトリ、および共有 Skills・プロンプトの審査基準を適用する C. 全員に共通の個人用 API キーをテキストファイルで配布する D. 監査ログをオフにしてディスク容量を節約する

解答

B。エンタープライズ展開では、管理ポリシー・MCP 許可リスト・統一テレメトリ／ゲートウェイ・共有資産の品質・安全ガバナンスの4点が柱になります。

問5

CI パイプラインで claude -p を使い、ローカルの個人設定や自動検出された MCP・フックの影響を受けない決定論的な実行を行いたい場合、適切な構成はどれですか。

A. --bare フラグを付与し、ANTHROPIC_API_KEY と --settings / --mcp-config で必要な構成だけを明示指定する B. --bare フラグを付与し、サブスクリプションログインの認証情報をそのまま流用する C. クラウドスケジュールタスク（ルーティン）を 1分間隔の cron で実行する D. /goal の完了条件に「画面の見た目が良くなったら終了」とだけ書く

解答

A。--bare フラグはフック・Skills・プラグイン・MCP・CLAUDE.md の自動検出をスキップし、--settings や --mcp-config の明示指定のみを読み込むため決定論的 CI 実行に適しています（ただし ANTHROPIC_API_KEY が必須）。クラウドスケジュールタスクの最短間隔は 1時間ごとであり、/goal の評価器はトランスクリプトしか読めないためテスト出力等で確認できる条件にする必要があります。

問6

チームでマネージド Code Review と anthropics/claude-code-action@v1 を併用する際の役割分担として最も適切なものはどれですか。

A. マネージド Code Review に PR の自動承認と自動マージを任せる B. マネージド Code Review で PR への重複排除・ランク付けされたインラインコメント（承認・ブロックなし）を受け取り、@claude メンションによる修正実装や定期レポートは claude-code-action@v1 に任せる C. バグ修正時はエージェントにテストファイルも同時に書き換えさせて全テストをパスさせる D. 同じ誤りがレビューで2回指摘されても CLAUDE.md や REVIEW.md は更新しない

解答

B。マネージド Code Review はインラインコメント投稿に特化し、承認・ブロック・修正プッシュは行いません（職務分掌を維持）。実装や定期タスクは claude-code-action@v1 を利用し、バグ修正時はテスト編集禁止フックで検証ループを保護します。
